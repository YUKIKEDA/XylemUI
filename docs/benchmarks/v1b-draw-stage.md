# V1b: 描画の段とフレームの駆動

木をたどって表示リストを作る描画の段と、ウィンドウ 1 つのフレームを回す `WindowFrames` を足した（ロードマップの行 V1 の V1b、Issue #312、設計書 §5.0「描画の段とフレームの駆動」）。その正しさと費用を確かめた。どれも Windows 11 26300、Intel Core i5-13400F で、時間は NativeAOT の Release で、プロセスを P コア（論理 CPU 2）に固定し、優先度を上げて測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe frames 600            # 表示リストを直接書く今の場面
<dir>/XylemUI.E2E.exe frames 600 --tree     # 同じ場面を木で作り、WindowFrames で描く
<dir>/XylemUI.E2E.exe layout                # L1a の layout の場面（UiNode の大きさの影響を見る）
```

`frames --tree` の木は、目印の矩形、1,000 個の絶対配置の箱、1 行の文字の葉でできている（`TreeScene.cs`）。1 フレームでは、次の順に進む。

1. 箱を、今の場面と同じ式で動かす（`SetStyle`）
2. layout の pass を流す（`layout_ms`）
3. 見えないノードの背景を切り替える。位置の変更は layout の印だけを付けるので、これで描画の印を付け、2 の後でもフレームが描くようにする
4. `WindowFrames.RunFrame`。`build_ms` は、`RunFrame` の始めから `Draw` までの時間（描画の段とグリフをそろえる処理）である

## 正しさ

- **画素（`DrawStageRenderTests`、WARP、125 %）:** 次の 2 つを、木から描いたものと、同じ命令を絶対座標で直接書いたもので比べた。どちらも画素がすべて一致した
  - 箱の木。影・角丸・枠線・背景の箱、その中の子、描く関数、重なる絶対配置の兄弟、`Hidden` の部分木（描く関数を持つ）を含む。描く関数は絶対座標の箱（10, 10, 120, 60）を受け取り、隠したノードの描く関数は呼ばれなかった
  - 余白のある文字の葉の行。同じ文字を `DrawText` で直接描いたものと、グリフも画素も一致した
- **フレーム（`WindowFramesTests`）:**
  - 変わらないフレームは、Draw も Present もしない
  - 色の変更は、layout をせずに 1 回 Present する
  - 描いている間に付いた印は、次のフレームを頼み、そのフレームで描かれる
- **確定した枠線の幅:** % の枠線を、根・Block の子・Flex の項目・絶対配置の子・幅が未定の根（max-content のビューポート）で解いた。どれも、残した枠線の幅が、layout が子を置いた位置と一致した
- **割り当て 0:** 次の 2 つの場面で 0 バイトだった
  - 色の変更、ウィンドウの大きさの変更、何も変わらないフレーム（100 個の箱）
  - 文字と文字の色の変更（20 個の文字の葉、Debug と Release）
- **ミュータント:** 6 個。どれも、狙ったテストが落ちた
  - 変わらないフレームでも Present する
  - 印を Draw の後で消す
  - Block の枠線を親の幅だけで解く
  - `Hidden` を飛ばさない
  - 描く関数を子の後に呼ぶ
  - 文字の位置に余白を足さない

## 費用

### 描画の段（`frames` と `frames --tree`、交互に 4 巡、600 フレームの中央値）

| 場面 | 描画の段（中央値 / p95） | layout の pass |
| --- | --- | --- |
| 表示リストを直接書く | 29.7〜30.8 / 34.6〜37.2 µs | — |
| 木から作る | 30.2〜30.5 / 32.9〜37.2 µs | 190.8〜195.0 µs |

- 描画の段の範囲は重なった。木から作る段は、1,002 個のノードをたどり、それぞれの命令を書く。直接書く場面は、1,000 個の矩形の位置の計算と、1 行の文字の整形を毎フレーム行う。木の文字の葉は、文字が変わらない限り整形し直さない。そのため、この 2 つは同じ処理の比べではない。木をたどる分の費用は、文字の整形の分（画面 1 枚の 3,200 文字で約 250 µs なので、25 文字で約 2 µs と見積もる。`docs/benchmarks/t1b-wrapping.md`）と同じくらいと推定する。差が出なかったので、プロファイルは取っていない
- layout の pass は、1,000 個の絶対配置の箱の位置が毎フレーム変わる分である。描画の段とは別に測った

### UiNode の大きさ

| | `Unsafe.SizeOf<UiNode>` |
| --- | --- |
| main（c446dcc） | 536 バイト |
| V1b | 576 バイト |

- 増えた 40 バイトは、描画の状態の参照（8）、確定した枠線の幅（`Edges`、16）、確定した余白と枠線の幅（16）である。詰め物には入らなかった
- L1a の layout の場面（`layout`）を main と交互に 4 巡測った。どの指標も、このブランチの範囲が main の範囲より上には出なかった。たとえば次のとおりである
  - 1 か所の変更（S6b）: main 21.1〜21.2 µs、V1b 20.9〜21.0 µs
  - 幅の変更（wrap）: main 1,236.1〜1,360.9 µs、V1b 1,242.8〜1,300.9 µs
  - 最初の layout（absolute）: main 2,266.3〜2,466.1 µs、V1b 2,429.6〜2,529.3 µs
