# IM1 3c: GIF と WebP のアニメーション

行 IM1 の 3c（Issue #783、設計書 §5.0.4「アニメーション」「テクスチャ」）。次のフレームだけをワーカーでデコードし、フレームの時間のタイマーが鳴って画素も届いたら、UI のフレームで同じテクスチャへ書く。ここでは、本物の窓での再生の遅れと、UI スレッドが起きる回数、同じテクスチャへ書く費用、実行ファイルの増分を測った。

## 再現

```powershell
./vendor/build.ps1
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe image-play <file> 10
<dir>/XylemUI.E2E.exe image-upload 20
dotnet publish samples/Counter -c Release -r win-x64 -o <dir> -p:IlcGenerateMapFile=true
```

NativeAOT、ハードウェアの GPU、60 Hz のモニタで測った。プロセスは固定していない（メッセージループとワーカーのスレッドを使う場面のため）。回の前の CPU の負荷は、1.3〜10.7 % だった。

測ったファイルは Pillow 12.1.0 で作った。512 × 512、24 フレーム、終わりなしで、グラデーションの上を円が動く絵である。

| ファイル | 形式 | フレームの時間 | 大きさ |
| --- | --- | --- | --- |
| `play-100.gif` | GIF | 100 ms | 566,428 バイト |
| `play-40.gif` | GIF | 40 ms | 566,428 バイト |
| `play-0.gif` | GIF | 0 ms | 566,236 バイト |
| `play-100.webp` | WebP（ロッシー、品質 80） | 100 ms | 63,666 バイト |
| `play-40.webp` | WebP（ロッシー、品質 80） | 40 ms | 63,666 バイト |
| `play-40-lossless.webp` | WebP（ロスレス） | 40 ms | 179,208 バイト |

## 再生の遅れと、UI スレッドが起きる回数

`image-play <file> 10`: 窓を開き、画像の要素 1 つでファイルを 10 秒再生する。メッセージループの反復のたびに、キャッシュがアニメーションを進めた回数を読み、進んでいればその時刻を取る。

- **遅れ**は、あるフレームを出した反復から次のフレームを出した反復までの時間から、ファイルが決めたフレームの時間を引いたものである。フレームの時間は、測った後に、同じファイルを別のデコーダで同じ順に読んで得た
- **反復**は、メッセージループが起きた回数である。アニメーションの最初の 1 フレームが進んだ時から数えた
- UI スレッドのアロケーションも、同じ時から `GC.GetAllocatedBytesForCurrentThread` で数えた

値は 3 回の流しの範囲。

| ファイル | 進んだ回数 | 遅れ p50 | 遅れ p95 | 遅れ 最大 | 反復 / 秒 | 反復 / 進み | UI スレッドのアロケーション |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `play-100.gif` | 91 | 8.8〜9.4 ms | 10.4〜11.0 ms | 11.1〜12.2 ms | 28.1〜28.5 | 3.08〜3.10 | 0 バイト |
| `play-100.webp` | 91 | 9.0〜9.1 ms | 10.6〜10.8 ms | 11.3〜12.4 ms | 28.2 | 3.08 | 0 バイト |
| `play-40.gif` | 213 | 6.7〜6.9 ms | 7.9〜8.0 ms | 8.2〜9.2 ms | 64.8〜65.0 | 3.03〜3.04 | 0 バイト |
| `play-40.webp` | 213 | 6.7〜6.8 ms | 7.7〜7.9 ms | 8.8〜9.4 ms | 65.0〜65.2 | 3.04〜3.05 | 0 バイト |
| `play-40-lossless.webp` | 213 | 6.6〜6.9 ms | 7.8〜7.9 ms | 8.3〜8.9 ms | 64.9〜65.3 | 3.03〜3.05 | 0 バイト |
| `play-0.gif` | 596〜597 | 16.7 ms | 16.8 ms | 48.3〜48.7 ms | 179.4〜179.7 | 3.01 | 0 バイト |

- フレームの時間が 100 ms と 40 ms のファイルでは、遅れは最大でも 12.4 ms で、UI の 1 フレーム（16.7 ms）を超えなかった。フレームは、タイマーが鳴って画素も届いた後の、最初の UI のフレームで出る。遅れは、その UI のフレームまでの待ちである
- 遅れは取り戻さない（設計のとおり、フレームの時間は出したフレームの時刻から数え直す）。100 ms のファイルは 10 秒で 91 回進み、1 回あたり約 109 ms である
- メッセージループは、アニメーションの 1 フレームにつき 3 回起きる。コードの上では、ワーカーがデコードの結果を `Post` する 1 回、タイマーが `Post` する 1 回、UI のフレームの 1 回で、測った 3.0〜3.1 回と合う。100 ms のファイルでは 1 秒に 28 回で、画像が出ている間に毎フレーム起きる形（60 回）の半分以下である
- フレームの時間が 0 の `play-0.gif` は、画面の更新ごとに 1 フレーム進む（設計のとおり、1 回の UI のフレームで進めるのは 1 フレームまで）。遅れの p50 と p95 は、画面の更新の間隔（16.7 ms）である

### 0 ms の GIF の出し始め

`play-0.gif` の遅れの最大（48.3〜48.7 ms）は、3 回の流しとも、出し始めから 3 つ目のフレームだった。出し始めの遅れを 2 回の流しで読むと、18.0・33.3・48.4 ms と 18.1・32.9・50.0 ms で、4 つ目からは 15.5〜16.7 ms になる。画面の更新の 1・2・3 回分である。

- 100 ms と 40 ms のファイルの出し始めには無い（`play-40.gif` の初めの 6 フレームは 4.7〜8.1 ms）
- フレームのスケジューラが、スワップチェーンの待機オブジェクトを 50 ms 待って打ち切った回数は 0、遅い開始の回数も 0 だった
- 1 フレームのデコードと合成は、GIF で p50 0.26 ms（最大 0.39 ms）、ロッシーの WebP で 0.51 ms（最大 2.47 ms）、ロスレスの WebP で 0.70 ms（最大 2.52 ms）で、画面の更新の間隔より短い（測った後に、UI スレッドで同じファイルを読んで測った）
- 画像を使わない `frames 300 --tree` では、2 回の流しのフレームの間隔の最大は 33.1 ms と 17.3 ms だった

出し始めの 3 フレームの遅れが、UI の 1 フレームを超えている。上の 3 つで、スケジューラの打ち切りとデコードの時間は原因でないと分かった。それ以上は絞れていない。扱いは PR に書く。

## 同じテクスチャへ書く費用

`image-upload 20`: 一辺 64〜4,096 画素の画像を、新しいテクスチャへアップロードするフレームと、同じ画像に画素を書き換えるフレーム（`TextureCache.Rewrite`。レンダラは同じテクスチャへ `UpdateSubresource` と `GenerateMips`）を測る。「GPU まで」は、描画の呼び出しの始まりから、画素を読み戻して GPU が終わるまでの時間である。値は 2 回の流しの p50 の範囲。

| 一辺 | 新しいテクスチャ（描画の呼び出し） | 新しいテクスチャ（GPU まで） | 書き換え（描画の呼び出し） | 書き換え（GPU まで） |
| --- | --- | --- | --- | --- |
| 64 | 0.010〜0.011 ms | 0.13 ms | 0.005 ms | 0.13 ms |
| 256 | 0.024〜0.025 ms | 0.16〜0.18 ms | 0.017 ms | 0.16〜0.18 ms |
| 1,024 | 0.13〜0.14 ms | 0.45〜0.47 ms | 0.12〜0.13 ms | 0.45〜0.47 ms |
| 2,048 | 0.68〜0.69 ms | 1.57〜1.59 ms | 0.65〜0.66 ms | 1.55〜1.57 ms |
| 4,096 | 3.93〜4.13 ms | 7.08〜7.33 ms | 3.81〜4.13 ms | 7.11〜7.39 ms |

書き換えの費用は、新しいテクスチャへのアップロードとほぼ同じで、画素の数に比例する。テクスチャの確保と解放が無くなる分、描画の呼び出しは 64〜256 画素で 0.005〜0.008 ms 短い。アニメーションの画像にも目標の大きさを当てる（設計書 §5.0.4「デコードの大きさ」）のは、この費用がフレームごとに掛かるためである。

## 実行ファイルの大きさ

NativeAOT で publish した実行ファイルを、3c の前（`main` に Issue #785 の修正を足した `53e72e6`）と後で比べた。`samples/Counter` は画像を出さない。「画像 1 つのアプリ」は、`XylemApp.Run(() => Elements.Image(ImageSource.FromFile(args[0])))` だけの、測るために作ったアプリである（`XylemUI.Desktop` を参照し、`XylemUI.Text.targets`・`XylemUI.Platform.Windows.targets`・`XylemUI.Imaging.targets` を取り込む）。

| アプリ | 前 | 後 | 増分 |
| --- | --- | --- | --- |
| `samples/Counter` | 5,051,904 バイト | 5,079,040 バイト | +27,136 バイト |
| 画像 1 つのアプリ | 4,961,792 バイト | 4,989,952 バイト | +28,160 バイト |

増分の内訳は、リンカのマップ（`/MAP`）で、オブジェクトファイルごとに番地の幅を足して比べた。

| 増えたもの | `samples/Counter` | 画像 1 つのアプリ |
| --- | --- | --- |
| マネージドのコードとデータ（ILC が作るオブジェクト） | +13,700 バイト | +14,144 バイト |
| libwebpdemux（`demux.c` と `anim_decode.c`） | +7,724 バイト | +7,724 バイト |
| shim（`xylemui_image.obj`） | +4,464 バイト | +4,464 バイト |

- 画像を出さない Counter にも、shim と libwebpdemux の分が入る。shim は 1 つのオブジェクトファイルなので、静止画の口と一緒にアニメーションの口もリンクされ、そこから `WebPAnimDecoder` が引かれる
- マネージドの増分を ILC のマップ（`IlcGenerateMapFile`）で型ごとに分けると、画像 1 つのアプリでは、`ImagePlayback` が 4,162 バイト、`ImageAnimation` が 2,369 バイト、`ImageBlock` が 2,349 バイト、`WindowImageCache` が 1,249 バイト、`TextureCache` が 530 バイト、`D3D11Renderer` が 402 バイト、`ImageDecodeQueue` が 329 バイトである。Counter には `ImageAnimation` が入らない（画像の要素を作らないので、デコードの道が残らない）
- 番地の幅の合計（Counter で 28,672 バイト、画像 1 つのアプリで 32,768 バイト）は、ファイルの増分より大きい。ファイルに置かれない `.bss` を含むためである
