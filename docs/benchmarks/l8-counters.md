# L8: L2 と L3 の遅れを命令の数で調べる

L2 と L3 の後、1 か所の変更が main より大きく測れた（L2 は最小値で 2〜4 %、原因未確定。L3 は CSS の既定で +1.4〜1.8 %）。機械のばらつきが大きく、時間ではコードによる差か判定できなかった（`docs/benchmarks/l2-layout.md`、`docs/benchmarks/l3-layout.md`）。行 L8（Issue #142）で、実行した命令の数を数えて判定した。

## 結論

- **L2 の差はコードによる。** 1 回の変更で命令が 3.1〜4.6 % 増えた（約 1 万〜2.7 万命令）。増えたのは、L2 の機能（表示しないノード、insets、aspect-ratio、計測のキャッシュに移した `Box`）を項目ごと・ノードごとに読む分だった。そのうち、aspect-ratio を後の手順で項目ごとに arena から引き直していた分は避けられたので直した（CSS の既定と `%` ありで −0.9〜1.0 %）。残りは、L2 の機能が読む値として受け入れる。固定サイズの行の中の変更でも、命令は +2.9〜3.4 % 増えた
- **L3 では、命令の数はほとんど変わらないが、サイクル数は増えた。原因は見つかっていない。** 命令の数は、1 か所の変更で ±0.2 %、固定サイズの行の中の変更で +0.2〜0.9 % だった。測るプロセスを性能コアの 1 つに固定すると、サイクル数は CSS の既定と `%` ありで +1.3〜1.8 % 増えていて、命令では説明できない。命令キャッシュの待ち、分岐の予測外れ、メモリを待ったスロットは増えていなかったので、原因はこの 3 つではない（PR #151 のレビュー）。続きはロードマップの行 L10 で調べる

## 測り方

- 命令の数（`INST_RETIRED.ANY`）とサイクル数（`CPU_CLK_UNHALTED.THREAD`）: Intel VTune 2026.4 のハードウェアのイベントを、10 万 3 イベントごとに標本にする（`benchmarks/counters/instructions.ps1`）。この機械のシェルは Medium の整合性レベルで、VTune はハードウェアのイベントを使えない（「Run the product as administrator」）。オーナーの UAC の承認で、管理者の PowerShell から 1 回ずつ走らせた
- 起動と木を作る費用を消すため、`XylemUI.E2E.exe layout-loop <場面> <種類> <回数>` を 2 万回と 12 万回で走らせ、イベントの数の差を 10 万で割って 1 回の変更あたりにする。種類は `change`（1 か所の変更）と `fixed_row`（同じ変更を、行が固定サイズの木で）
- 順番は 1 組を A・B・B・A にして 2 組。結果は `benchmarks/counters/summarize.py` で読む
- 権限の要らない目安として、プロセスのサイクル数（`QueryProcessCycleTime`）も同じやり方で測った（`benchmarks/counters/cycles.ps1`、6 組）
- 測るプロセスは、高い優先度で論理プロセッサ 2 に固定する（どちらのスクリプトも `-Processor`）。この機械の CPU（Core i5-13400F）は性能コアと効率コアを持ち、固定しないとプロセスが両方に移る。固定する前のサイクル数は ±5 % ほど動き、判定に使えなかった。固定すると、4 回の範囲は多くの場面で ±3 % ほどになった。命令の数は、固定してもしなくても 0.2 % の中で同じだった

```powershell
# 管理者の PowerShell で
./benchmarks/counters/instructions.ps1 -Builds <dir> -Pairs '7e1a2fd:558a95e','350b555:426dd07' -Out <out>
python -I benchmarks/counters/summarize.py instructions <out>
# 権限なしで
./benchmarks/counters/cycles.ps1 -Builds <dir> -Pairs '7e1a2fd:558a95e','350b555:426dd07' -Out <file>
python -I benchmarks/counters/summarize.py cycles <file>
```

`<dir>/<名前>/XylemUI.E2E.exe` は、そのコミットの `dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64`（NativeAOT）。

| CSS の既定 | `QueryProcessCycleTime`、12 回 | 81,592（81,089〜84,165） | 82,942（81,502〜84,866） | +1.65 % |

固定サイズの行の中の変更（1 回が 13,000〜52,000 サイクル）では、`QueryProcessCycleTime` の 12 回で L3 の前と L3 の差が +0.5〜1.6 %、VTune の 4 回で +2.3〜4.3 % だった。どちらも 4 回や 12 回の範囲が中央値の差より広く重なり（たとえば CSS の既定の L3 は 48,181〜55,044）、2 つの測り方で大きさもそろわないので、判定できない。L2 の前と L2 も同じで、`QueryProcessCycleTime` で +0.3〜1.7 %、VTune で −3.3〜+1.4 % だった。

CSS の既定と `%` ありでは、2 つの測り方がどちらも +1.3〜1.8 % を示し、中央値の差は 4 回の範囲の幅と同じくらいある。同じ VTune の回で、待ちの原因になるイベントを 1 回の変更あたりで数えた:

| イベント | CSS の既定: L3 の前 → L3 | `%` あり: L3 の前 → L3 |
| --- | --- | --- |
| `INST_RETIRED.ANY`（命令） | 644,590 → 645,359（+0.12 %） | 617,632 → 616,991（−0.10 %） |
| `ICACHE_DATA.STALLS`（命令キャッシュのミスで止まったサイクル） | 2,183 → 1,972（−9.7 %） | 2,062 → 2,049（−0.6 %） |
| `BR_MISP_RETIRED.ALL_BRANCHES`（分岐の予測外れ） | 194 → 191（−1.3 %） | 183 → 184（+0.3 %） |
| `TOPDOWN.MEMORY_BOUND_SLOTS`（メモリを待ったスロット） | 51,860 → 51,098（−1.5 %） | 31,998 → 32,125（+0.4 %） |

増えたサイクル（約 2,400〜3,300）は、どのイベントの増え方でも説明できない。残る候補は、命令の取り出しと解読（uop キャッシュに入らない、コードの配置が変わった）と、命令どうしの依存で実行が待つことだが、どちらも数えていない（行 L10）。`TOPDOWN.SLOTS` も頼んだが、VTune の報告に列が無かった。CSS の既定と `%` ありの 1 か所の変更は約 37〜40 µs（`docs/benchmarks/l3-layout.md`）で、1.5 % は約 0.6 µs にあたる。

## L2 で増えた命令の内訳（S6b の意味、VTune の関数ごとの命令の数）

| 関数 | 1 回あたりの増え方 | L2 が足したもの |
| --- | --- | --- |
| `GenerateFlexItems` | +4,765 | 項目ごとに、`Box` を計測のキャッシュから読む（`UiNode` を小さくするため L2 で移した）、`HasInset` を写す、伸ばす項目の最大値で `AspectRatio` を読む |
| `LayoutChild` と `ComputeFlex` | +1,798 と +1,197 | ノードごとに、`Hidden` の確かめ、流れの外の子の数（arena を 2 回引く）、測るときの親の有無の確かめ |
| `DetermineFlexBaseSizes` | +1,045 | 項目ごとに、aspect-ratio を読むため arena からノードを引き直す（同じことを別の手順でもう 1 回） |
| ほかの関数 | 合わせて約 +1,200 | インライン展開の場所が移ったもの（`Place` −2,912 と `IsLayoutBoundaryForInvalidation` +2,821、`LayoutCacheKey.Matches` −1,032 と `MeasureCache.TryGet` +914）と、小さな増減の和 |

上の 4 つの関数で +8,805、ほかで約 +1,200、合わせて S6b の意味の増え方（+10,026）になる。S6b の意味では、項目 1 つあたり十数命令で、1 回の変更で約 400 回（行の 100 項目と列の 100 項目を、測る実行と layout の実行で作る）なので、勘定が合う。CSS の既定（+27,485）と `%` あり（+27,108）は、同じ 400 回で割ると項目 1 つあたり約 70 命令になる。この 2 つの場面は関数ごとに数えていないので、内訳と勘定は S6b の意味に限る。

## 直したこと: aspect-ratio を項目に写す

aspect-ratio を、項目を作るとき（`GenerateFlexItems`、スタイルを読んでいるところ）に `FlexItem.AspectRatio` に写し、後の 2 つの手順は項目から読む。L3 の 426dd07 と比べた命令の数（4 回の中央値）:

| 場面 | 426dd07 | 直し | 差 |
| --- | --- | --- | --- |
| S6b の意味 | 337,131 | 336,830 | −0.09 % |
| CSS の既定 | 645,674 | 639,956 | −0.89 % |
| `%` あり | 618,293 | 611,949 | −1.03 % |

S6b の意味でほとんど減らないのは、この場面の変更では、多くの項目が基準の大きさを引き継ぎ（`FlexBaseMemo`）から取り、aspect-ratio を読む手順を通らないためと考えられる（確かめていない）。サイクル数の差は ±1.5 % の中で、判定できなかった。
