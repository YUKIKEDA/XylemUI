# KM2b: 部品のキーの載せ直し

文字の欄・メニュー・Select・メニューバー・選択の領域がキーのハンドラで受けていたキーを、部品の文脈の行と動作にした（ロードマップの行 KM2b、Issue #816、設計書 §7「既定のキーと動作」）。メニューとメニューバーの項目が動作を指す形は、次の行 KM2c である。

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe input'    # キーの配送、Tab、スクロールのキー、文字の欄
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe keymap'   # 既定の行を作る時間と、キーマップの 3 つの場面
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe menu'     # menu、select、menubar も同じ形
```

どれもウィンドウを開かない。`input` に、文字の欄を作る費用（`text_field_create_us_p50`、`text_field_create_bytes_p50`）を足した。1 行の欄 100 個をスコープの中で作り、1 個あたりの時間と割り当てを出す（21 標本の中央値。フレームは走らせない）。

## 正しさ

- **今あるテスト:** `XylemUI.Primitives.Tests` の 48 件と、`XylemUI.Desktop.Tests` の文字の欄・メニュー・Select・メニューバー・選択の領域・コンテキストメニュー・IME のテストは、テストを変えずに通る。
- **部品の動作（`PartActionsTests`、12 件。`XylemUI.Desktop.Tests`）:**
  - アプリは、欄の文脈 `TextField` の行で、欄の動作を別のキーに割り当て、名前（`text::MoveToStart`）から作り、欄のキーを外せる
  - 動作にキーが 2 つある場合、出すキーは Windows のメニューのもの（`Ctrl+X`・`Ctrl+C`・`Ctrl+V`・`Ctrl+Y`）
  - アプリが欄に文脈 `Search` を付けても、欄のキーは効く。条件 `Search` と `TextField && Search` の行が合う。アプリの文脈を外しても、欄のキーは効く
  - メニューが使わない矢印は、下のページをスクロールしない（横にスクロールするページの中のメニューで、右と左を押す。メニューが閉じている時は、右でページが 50 動く）
  - IME の変換中、Enter は 1 行の欄を送信せず、Esc は変換を壊さない。確定の後の Enter は送信する
  - 欄のキーの表の全部の行（文字・単語・行・文書の移動と選択、上下とページ、削除、元に戻すとやり直し、改行、切り取り・コピー・貼り付けの 2 つずつのキー）を押し、選択と文字列を確かめる
  - 欄ができない動作は、キーを通さずに配っても受けない（1 行の欄の上下と改行、読み取り専用の欄の編集、`OnSubmit` の無い欄の送信）。出すキーは欄の種類に合う（1 行の欄は送信に `Enter`、複数行の欄は改行に `Enter`）
  - 欄は、自分にフォーカスがある時だけ動作を受ける。欄のコンテキストメニューの中からの Ctrl+A と Backspace は何もしない。メニューの無い欄の Shift+F10 は受けられない
  - メニューの Space は項目を選ぶ。項目の横に開いたサブメニューは、下の矢印で閉じる。パネルの中の、項目でないノードの上の Enter は受けられない
  - 項目が 3 つのメニューバーは、左と右でそれぞれの向きに動く。開いたメニューの中の、メニューが受けなかった Enter と、バーの別の項目のアクセスキーは、バーを動かさない
  - Select は、自分の状態に合わない動作を、キーを通さずに配っても受けない（閉じた箱への `select::PageDown`、一覧が開いている間の箱への `select::Next`）。一覧の Space は行を選ぶ
  - メニューの無い選択の領域の Shift+F10 は受けられない
- **Core（`DefaultKeysTests` に 4 件。`XylemUI.Testing.Tests`）:**
  - キーマップは、UI スレッドの外で作っても既定の行を持つ。そこで行を足すと例外
  - 既定の行が 1 つも登録されていなければ、起動の検査が `Keymap.RegisterDefaults` を名指しする例外を投げる
  - 部品の文脈とアプリの文脈は 1 つの文脈として見え、同じキーの値はアプリのものになる。片方を外しても、もう片方は残る
  - 部品が基底の型に付けたハンドラは、派生の型の動作を受け、「実行できる」と答える。1 つの型に付けたハンドラは、その型だけを受ける

- **ミューテーション:** 文脈の合わせ方、キーマップのスレッドと起動の検査、欄・選択の領域・メニュー・Select・メニューバーの動作と行、基底の型のハンドラに 83 個の変異を入れ、作業用の worktree で、関わるテストのプロジェクトを流した。1 回目は 69 個を検出し、13 個が生き残り、1 個は変異がビルドできなかった（書き直して検出）。生き残りへの対応は次のとおりで、直した後は 82 個を検出する。
  - Ctrl+右を 1 文字の移動にする: テストが、1 文字先と単語の終わりが同じになる位置から押していた。単語の頭から押す確かめを足した
  - メニューが使わない矢印を先へ進める: テストが、右と左を続けて押した後のページの位置だけを見ていた（右で動き、左で戻る）。1 つ押すたびに見る形に直した
  - メニューの Space の行を消す、一覧の Space の行を消す、メニューバーの左を右にする（今あるテストは、有効な項目が 2 つで、左と右が同じ結果になる）、移動でサブメニューを閉じない: 今までもテストが無かった動きだった。テストを足した
  - 項目でないノードの上の Enter を受ける、メニューの中からの Enter でバーの項目を開く、メニューの中からのアクセスキーでバーが動く: メニューの中に項目でないノードを置いたテストを足した
  - Select の箱が、一覧が開いている間も受ける、箱が一覧の動作を受ける: 動作を直に配るテストを足した
  - メニューの無い選択の領域でメニューを開く: テストを足した
  - 文脈を合わせる所の、重複した値を省く条件: あっても無くても同じ動きだった。条件を消した
  - **残した 1 個:** メニューバーの項目は、メニューの中からの矢印を「自分のメニューが開いている」時だけ受ける。この条件を外しても、どのテストも落ちない。メニューの中から動作が届くのは、メニューが開いている時だけだからである。元のキーのハンドラが見ていた条件なので、そのまま残した

## 計測

NativeAOT の Release（`win-x64`）。基準は main（`b223d46`、KM2a）に、欄を作る費用の計測だけを足したもの。KM2b は `fcc7ec6`。論理プロセッサ 2 に固定し、優先度を High にして、同じ回の中で交互に流した（`input` は KM2b、基準、基準、KM2b を 4 巡で各 8 回。ほかは各 4 回）。µs。値は各回の中央値の、中央値と範囲。計測の間の CPU の負荷は 3〜12 % だった。

| キー（A）、深さ 50 | 1.792 [1.735..1.828] | 1.880 [1.831..2.329] |
| ボタンの Enter と Space のクリック | 0.1736 [0.1688..0.1882] | 0.3185 [0.2946..0.3362] |
| スクロールのキー | 0.2246 [0.2228..0.2464] | 0.3419 [0.3153..0.3483] |
| Tab（10,101 ノード） | 151.8 [151.2..159.1] | 153.8 [149.8..163.4] |
| 文字の欄の 1 文字の入力のうち、入力の処理 | 0.6 [0.6..0.7] | 0.6 [0.6..0.7] |
| 文字の欄の単語の移動のうち、入力の処理 | 19.5 [19.2..21.5] | 19.65 [19.3..21.7] |

| 文字の欄を 1 個作る割り当て（バイト） | 5,336 | 5,872 |

- **どのキーも、約 0.07 µs 長くなった。** 既定の行が 39 から 87 に増え（Core の 11 行と Primitives の 76 行）、押下のたびに端から見る（増えた 48 行で 0.071 µs、1 行あたり約 1.5 ns）。深さ 50 のキーの差（0.09 µs）も同じである。
- **ボタンの Enter と Space は約 0.145 µs、スクロールのキーは約 0.117 µs 長くなった。** Enter・Space・矢印は、部品の行（欄、メニュー、Select、一覧、メニューバー）が同じキーを持つ。キーが合った行ごとに、根までの文脈に条件を当てる。どの条件も成り立たず、ボタンのキーのハンドラか Core の行へ進む。
- **Tab は範囲が重なる。**
- **文字の欄の入力と単語の移動は変わらない。** 単語の移動は、キーのハンドラから、行と動作のハンドラに替わった。
- **欄 1 個は、536 バイトと約 0.3 µs 増えた**（時間は範囲が少し重なる）。部品の文脈と、動作のハンドラ 2 つ（欄の動作の全部を受ける 1 つと、コンテキストメニューを開く 1 つ）の分である。
- 行を最初のキーで引く索引は、入れていない。キーは 1 秒に多くて数十回で、0.07〜0.15 µs は、フレームの予算（§11.3）にも入力の遅延にも現れない。行が増える場合（アプリと利用者のキーマップ）の費用は、行 KM1b の 200 行の場面にある。

### 最初の版: 動作ごとにハンドラを付けた形（採らなかった）

最初は、欄が、動作の型ごとに `OnAction<T>` でハンドラを付けた（36 個と、コンテキストメニューの 1 個）。同じ形で測った結果（基準は上と同じ）:

| | 基準（KM2a） | 動作ごとのハンドラ |
| --- | --- | --- |
| 文字の欄を 1 個作る | 3.210 [2.974..3.364] | 6.572 [5.962..7.336] |
| 文字の欄を 1 個作る割り当て（バイト） | 5,336 | 19,872 |
| メニューバーのメニューを開くフレーム | 95.5 [95.2..102.9] | 106.7 [99.5..108.9] |
| メニューバーのメニューを切り替えるフレーム | 98.55 [96.1..103.4] | 112.15 [105.9..112.6] |
| メニューバーの切り替えの割り当て（バイト/フレーム） | 37,928 | 42,416 |

- ハンドラ 1 つは、エントリ、デリゲート、スコープの後始末のクロージャを確保し、ノードのハンドラの配列を 1 つ長いものに取り替える。欄 1 個で 14.5 KB、メニューの項目ごとに 2 つとパネルに 6 つで、開くフレームが約 11 µs 延びた。
- そこで、部品の動作に基底の型を持たせ（`TextAction`・`MenuAction`・`SelectAction`・`MenuBarAction`）、部品が基底の型に 1 つのハンドラを付ける形にした（`OnActionsOf<T>`、Core の内部の入口。配送は、型が同じか、ハンドラが派生も受けると言っていて派生なら呼ぶ）。メニューの項目は、サブメニューを持つものだけがハンドラを持つ（項目の Enter と Space は、パネルが、アクセスキーの登録から項目を引いて行う）。
- 公開の `OnAction<T>` は、今までどおり、その型だけを受ける（GPUI と同じ）。

## 覚えておくこと

- **表から変えた所**は、設計書 §7「表から変えた所（行 KM2b）」にある（`select::Toggle`、`select::CloseAndFocusNext`・`CloseAndFocusPrevious`、`menubar::Open` の `Last`、アプリケーションキー、選択の領域）。
