# KM1b: キーマップ

キーの並びの文字列、文脈と条件、キーマップ、続けて押す形、キーの配送の中の順、引数のある動作を名前から作るコードの生成を入れた（ロードマップの行 KM1b、Issue #809、設計書 §7「ショートカットと動作」）。既定のキーの載せ直しとメニューは、次の行 KM2 で行う。

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe keymap    # キーマップの 3 つの場面（ウィンドウを開かない）
<dir>/XylemUI.E2E.exe input     # 変更していないキーの配送（us_per_key_depth_*）
```

`keymap` は、`input` の `us_per_key_depth_50` と同じ鎖（入れ子の 50 個の箱。どれも capture と bubble にキーのハンドラを持ち、葉にフォーカス）を使う。根は文脈 `Workspace`、葉は `Editor mode = full`、途中の 5 個の箱は `Pane` と名乗る。場面は 3 つ。

- **行なし:** キーマップが空。キーは 100 個のキーのハンドラに届く。
- **200 行に合わない:** ほかのキーの行が 200（半分は条件 `Pane > Editor && mode == full` 付き、174 行は 2 つのキーの並び）。押したキーはどの行にも合わず、100 個のキーのハンドラに届く。
- **合う行がある:** 上の 200 行に、押すキー（Ctrl+S）の行を 1 つ足す。条件は `Workspace > Editor` で、動作は根が受ける。キーのハンドラには届かない。

## 正しさ

- **キーの並びの文字列（`KeystrokeTests`、6 件）:** 名前のキーと修飾キー（大文字と小文字、修飾キーの順によらない）、`secondary`、記号は文字の段になり Shift を持たない、誤った文字列は断る、キーの段は論理キーと修飾キーで、文字の段は文字と Shift を除いた修飾キーで合う、書き戻しと表示（Windows は Ctrl、Alt、Shift、Win の順で `+` 区切り）。
- **文脈と条件（`KeyContextTests`、5 件）:** 文脈の名前と値（値を持つキーは名前でもある）、誤った文字列は例外。条件の評価は、GPUI 自身のテスト（zed v1.25.3 の `crates/gpui/src/keymap/context.rs` の `test_child_operator` と `test_not_operator`）の 34 行を、同じ条件と同じ文脈の並びで期待値にした。演算子の結合の順（`>` が最も弱く、`||`、`&&`、比較、`!` の順）、無いキーの比較、条件の深さ。
- **キーマップ（`KeymapTests`、10 件）:**
  - 行のあるキーは、キーのハンドラより先に動作を頼む。動作を受けるハンドラが無ければ、キーはキーのハンドラへ進む
  - 深い条件の行が勝ち、同じ深さでは後から足した行が勝ち、条件の無い行は最も深いものとして数える。どこにも当てはまらない条件の行は合わない
  - 勝った行の動作が受けられなければ次の行を試す。動作の無い行はそこで終わる。外した行は試さない
  - 続けて押すキーは、最後のキーで動作を頼む。途中のキーはどのハンドラにも届かず、修飾キーだけの押下は並びを切らない
  - 次のキーが並びに合わなければ、溜めたキーをキーのハンドラと文字の入力へ流し、次のキーを最初から引く
  - 1 秒たつと、溜めたキーのうち行になっている最も長い並びが動作を頼み、どの行でもないキーはキーのハンドラへ届く（999 ms では何も起きない）
  - キーマップは Tab の既定の動きより先に試す
  - 動作の行（メニューが出す行）は、ちょうどその型の、最後に足した行。読んだ Effect は、行の追加と削除で再実行される
  - 書き方の誤った行は例外で、足されない
  - 行に合うキーから動作のハンドラまでの割り当ては 0（50 行のほかのキー、条件付きの行、2 つのキーの並び。1,000 回）
- **文字の欄と IME（`KeymapTextFieldTests`、3 件。`XylemUI.Desktop.Tests`）:**
  - 文字を受ける欄にフォーカスがあると、文字になるキー（J、スペース）はキーマップで引かれず、Ctrl の付いたキーは引かれる。フォーカスが箱にあるときと、読み取り専用の欄では、文字になるキーも引かれる
  - IME の変換中は、Ctrl+S も Esc も引かれない。確定の後は引かれる
  - 途中まで合ったキーがある間は、欄にフォーカスがあっても、文字になるキーを引く（`ctrl-k s`）
- **引数のある動作（`ActionArgumentTests`、3 件。Generator の側は `ActionTableGeneratorTests` に 3 件）:**
  - 名前と引数から作った動作は、引数をプロパティの型で読んで持つ（int、long、double、float、bool、string、列挙。名前は大文字と小文字を区別しない。数は不変カルチャ）。引数の無いプロパティは既定の値のまま
  - 無い名前、無い引数、型に合わない値は断り、どれが誤りかを文で返す
  - 名前で足した行は、引数つきの動作を頼む。誤った名前と引数は、足すときに例外
  - record の init だけのプロパティは `with` で、クラスの set できるプロパティは代入で設定するコードが生成される。設定できて引数に書けない型のプロパティと、record でないクラスの init だけのプロパティは、警告 XYLEM006
- **ミューテーション:** 照合・順・文字列・条件に 28 個の変異を入れ、作業用の worktree で `XylemUI.Testing.Tests` と `KeymapTextFieldTests` を流した。28 個とも、どれかのテストが落ちた。1 回目は 1 個（溜めたキーを 2 秒待つ）が生き残った。テストが時計を進めた後に `PumpAndSettle` を呼んでいて、それが次のタイマーまで時計を進めていた。時計を進めた直後に確かめる形に直した。2 個は変異がビルドできなかったので、書き直して流した。

## 計測

NativeAOT の Release（`win-x64`）。KM1a（`9284e33`）と KM1b（`306e08a`）の実行ファイルを、同じ回の中で交互に流した。µs。値は各回の中央値（`input` は 21 標本、`keymap` は 21 標本 × 10,000 キー）。

### 変更していないキーの配送（`input`、キーマップは空）

2 つ目の回（順は KM1b、KM1a、KM1a、KM1b を 4 巡。各 8 回）:

| | 深さ 1 | 深さ 50 |
| --- | --- | --- |
| KM1a | 中央値 0.0589 [0.0536..0.0785] | 中央値 1.842 [1.762..2.822] |
| KM1b | 中央値 0.0610 [0.0556..0.0667] | 中央値 1.904 [1.728..2.420] |

1 つ目の回（順は KM1a、KM1b、`keymap` を 5 巡。各 5 回）:

| | 深さ 1 | 深さ 50 |
| --- | --- | --- |
| KM1a | 中央値 0.0632 [0.0589..0.0745] | 中央値 2.403 [1.836..2.951] |
| KM1b | 中央値 0.0609 [0.0564..0.0612] | 中央値 1.842 [1.781..1.906] |

- 深さ 1 のキーは、2 つ目の回の中央値で KM1b が 0.002 µs（2 ns）長い。キーの配送の入口に、キーマップを引くかの判定（押下か、修飾キーか、行があるか）と、その後の配送を別のメソッドにした呼び出しが 1 つ増えた。
- 深さ 50 のキーは、2 つの回で大小が入れ替わり、範囲が重なる。差は読めない。
- どちらの実行ファイルにも、ほかより 3〜5 割ほど長い回がある（2 つ目の回で 8 回のうち 1 回ずつ、1 つ目の回では KM1a に 3 回）。両方に出るので、この変更によるものではない。原因は調べていない。

### キーマップの 3 つの場面（`keymap`、KM1b、5 回）

| 場面 | 中央値 | 範囲 | 割り当て |
| --- | --- | --- | --- |
| 行なし（キーのハンドラ 100 回） | 1.903 | 1.846〜1.971 | 0 バイト |
| 200 行に合わない（キーのハンドラ 100 回） | 2.520 | 2.492〜2.571 | 0 バイト |
| 合う行がある（動作のハンドラ 1 回） | 1.481 | 1.464〜1.510 | 0 バイト |

- 200 行に合わないキーは、行なしより約 0.62 µs 長い。行を端から端まで見る（1 行あたり約 3 ns）のと、根から葉までの文脈を集める分である。GPUI も、キーごとに行を全部見る（zed v1.25.3 の `crates/gpui/src/keymap.rs` 165〜174 行目、`self.bindings().enumerate().rev()`）。キーは 1 秒に多くて数十回なので、フレームの予算（§11.3）には効かない。行を最初のキーで引く索引は、入れていない。
- 合う行があるキーは、50 個の箱のキーのハンドラを呼ばずに根の動作のハンドラで終わるので、行なしより短い。
- 実行ファイル（`XylemUI.E2E.exe`）は 7,527,936 バイトで、KM1a の 7,466,496 バイトより 61,440 バイト大きい。publish の警告は 0。

## 設計から変えた所

設計は「文字を受ける欄では、文字になるキーを先に文字の入力へ送り、欄が受けなかったときだけキーマップを試す」としていた。キーが下りた時点では、後から来る文字を欄が受けるかは分からない。実装は、「文字を受ける欄（フォーカスしたノードが文字の入力の相手を持ち、読み取り専用でない）にフォーカスがあるとき、文字になるキーはキーマップで引かない」とした。設計書 §7「キーと文字の入力の順」を、この形に直した。
