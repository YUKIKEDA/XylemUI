# L1b のレイアウトの基準値

Flex の既定値以外の値と block の中の揃え（ロードマップの行 L1b、Issue #90、設計書 §3.2）を入れた後の費用を、L1a と同じ方法で測った。L1a の 3 つの場面に、wrap の場面を足した（設計書 §3.2 の「L1b の受け入れ」）。

## 測った物と機械

- コミット: このファイルを加えたコミット（`git log -1 -- docs/benchmarks/l1b-layout.md`）
- 機械と版と作り方: L1a と同じ（`docs/benchmarks/l1a-layout.md`）
- wrap の場面: 10 × 10 の箱 10,000 個を、2,000 × 2,000 の容器で折り返す。XylemUI と Taffy は `flex-wrap: wrap` と `align-content: flex-start` の行 1 つ（`align-content` の既定の `stretch` は、行の高さを容器の高さまで伸ばすので、Flutter と Avalonia に合わせて外した）。Flutter は `RenderWrap`、Avalonia は `WrapPanel`。測るのは L1a と同じ 3 つで、変える箱は 5,050 番目
- L1a の 3 つの場面は、L1a の実装が入った main（9c664c1）と、この行のコミットを交互に測って比べた

## 再現

```powershell
./benchmarks/compare/build.ps1 -Out <dir>
./benchmarks/compare/layout.ps1 -Built <dir> -Rounds 5
<dir>/xylemui/XylemUI.E2E.exe layout-loop wrap <change|width> 10000   # プロファイル用
```

## 結果: wrap の場面

`layout.ps1` で 4 つを 5 ラウンド交互に測った。表はラウンドの中央値、括弧は最小〜最大。

| 指標 | Flutter | Avalonia | Taffy 0.9.0 | XylemUI |
| --- | --- | --- | --- | --- |
| 最初の layout（µs） | 844（771〜1,457） | 6,124（5,922〜10,752） | 4,883（4,567〜9,324） | 3,650（3,094〜6,994） |
| 1 か所の変更（µs） | 867（644〜1,793） | 2,633（2,576〜3,456） | 2,920（2,814〜5,744） | 1,613（1,520〜4,363） |
| 幅の変更（µs） | 1,001（763〜2,230） | 1,436（1,359〜1,483） | 3,138（2,840〜5,453） | 1,661（1,575〜4,488） |

- **計算の回数**: 最初の layout で、ノードのアルゴリズムか計測関数が動いた回数は XylemUI で 40,001 回（葉 1 つにつき 4 回）。Taffy 0.9.0 の葉も 40,000 回で同じ
- **1 か所の変更が重い理由**: 容器が 1 つに 10,000 個の箱を持つので、箱 1 つの変更でも、容器は 10,000 個の項目を集めて行を切り直す。子はキャッシュに当たる（計算は 4 回）。Flutter の `RenderWrap` も全部の子を並べ直す

## 遅くなった分の内訳

1 か所の変更の 4 つの項目は、ばらつきを超えて 4〜8 % 遅い（0.7〜2.1 µs）。`layout-loop s6b change 300000` を両方のコミット（L1b は 481ae6b）でプロファイルした（NativeAOT、Visual Studio の収集と xperf）。サンプルの合計は 8,591,521 から 9,317,120 に 8.4 % 増え、増えた分の大きいものは次のとおり。

- `GenerateFlexItems`: 1,164,753 → 1,489,820（+28 %）。項目ごとに、`auto` のマージンの印 4 つ、`align-self`、stretch するかの印、stretch の最大、ベースラインと 2 つのずれの初期値を書く
- 最終配置: L1a では `ComputeFlex` の中にあった。`ComputeFlex` と `FinalLayoutPass` の合計で 751,191 → 959,178（+28 %）。項目ごとに、主軸と交差軸のずれを足し、逆向きの順と、ベースラインを読む項目かを見る
- `ResolveFlexibleLengths`: 654,585 → 754,216（+15 %）。gap を空きから引く
- `ContainerBaseline`: 24,796（新しい）。容器のベースラインを決める（直した後は、ベースラインを決める項目を選ぶだけの `BaselineItem`）

既定値の動きのとき（`flex-start`・stretch・gap 0・`auto` のマージン無し）は、主軸と交差軸の揃えの手順を飛ばす。残る増分は、項目の初期化と最終配置の、値を見て分かれる処理の分。

**試して戻したもの**（差がばらつきの中）: 項目と行の配列をスタックに置く、`GenerateFlexItems` の 3 つの印を局所変数に集めてループの後で書く、`GenerateFlexItems` と最終配置のループで使う `FlexConstants` の値を局所変数に移す。

## 受け入れ（設計書 §3.2、Issue #90）

- (1) wrap の場面で GPUI のレイアウト（Taffy 0.9.0）よりばらつきを超えて遅くない: 満たす（3 つとも速い）
- (2) 幅の変更が Layout の予算 2.0 ms の内側: wrap の場面はラウンドの最良値で 1,575 µs、中央値で 1,661 µs。L1a の 3 つの場面は、L1a と L1b の比較で中央値 952・1,488・1,982 µs
- (3) 定常状態のアロケーション 0: `SteadyState_RelayoutAfterOneChange_AllocatesNothing` に wrap の場面を足した
- (4) L1a の 3 つの場面が悪くならない: 最初の layout と幅の変更は範囲が重なる。1 か所の変更の 4 つの項目は 4〜8 % 遅い（上の内訳）。オーナーの判断で受け入れ、行 L4 で扱う（L4 は項目ごとの計算の回数と、子の変更で親の flex を解き直す費用を減らす行で、遅くなった手順を作り直す）
- Flutter との差（wrap の場面で、最初の layout が約 4 倍、1 か所の変更が約 2 倍、幅の変更が約 1.7 倍）は行 L4
