# IM1 3a: 窓の画像のキャッシュ

行 IM1 の 3a（Issue #769、設計書 §5.0.4「キャッシュ」「3a の実装」）。木が持つ窓ごとの画像のキャッシュ（`WindowImageCache`: 鍵、3 つの組、枚数とバイト数の上限）と、Core の `ImageCache`（`MaximumCount`・`MaximumBytes`・`Evict`・`Clear`）を入れ、`Elements.Image` がキャッシュを通して画像を出すようにした。Windows 11 26300、Intel Core i5-13400F、NVIDIA GeForce RTX 3060 Ti、NativeAOT の Release（win-x64）。main は `b827070`。

## 再現

```powershell
./vendor/build.ps1
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe image-scroll 600"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe image-tree 600"
<dir>/XylemUI.E2E.exe frames 600 --images
```

`image-scroll` と `image-tree` は、プロセスを論理プロセッサ 2 に固定し、優先度を High にして流した。`frames` は、1b-1 と 1b-2 の記録と同じく固定していない。時間は `Stopwatch` で測り、1 目盛りは 100 ns である。p50 は 0.1 µs の刻みで出る。

## 100 枚の画像のスクロール

`image-scroll 600`: 設計書 §11.3 の 100 枚の画像の場面を、`ImageCache` の既定の上限（1,000 枚、104,857,600 バイト）のまま流す。

- 10 × 10 の格子（高さ 320）を、幅 420・高さ 200 のスクロールする箱に入れた。画像の要素は 1 つずつ別の読み込み元を持ち、512 × 512 にデコードして 32 × 32 に描く。100 枚で 104,857,600 バイトになり、既定のバイト数の上限と同じである
- 比べる相手は、背景を塗った 32 × 32 の箱 100 個の同じ格子である
- デコードは代わりの関数（`ImageDecodeQueue.DecodeForTests`）である。レンダラの代わりは、描画のたびに、アップロードを待つ画像と `Release` された画像を取り出すだけで、描かない
- ホイールを下へ 50、上へ 50 と交互に送り、そのたびに、頼まれたフレームを 1 つ流す。10 回温めてから 600 回測った
- 格子は仮想化していないので、100 個の要素はスクロールの間ずっと木にある

値は 4 回の流しの p50 の範囲。

| | フレームの CPU（p50） | ホイールのアロケーション | フレームのアロケーション |
| --- | --- | --- | --- |
| 箱 100 個 | 4.4〜4.7 µs | 0 バイト | 0 バイト |
| 画像 100 個 | 7.4〜8.0 µs | 0 バイト | 0 バイト |

- 4 回とも、600 回のホイールのすべてでスクロールの位置が動き、600 個のフレームがすべて描かれた。どちらかが欠けると、場面は終了コード 1 で終わる
- アロケーションは、ホイールを渡す呼び出しとフレームの呼び出しの前後で `GC.GetTotalAllocatedBytes(precise: true)` を読んで数えた
- 測った後のキャッシュ（4 回とも同じ）: デコードを頼んだ回数 100、鍵が索引にあった回数 0、数える組 100 枚・104,857,600 バイト、上限が外した項目 0、数える組に入らなかった回数 0。窓の画像は 100 枚
- ゲートのテスト `WindowImageCacheTests.SteadyState_ScrollingAHundredImages_AllocatesNothing` も、同じ既定の上限で、100 枚の画像（16 × 16）のスクロールを 1,000 往復流し、アロケーションが 0 であることを確かめる

## 画像の要素 100 個のフレーム

`image-tree 600`（1b-2 の場面。`docs/benchmarks/im1-element.md`）を、main とこの PR で比べた。場面は、格子のノードを描き直させてフレームを流す。画像の要素を作り直さないので、測るフレームの中でキャッシュは呼ばれない。

| | 画像 100 個のフレームの CPU（p50）と、その値が出た回数 | 箱 100 個（p50） |
| --- | --- | --- |
| main（8 回） | 6.9 µs が 6 回、7.0 µs が 2 回 | 3.6〜3.7 µs |
| この PR（8 回） | 7.0 µs が 7 回、11.3 µs が 1 回 | 3.6〜3.7 µs（11.3 µs の回は 6.4 µs） |
| 写し（8 回） | 7.0 µs が 6 回、6.9 µs が 2 回 | 3.6〜3.7 µs |

- 3 つのビルドを順を混ぜて 24 回流した（`BCAACBCABBACABCCBABACCAB`。A が main、B がこの PR、C が写し）。写しは、この PR の `ImageBlock.cs` だけを main の形に戻したビルドで、要素はキャッシュを使わず、木はキャッシュを持つ
- この PR の 11.3 µs の回は、箱のフレームも 6.4 µs で、どちらの格子も長かった。比べる値には入れない
- 描き直させる印とフレームのアロケーションは、24 回とも、箱でも画像でも 0 バイト。窓の画像は 100 枚
- その前に、main とこの PR だけを交互に 12 回ずつ流した。main は 6.9 µs が 8 回、7.0 µs が 3 回、7.1 µs が 1 回、この PR は 7.0 µs が 9 回、7.1 µs が 2 回、7.4 µs が 1 回だった。2 つを合わせた 20 回で、この PR に 6.9 µs の回は無い
- 3 つのビルドの 24 回の流しは、上の表の前に 2 度流している。その 2 度は、同じ機械でほかのプロジェクトのテストが 2〜3 個のコアを使っていた間で、およそ半分の回で、箱か画像の値が約 1.5 倍（箱 5.7〜7.3 µs、画像 9.2〜10.8 µs）になった。比べる値には入れない

この PR は main より時計の 1 目盛り（0.1 µs、画像 1 個あたり 1 ns）長い回が多い。main の値も 6.9〜7.1 µs に広がる。写しも 7.0 µs が多いので、要素がキャッシュを使うことによる差ではない。

3 つの実行ファイルを `dumpbin /disasm:nobytes` で比べた。

- `WindowFrames.RunFrame` から、直接の `call` と `jmp` で 8 段までに届く関数は 1,560 個。そのうち 1,393 個は、3 つのビルドで、番地のほかは同じ命令である
- 166 個は、命令は同じで、メモリのオペランドだけが違う。この PR でも写しでも同じ結果である。違いは 405 か所で、397 か所は変位が 8 増えたもの（0x58〜0x188 が 0x60〜0x190 に。うち 253 か所は 0xD0 が 0xD8 に）、8 か所は `memcpy` と `memset` の中の飛び先の表の番地である。この PR の `UiTree` のコンストラクタは、新しい `WindowImageCache` を `[rbx+58h]` に入れる。`UiTree` は 0x58 にフィールドを 1 つ足し、その後ろのフィールドが 8 バイトずれた。166 個のうち 161 個は XylemUI の関数で、残りは `memcpy`・`memset` と、`SharedArrayPool<char>` の 3 つの関数（`Rent`・`Return`・`InitializeTlsBucketsAndTrimming`。変位が 8 増えたところが 1 か所ずつ）である。この 3 つは `UiTree` を触らない。この PR は、スレッドごとの静的フィールドも 1 つ足している（`ImageCache` の上限の組）
- 残る 1 個は `BCryptGenRandom` のラベルで、輸入のラベルの後ろに、名前の無いネイティブのコードと飛び先の表が続く。見た違いは、表の番地と、命令として読まれた表のデータだった
- 画像を描く `ImageBlock.Draw` は、デリゲートで呼ばれるので上の 1,560 個に入らない。3 つのビルドとも 173 命令で、main とこの PR の違いは 1 か所（`mov rbp,qword ptr [rcx+0D0h]` が `[rcx+0D8h]` に）、main と写しの違いは 7 か所で、どれも変位が 8 増えたものである。`ImageBlock.Draw` が呼ぶ `ImageFitting.Place`（338 命令）と `DisplayList.DrawImage`（239 命令）は、番地のほかは同じである
- 先頭の番地を 64 で割った余りは、1,560 個のうち、この PR で 1,303 個、写しで 917 個の関数で変わった（`ImageBlock.Draw` は main が 0、この PR が 32、写しが 16）

フレームの経路の命令は同じで、違うのは、フィールドを足したことによるフィールドの位置と、機械語の置き場所である。1 目盛りの差は、この違いによるものとみる（`.cursor/rules/bench.mdc`）。

## テスト

- `tests/XylemUI.Core.Tests` の `WindowImageCacheTests`（18 個。デコードを代わりの関数にし、ループの無い木で）: 同じ鍵の 2 つの要素が 1 回のデコードと 1 つの画像を分け合う（デコード中も）、鍵は読み込み元と幅と高さの 3 つ、上限を超えたら最近使っていないものから外れる、デコードのたびに数える組が 2 つの上限の中にある、外された画像は出ている間は生きていて鍵で引ける、最後の要素が外れたとき数える組の中なら残り外なら放す、バイト数の上限より大きい画像は出すが数えずほかも追い出さない、枚数の上限が 0 なら出ていない画像を残さない、失敗した項目は残らずデコードし直す、待つ要素のいないデコードは始まる前なら飛ばし走っていれば出ていない項目になる、キャッシュにある読み込み元は読み込み中の要素を挟まない、木を捨てるとすべて放し遅れた結果は足さない、定常状態のアロケーションが 0（キャッシュにある読み込み元の切り替え、上限が画像を外すとき、100 枚の画像のスクロール）
- `tests/XylemUI.Core.Tests` の `ImageCacheTests`（10 個）: 既定の上限、枚数とバイト数の上限を下げるとその場で開いている窓それぞれを外す、負の値は `ArgumentOutOfRangeException` で値を変えない、`Evict` はすべての大きさとすべての窓から外す、デコード中の `Evict`（待っている要素は結果を出し、索引には入らない。要素もいなくなれば画像を残さない）、`Evict(null)` は `ArgumentNullException`、`Clear` はすべての窓のすべての画像を外す、UI スレッドの外からは `InvalidOperationException`
- `tests/XylemUI.Desktop.Tests`: `ImagePixelTests.App_Disposed_ReleasesTheImagesOfItsCache`（ヘッドレスのアプリを捨てるとキャッシュの画像を放す）と、`ImageWindowTests.Close_ReleasesTheImagesOfTheCache`（窓を閉じると放す）
- テストが規則の誤りで落ちることを、製品のコードを 1 か所ずつ変えた 50 個の変種で確かめた。50 個とも、どれかのテストが落ちた。1 回目は 47 個のうち 3 個でテストが落ちなかった（デコード中に `Evict` した後に要素がいなくなったときの画像、鍵の等しさが幅を見ない、高さを見ない）ので、テストを 2 つ足した（`ImageCacheTests.Evict_WhileDecoding_ThenTheElementGoes_KeepsNoImage`、`WindowImageCacheTests.Key_Equals_ComparesTheSourceTheWidthAndTheHeight`）
