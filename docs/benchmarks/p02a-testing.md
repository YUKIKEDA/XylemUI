# P02a: XylemUI.Testing の操作の土台

`XylemUI.Testing` の操作の土台（ヘッドレスのアプリ、仮想の時計、入力の注入、木の検索、`PerformanceAssert`）を作った（ロードマップの行 P02a、Issue #460、設計書 §12 と §11.3）。フレームの経路で変えたのは、ノードを消すときにテスト ID の表を見る 1 か所だけである。その費用は、ブランチの基点（a0c4589）と比べた。もう 1 つ、リポジトリのテストを並行 GC のまま動かすようにしたので、`DoesNotAllocate` が区間をやり直した回数と、テストの時間を数えた。

どれも Windows 11 26300、Intel Core i5-13400F で測った。

## ノードを消す費用（`lists`）

NativeAOT の Release を論理 CPU 2（P コア）に固定し、優先度を高くした。`lists` は、`For` で 1 万行の列を作り、真ん中の行を消して戻す（`remove_middle`）。消すときに、行のノードの解放（`FreeSubtree`）がテスト ID の表を見る。`--test-ids` は、1 万の行のすべてにテスト ID を付ける（このブランチで足した変種）。基点と、このブランチの 2 つを、基点・このブランチ・テスト ID あり・テスト ID あり・このブランチ・基点の順で 3 巡流した。表の値は 6 回の中央値（p50）の最小〜最大と、6 回の中央値である。

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c "start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe lists > lists.json"
cmd /c "start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe lists --test-ids > lists-ids.json"
```

| 指標（µs） | 基点 | このブランチ | 1 万行にテスト ID |
| --- | --- | --- | --- |
| 真ん中の行を消す（`remove_middle_diff`） | 109.7〜124.0（114.5） | 102.9〜114.2（111.2） | 107.0〜117.0（113.6） |
| 行を足す（`append_diff`） | 116.9〜134.6（120.8） | 114.6〜131.8（120.6） | 114.2〜119.9（117.7） |
| 逆に並べる（`reverse_diff`） | 848.9〜917.4（883.3） | 841.7〜887.2（850.2） | 864.8〜913.3（882.6） |
| `Show` の切り替え | 1.6〜1.9（1.7） | 1.6〜2.0（1.65） | 1.7〜2.8（1.85） |

- **テスト ID の無い木:** 3 つの指標とも、基点とこのブランチの範囲が重なる。足したのは、ノードを 1 つ解放するたびの、表の件数を 0 と比べる 1 回である
- **1 万行にテスト ID:** 真ん中の行を消すと、表から 1 件消える。範囲は基点と重なり、差は測れなかった。表は付けたノードだけを持つので、付けないアプリの費用は増えない
- **割り当て:** 表から消すのは `Dictionary.Remove` で、割り当てない。フレームの経路の段（layout、描画の段）は変えていない

## 並行 GC のままのテスト

`tests/Directory.Build.props` の `ConcurrentGarbageCollection=false` を外し、利用者のテストのプロジェクトと同じ条件にした。`DoesNotAllocate` は、区間の中で背景の GC が終わった区間（`GC.GetGCMemoryInfo(GCKind.Background).Index` が動いた）と、第 2 世代の GC が始まった区間をやり直す。

- **番号だけで見たとき:** Core のテストを Release で 8 回流し、2 回で 1 つの区間が 5,376 バイトと 7,840 バイトを数えて失敗した（`ElementsTests.SteadyState_ClickThatChangesTheBackground_AllocatesNothing`）。ほかの 9 区間は 0 バイトで、その区間に GC は数えられていない。#332 の、背景の GC の mark の終わりで数えられるバイトと同じ形である。背景の GC が区間の前に始まって区間の中で mark を終え、番号は区間の後で動いたので、やり直さなかった
- **直した形:** 各区間の前にブロックする第 2 世代の GC を 1 回回し、走っている背景の GC を終わらせる。区間の中で始まった背景の GC は、始まりで第 2 世代の GC の数を 1 つ増やすので、それでやり直す
- **直した後:** Core を 10 回、Text・Desktop・Testing・Primitives を 3 回ずつ流し、失敗は 0 だった。本物の重なりでやり直した区間は延べ 67 だった（`XylemUI.Testing.Tests` が偽の数でわざと重ねた分を引いた）。3 回やり直しても重なった区間もあったが、どれも 0 バイトで通った。重なりはバイトを足すだけなので、0 バイトは本物の 0 である
- **後で落ちた回（P02b の 3 つ目の PR、#492）:** 手元のゲートを 3 回流し、2 回で、その PR が触っていない経路の割り当てのテストが 1 つずつ落ちた。`DirectWriteGlyphRasterizerTests.Rasterize_NewGlyphs_AllocatesNothing(Gray)`（Release）と `ReactiveDependencyTests.SteadyState_SetAndFlush_AllocateNothing`（Debug）である。どちらも、そのプロジェクトだけを流し直すと通った（前者は 3 回とも）。数えたバイトとやり直しの回数は残していない。やり直しの後も落ちたので、背景の GC の重なりとは別の理由である。次に落ちたら、失敗の文（区間ごとのバイト）をここに足す
- **回数の数え方:** 回数を確かめるテスト（クリックやフリングを数える 6 つ）は、やり直した区間の回数も数える。`DoesNotAllocate` は、回した回数（慣らし・測った回・やり直した回）を返し、テストはそれと比べる。前の `1_100` の決め打ちは、やり直しがあると 1,200 になって失敗した

## テストの時間

ローカルの Release で、テストのプロジェクトごとに 3 回流した（`dotnet test --no-build`、ビルドを除く）。Core と Text は、基点とこのブランチを交互に流した。

| プロジェクト | 基点 | このブランチ |
| --- | --- | --- |
| `XylemUI.Desktop.Tests` | 11〜13 秒 | 7〜11 秒 |
| `XylemUI.Core.Tests` | 6.3〜8.7 秒 | 6.8〜7.2 秒 |
| `XylemUI.Text.Tests` | 4.5〜5.5 秒 | 5.5〜6.2 秒 |
| `XylemUI.Testing.Tests` | なし | 2〜4 秒 |

- **Desktop:** Todo の 5 つのテスト（項目の切り替え・削除・絞り込み・並べ替え・割り当て）を、本物のウィンドウと WARP から `HeadlessApp` に移した。スクロールした行の画素を読むテストは、画素を読む行 P02a2 まで本物のウィンドウに残る。Q5 のハング（`D3D11Renderer.Dispose`、#415）は `TodoTests.RemoveButton_RemovesItsItem` のウィンドウを閉じる所で起きていたが、このテストはウィンドウを作らなくなった
- **Core:** 範囲が重なり、差は測れなかった
- **Text:** 3 回とも 0.3〜1.0 秒長い。区間の前のブロックする第 2 世代の GC の分である。それだけを外したビルドを 4 回流すと 4.5〜5.4 秒で基点と重なり、戻すと 5.3〜6.1 秒だった。Text の Zero-Alloc のテストは 14 か所で、1 つにつき 10〜40 区間、つまり 140〜560 回の GC になる。差の約 0.7 秒をこの回数で割ると、1 回あたり約 1〜5 ms になる。テストのプロセスのヒープが 2 万余りのテストのデータを持つためと見ているが、GC 1 回の時間は測っていない。GC を回さずに番号だけで見ると重なりを見逃した（上の「番号だけで見たとき」）ので、この時間を払う
