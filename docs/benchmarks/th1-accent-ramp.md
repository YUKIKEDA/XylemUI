# TH1: OS のアクセントの色からブランドの 16 段を作る規則

行 TH1 の手順の 1 の残り（Issue #899、設計書 §13.2「アクセントの色」）。Fluent のブランドの段（`BrandVariants` の 10〜160）を、OS のアクセントの色から作る規則を決めるために、次の 4 つを計算で確かめた。

- (a) 調べる時に使った Python の写しが、Fluent のテーマの設計の道具（theme designer）の TypeScript と同じ値を出すか
- (b) 決めた規則（キーは OS の `Accent` の 1 色、曲線は theme designer のもの、各段の明度は `brandWeb` のもの）で、測った青と、ほかのキーの 16 段
- (c) その 16 段で、Fluent の別名の色が組む文字と背景の対比
- (d) 色の無いキー（灰、黒、白）と、ハイコントラストで 7 色が 1 色になった時

**Windows の画面では何も測っていない。** OS の 7 色は `docs/benchmarks/th1-os-appearance.md`（Windows 11 26H2、アクセントは青）の値を使った。ほかのアクセントで OS が返す 6 段は読んでいない。

計算に使ったスクリプトはリポジトリに入れていない。下の「方法」の手順で作り直せる。

## 方法

- **元のコード:** microsoft/fluentui のコミット `1f59fc2121f828b57713915f6aa035b4e77c7d47`（設計書 §13.2「トークンの元」と同じコミット）の `packages/react-components/theme-designer/src/` から、`colors/csswg.ts`・`colors/geometry.ts`・`colors/hueMap.ts`・`colors/types.ts`・`colors/palettes.ts`・`utils/getBrandTokensFromPalette.ts` を `git show` で取り出した。これらのファイルは、`1f59fc2` と `f9720c35`（2026-11-12）の間で変わっていない（`git diff --stat` が空）
- **変えたところ:** import の道のりだけである。Node の ESM が拡張子を要るので、`'./csswg'` を `'./csswg.ts'` のように書き換えた（`palettes.ts` の 4 行）。`getBrandTokensFromPalette.ts` では、型だけの import `@fluentui/react-theme` を `Record<string, string>` の型に置き換え、`'../colors'`（`templates.ts` も読み込む `index.ts`）を `'../colors/palettes.ts'` にした。計算の行には触れていない
- **動かし方:** Node v22.11.0 の `--experimental-strip-types` で、型を外して TypeScript をそのまま動かした
- **規則の計算:** `curvePathFromPalette`・`getPointsOnCurvePath`・`Lab_to_LCH`・`LCH_to_Lab`・`snap_into_gamut`・`Lab_to_hex` は元の関数を呼んだ。各段の明度だけを `brandWeb` のものにするため、`palettes.ts` の 101〜117 行目の取り出しの繰り返しを、目標の配列だけ替えてスクリプトに写した（この関数は外に出ていない）
- **対比:** `csswg.ts` の `contrast`（506〜520 行目。WCAG 2.1 の式）で求めた
- **明度:** `csswg.ts` の `sRGB_to_LAB`（533〜541 行目）で求めた。sRGB（D65）を XYZ にし、Bradford の行列で D50 に移してから CIE Lab にする

## (a) Python の写しと TypeScript の突き合わせ

Issue #899 の Grill の前の調べ（`.dev/grill/TH1-accent-ramp.md`）は、theme designer の計算を Python に写して使った。同じ入力で `getBrandTokensFromPalette` をそのまま動かし、16 段の 16 進を比べた。

| `#0F6CBD` | `darkCp = lightCp = 0`（道具の画面の既定、Vibrancy 0） | 16 / 16 |
| `#0F6CBD` | 関数の既定（`darkCp = 2/3`、`lightCp = 1/3`） | 16 / 16 |

64 段がすべて一致したので、調べで出した数は theme designer の計算と同じである。

## (b) 規則と 16 段

### 各段の明度の目標

`brandWeb`（`packages/tokens/src/global/brandColors.ts` 3〜20 行目）の各段の 16 進を、上の `sRGB_to_LAB` で CIE Lab（D50）の L\* にした値である。

| 段 | L\* | 段 | L\* |
| ---: | ---: | ---: | ---: |
| 10 | 6.8804 | 90 | 54.0170 |
| 20 | 12.5995 | 100 | 62.8844 |
| 30 | 17.6508 | 110 | 67.6112 |
| 40 | 23.3234 | 120 | 72.0205 |
| 50 | 28.6248 | 130 | 77.9129 |
| 60 | 34.0902 | 140 | 84.0472 |
| 70 | 38.4971 | 150 | 89.5312 |
| 80 | 44.1490 | 160 | 95.4287 |

theme designer そのものは、この代わりに色相ごとの表（`colors/hueMap.ts` 36 行目の `hueToSnappingPointsMap`）から目標を作る。青では L\* 0.9〜86.0 になり、段 160 が `brandWeb` より暗い。

### 曲線

theme designer と同じである。

- **曲線の形:** Lab の中の 2 本の 2 次ベジェで、黒（L\* 0）からキー、キーから白（L\* 100）を結ぶ。制御点は、キーの a と b のまま、明度を L_key·(1 − darkCp) と L_key + (100 − L_key)·lightCp に置く（`palettes.ts` 176〜193 行目）
- **制御点の値:** `darkCp = 2/3`、`lightCp = 1/3`。`getBrandTokensFromPalette` の既定である（27 行目）
- **ねじれ:** 色相のねじれは 0 である
- **点の取り方:** 曲線ごとに 24 等分した 25 点を取る（`getPointsOnCurvePath`、`geometry.ts` 186〜205 行目。分ける数は `palettes.ts` 129 行目の `ceil(24 × (1 + |torsion || 1|) / 2)` で、ねじれが 0 の時は 24）。続けて同じ点は 1 つにする
- **段の色:** 段ごとに、その明度で折れ線の上を線形に補間する。補間する時は、点の L\* が目標を超えるまで進める
- **色域:** sRGB の外に出た色は、L と色相を保って C を二分探索で縮める（`snap_into_gamut`、`csswg.ts` 742〜774 行目）
- **16 進への丸め:** 各成分を `floor(x × 256)` にする。0 未満は 0、1 以上は 255 である（`sRGB_to_hex`、`palettes.ts` 135〜142 行目）

ねじれが 0 の時、色相を回す段（`palettes.ts` 163〜168 行目、Lab → LCH → Lab の往復）は、あってもなくても結果が同じだった。比べたのは、下の 9 つのキーと、sRGB の各成分を 0 から 255 まで 17 刻みにした 4,096 色の、計 4,105 個のキーの 65,680 段で、すべて同じ 16 進になった。

### 色の無いキー（灰、黒、白）

- 灰・黒・白は、3 つとも同じ灰色の 16 段になった
- C\* が 0 のキー（白は Bradford の行列の誤差で 0.02）では、制御点とキーの a と b がほぼ 0 なので、曲線は L\* の軸の上を通る。各段は、その明度の灰になる
- 黒のキーでは、黒からキーまでの曲線が 1 点に縮み、続けて同じ点を 1 つにする処理でその点が消える。残るのはキーから白までの曲線で、段はそこから取る
- 白のキーでは、キーから白までの曲線が使われない。目標の明度はどれも 6.88〜95.43 で、黒からキーまでの曲線の中にある
- どの場合も 0 で割る所は無く、上の 4,105 個のキーで、16 進にならない段は 0 だった

## (c) 文字と背景の対比

Fluent の別名の色（`packages/tokens/src/alias/lightColor.ts` と `darkColor.ts`、コミット `1f59fc2`）が組む次の 4 組を比べた。

- 明: `colorBrandBackground: brand[80]` と、ホバーの `brand[70]`（124〜125 行目）
- 暗: `brand[70]` と、ホバーの `brand[80]`（同じ行）
- 背景の上の文字は `colorNeutralForegroundOnBrand: white`（55 行目、明暗とも）
- 明の `colorBrandForeground1: brand[80]`（44 行目）は、`colorNeutralBackground1: white`（67 行目）の上にある
- 暗の `colorBrandForeground1: brand[100]`（44 行目）は、`colorNeutralBackground1: grey[16]`（`#292929`、67 行目）の上にある

| キー | 白の文字 / 段 70 | 白の文字 / 段 80 | 段 80 / `#ffffff` | 段 100 / `#292929` |
| --- | ---: | ---: | ---: | ---: |
| brandWeb（基準） | 6.66 | 5.38 | 5.38 | 5.18 |
| 測った青 `#0078D4` | 6.63 | 5.38 | 5.38 | 5.19 |
| 黄 `#FFB900` | 6.91 | 5.59 | 5.59 | 4.96 |
| 赤 `#E81123` | 7.00 | 5.72 | 5.72 | 4.93 |
| 青緑 `#00B294` | 6.84 | 5.50 | 5.50 | 5.11 |
| 灰・黒・白 | 6.90 | 5.57 | 5.57 | 5.04 |
| `#0F6CBD` | 6.63 | 5.38 | 5.38 | 5.15 |
| ハイコントラストの 1 色 `#A1BFDE` | 6.82 | 5.53 | 5.53 | 5.10 |

- **すべての組が 4.5 を超えた。** WCAG 2.x の、普通の大きさの文字の AA の値である
- **4,105 個のキーでの最小:** 白の文字と段 70 は 6.35（`#0044ff`）、段 80 は 5.23（`#5555ff`）、段 100 と `#292929` は 4.90（`#ee4400`）だった。段 80 の最大は 5.74（`#dd2211`）である
- **キーによって 0.3 ほど動く理由:** 段の明度は D50 に移した Lab の L\* で揃えている。WCAG の輝度は D65 の Y で、Bradford の移し方では、色の付いた色ほど 2 つが少しずれる
- **段 80 の 2 列が同じ値になる理由:** 対比は 2 色のどちらを文字にしても同じ値になる。明の `colorBrandBackground` の上の白の文字と、白の背景の上の明の `colorBrandForeground1` は、どちらも白と段 80 の組である

比べに、Grill の前の調べで捨てた形を、上の組のうち 3 つで並べる。数はどれも、取り出した TypeScript の関数（`contrast`・`sRGB_to_LAB`・`snap_into_gamut`・`Lab_to_hex`）で出し直した。Python の写しの値と同じだった。OS の 7 色を段に置く形では、段 110 は Light1 と Light2 の間を Lab で 1/3 の所に補間した `#2aa1fb` である。

| 形 | 白の文字 / 段 80 | 段 100 / `#292929` | 段 110 / `#292929` |
| --- | ---: | ---: | ---: |
| theme designer そのまま（キー `#0078D4`、Vibrancy 0） | 5.78 | **3.75** | **4.48** |
| OS の 7 色を決まった段に置く（Dark1 → 80、Light1 → 100 など） | 5.67 | **4.44** | 5.26 |
| 同じ、ハイコントラストで 7 色が `#A1BFDE` になった時 | **1.91** | 7.64 | 7.64 |

theme designer そのままの形の段 110 は、theme designer が暗の `colorBrandForeground1` を `brand[110]` に替える時の値である（`utils/getOverridableTokenBrandColors.ts` 70〜75 行目）。

## (d) ハイコントラストで 7 色が 1 色になった時

ハイコントラストのテーマは、ブランドの段を使わない（`utils/createHighContrastTheme.ts` 11 行目は引数を持たず、`alias/highContrastColor.ts` に `brand[` は 1 つも無い）。OS がハイコントラストの間にアプリが明か暗を求めた時だけ、`Accent` の `#A1BFDE` がキーになる。その時の 16 段は、明度が目標どおりの灰青色で、C\* は 4.7〜19.7 である。対比は上の表の最後の行にある。段 10 から 160 の順に次のとおりである。

## 制御点

`getBrandTokensFromPalette` の既定（2/3 と 1/3）と、theme designer の画面の既定（Vibrancy 0、つまり両方 0。`Context/ThemeDesignerContext.tsx` 74〜80 行目、`components/Sidebar/Form.tsx` 103・116 行目）を、キー `#0F6CBD` で `brandWeb` と比べた。値は CIE76 の色差 ΔE で、段 10 から 160 の順である。

| 制御点 | ΔE（段 10〜160） | 最大 |
| --- | --- | ---: |
| 2/3 と 1/3 | 8.1 8.5 8.2 9.2 7.0 6.2 3.0 0.0 5.9 10.9 9.0 8.6 6.9 5.3 3.8 1.4 | 10.9 |
| 0 と 0 | 4.6 4.3 3.8 4.0 3.5 3.2 0.6 0.0 12.1 18.7 16.3 15.1 12.5 9.0 5.3 1.8 | 18.7 |

0 では、キーより明るい段の彩度が早く落ち、段 90〜130 で `brandWeb` から大きく離れる。そこで、関数の既定の 2/3 と 1/3 にした。どちらの値でも、`brandWeb` は作れない。`brandWeb` は手で決めた段で、この曲線の上には無い。

## 分かったこと

- **調べの数は確かめられた。** Python の写しは theme designer と 64 段すべてで同じ値を出した。規則の値も、元の関数を動かして出し直した
- **対比が守られる:** この規則は、色相によらず、Fluent の別名の色が組む 4 組で 4.5 を超える。4,105 個のキーでの最小は 4.90 で、`brandWeb` の 5.18 より 0.3 低い所がある
- **色の無いキーとハイコントラストで壊れない:** 灰・黒・白は同じ灰色の 16 段になる。ハイコントラストで 1 色になっても、明度は目標どおりになる
- **捨てた 2 つの形は、測った青でも組を落とした:** theme designer そのままの形は、暗の `colorBrandForeground1` が 3.75 だった。OS の 7 色を段に置く形は、同じ組が 4.44 で、ハイコントラストの 1 色では白の文字が 1.91 だった
- **曲線の色相を回す段は省ける:** ねじれが 0 の時は、この段があってもなくても同じ結果になる

## 確かめていないこと

- **Windows の画面:** 何も測っていない。ほかのアクセントで OS が返す 6 段は読んでおらず、この規則と比べていない。Windows がアクセントの 6 段を作る式は公開されていない
- **公開されている theme designer:** Web の画面は動かしていない。動かしたのはコミット `1f59fc2` のソースで、公開されている版とは違うかもしれない
- **対比の基準:** WCAG 2.x の対比だけを見た。APCA などのほかの基準と、文字の大きさごとの値は見ていない
- **C# の写し:** まだ無い。行 TH1 の実装で、この記録の 16 進と同じになることを確かめる（設計書 §13.2「確かめ方」）
