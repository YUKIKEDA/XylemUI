# T12: リッチテキストの範囲のスタイル・装飾・リンク

テキストの葉に、範囲のスタイル・装飾・リンクと文字の単位の当たり判定を足した（ロードマップの行 T12、Issue #425、設計書 §4.8）。範囲を持つ葉の費用を、範囲を持たない同じ葉と比べた。範囲を持たない葉が通る道（整形・layout・入力）は、ブランチの基点（d8abb47）と比べた。どれも Windows 11 26300、Intel Core i5-13400F で、NativeAOT の Release を論理 CPU 2（P コア）に固定し、優先度を高くして測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c "start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe rich-text plain > plain.json"
cmd /c "start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe rich-text ranged > ranged.json"
cmd /c "start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe segment > segment.json"
```

`resize-text 51` と `input` も同じ形で流した。基点との比較は、2 つのビルドを A・B・B・A の順で 3 巡（先に流す側を巡ごとに入れ替える）、範囲を持つ葉と持たない葉の比較も同じ順で 3 巡、それぞれ 6 回ずつ流した。表の値は、6 回の中央値（p50）の最小〜最大である。

`rich-text` は、ウィンドウを開かずに、Windows のフォント（`DirectWriteFontProvider`）で、14 px の日本語の 1 文（33 文字）の葉を 100 個、列に並べる。範囲を持つ葉は、リンク（ホバー中に下線）、太字、赤、下線、背景の 5 つの範囲を持つ。レイアウトの範囲は太字の所で分かれて 3 つ、描画の範囲は 9 つになる（太字はレイアウトの範囲だけを分け、リンクはスタイルを持たないのでレイアウトの範囲を分けない）。

## 範囲を持つ葉の費用（`rich-text`）

| 指標 | 範囲を持たない葉 | 範囲を持つ葉 |
| --- | --- | --- |
| 最初の layout（100 葉） | 0.83〜1.55 ms | 1.57〜3.26 ms |
| 描画の段（100 葉、layout は済み） | 132.8〜146.5 µs | 257.7〜270.4 µs |
| 1 つの葉の見た目を変えたフレーム | 132.9〜146.5 µs | 258.6〜270.8 µs |
| マウスの移動（リンクに入る・出る） | 0〜0.1 µs | 0.9〜1.1 µs |
| その移動が求めるフレーム | なし | 241.2〜271.6 µs |

- **描画:** 範囲を持つ葉は、1 つあたり約 1.25 µs 長い。1 行が、色ごとのグリフの並び 3 本、背景の矩形 1 つ、下線（字形との重なりを空けて）を描く。範囲を持たない葉は、グリフの並び 1 本である
- **見た目の変更:** 範囲を持たない葉は文字の色を、範囲を持つ葉は 1 つの範囲の色を変えた。どちらも layout をし直さず、フレームは描画の段とほぼ同じ時間だった。今の描画の段は、1 つの葉が変わっても表示リスト全体を作り直す
- **ホバー:** 移動そのものは、リンクの検索とホバーの印で約 1 µs。ホバー中の下線を描くために、葉に描画の印を付け、次のフレームが表示リスト全体を作り直す
- **最初の layout:** 範囲を持つ葉は、1 つの葉を 3 回に分けて整形し、太字のフォントの run も持つ
- **字形の輪郭:** 下線を引いた字形の輪郭は、`GlyphIntercepts` に 5 つ覚えた（上限は 1,024）

## 範囲を持たない葉の道（基点 d8abb47 と比較）

### 整形と折り返し（`segment`）

| 文 | 整形（基点） | 整形（T12） | 折り返し（基点） | 折り返し（T12） |
| --- | --- | --- | --- | --- |
| 日本語 | 230.8〜254.2 µs | 242.5〜268.6 µs | 16.67〜18.37 µs | 17.12〜18.64 µs |
| 英文 | 211.9〜228.7 µs | 218.8〜237.9 µs | 4.79〜5.38 µs | 4.72〜5.22 µs |

範囲は重なったが、整形の最小値は T12 が 3〜5 % 大きい。原因は、行 T13 で変種を作って分けた。グリフごとの字間の確かめ（`Spacing`）によるもので、ループの形ではない（`docs/benchmarks/t13-inline-objects.md` の「T12 の整形の差の原因」）。折り返し、行を並べる処理、絵文字の run ごとの整形と分割は、範囲が重なり、最小値も同じだった。

### layout（`resize-text 51`、10,101 ノード）

| 指標 | 基点 | T12 |
| --- | --- | --- |
| 折り返す葉、当たったとき | 1.67〜2.61 ms | 1.70〜2.08 ms |
| 折り返す葉、外れたとき | 8.86〜10.21 ms | 9.46〜10.88 ms |
| 1 行の葉、当たったとき | 0.51〜0.60 ms | 0.49〜0.60 ms |
| 最初の layout（折り返す葉） | 60.97〜68.83 ms | 59.63〜68.19 ms |
| 管理ヒープ（折り返す葉の木） | 39.51〜39.52 MB | 40.07〜40.08 MB |

- 時間の範囲は、すべて重なった
- ヒープは、1 万の葉で 0.56 MB、葉 1 つで 56 バイト増えた。`TextLeaf.Ranges` の 8 バイト（葉のオブジェクトは 112 → 120 バイト）、run の `RunStyle` の 24 バイト、その配列の頭の 24 バイトである。§3.2 の式（56r）と V1a のテストの上限（配列の頭を 15 個）も、これに合わせて直した

### 入力（`input`）

レビューの後、リンクを持つ葉が木に 1 つもなく、ポインタがリンクの上にもないときは、リンクを探さない形にした（`UiTree.LinkLeaves`）。次の表は、その形で測り直した値である。

| 指標 | 基点 | T12 |
| --- | --- | --- |
| Click（押して離す） | 0.314〜0.351 µs | 0.329〜0.363 µs |
| タッチのタップ | 0.288〜0.331 µs | 0.303〜0.346 µs |
| ホバーの変化 | 0.192〜0.238 µs | 0.189〜0.224 µs |
| 移動（深さ 1） | 0.147〜0.169 µs | 0.149〜0.173 µs |
| 移動（深さ 50） | 4.33〜5.05 µs | 4.30〜5.12 µs |
| ホイール | 0.094〜0.105 µs | 0.098〜0.109 µs |

- すべての指標で、範囲が重なった
- 測り直す前の T12 は、Click が 0.340〜0.377 µs で、基点と範囲が重ならなかった。押すときと離すときの当たり判定のたびに、当たったノードの文字の葉を読んでリンクを探していた（`FindLink`）
- 範囲を持たない木で基点より増えた処理は、当たり判定ごとの `LinkLeaves` の読み出しと、押したときにリンクを覚える 2 つの書き込みだけである。Click とタップの最小値は 0.015 µs 大きいが、範囲は重なった

### フレーム（`frames`、`frames --tree`、ウィンドウあり、600 フレーム）

> この節の `frames` と `frames --tree` の値は、62.5 Hz のタイマーの時計で測った（Issue #445、`docs/benchmarks/q2-frames-clock.md`）。基点との比べは成り立つが、CPU のフレームの約 16.5 ms は、Present が止まっていた時間を含む。

| 場面 | 表示リストを作る（基点） | 表示リストを作る（T12） | CPU のフレーム（基点） | CPU のフレーム（T12） |
| --- | --- | --- | --- | --- |
| `frames`（1 行の文字を含む） | 0.0229〜0.0273 ms | 0.0221〜0.0277 ms | 16.48〜16.53 ms | 16.50〜16.53 ms |
| `frames --tree`（1,000 ノード） | 0.0347〜0.0386 ms | 0.0337〜0.0384 ms | 15.99〜16.19 ms | 15.98〜16.08 ms |

- どの指標も範囲が重なった。layout（`--tree` の 0.179〜0.202 と 0.173〜0.201 ms）、GPU の時間、表示までの時間も同じだった

## 割り当て

次は 0 バイトだった（テストの `SteadyStateAllocation`）。

- 範囲を持つ葉の書き直し（同じ範囲、色を入れ替えた範囲、背景・下線・取り消し線・破線の上線を含む描画）
- リンクのホバーの出入りと Click の配送、その後のフレーム
- 覚えた字形と帯での `GlyphIntercepts.Intercept`

## メモリ（テストの `Ranges_Memory_IsTheFormula`）

範囲を持つ葉の `TextRanges` は、136 + 80L + 60P + 144K バイトである（設計書 §4.8）。L・P・K は、レイアウトの範囲・描画の範囲・リンクの配列の長さで、2 から始まり、足りないときに 2 倍にする。`rich-text` の葉（L = 3、P = 9、K = 1）は、配列が 4・16・2 の長さになり、136 + 320 + 960 + 288 = 1,704 バイトである。
