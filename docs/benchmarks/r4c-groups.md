# R4c: 層・グループの不透明度・その中の文字のグレースケール

表示リストに `PushOpacity` と `Pop` を足し、レンダラに層とそのテクスチャのプールを足した（ロードマップの行 R4、Issue #263、設計書 §5.0「層・クリップ・変換・`DrawingContext` の API」）。その正しさと費用を確かめた。どれも Windows 11 26300、Intel Core i5-13400F、主モニタは 125 % で、時間は NativeAOT の Release で測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe frames 600              # 今の場面（矩形 1,000 個と文字 1 行）
<dir>/XylemUI.E2E.exe frames 600 --shapes     # R4a の形の場面
<dir>/XylemUI.E2E.exe frames 600 --curves     # R4b の線・楕円・円弧の場面
<dir>/XylemUI.E2E.exe frames 600 --groups     # 1 行 10 個の矩形のカード 100 枚。どれも不透明度 0.8 のグループ
<dir>/XylemUI.E2E.exe frames 600 --groups --layers 10   # そのうち層になるカードを 10 枚にする
<dir>/XylemUI.E2E.exe draw-text               # 定常状態の DrawText、1 グリフ
<dir>/XylemUI.E2E.exe fill-rect 1.25          # 矩形 1,000 個を書くだけ、1 個
<dir>/XylemUI.E2E.exe fill-rect 1.25 --grouped   # 同じ矩形を 10 個ずつ不透明度 0.8 のグループに入れる
```

`--groups` の場面では、1 枚おきのカードに、最初の矩形に重なる 11 個目の矩形を置く。既定では、層になるのは 50 枚、アルファを子に配るのは 50 枚である。`--layers N` は、11 個目の矩形を置くカードを奇数番目の最初の N 枚にする。

## 正しさ（WARP、`GroupRenderTests`・`GroupListTests`）

WARP で描いた画素を読み戻し、CPU で重ねた値と比べた。

| 場合 | 許した差 |
| --- | --- |
| 子が離れたグループ: 層を作らず、子の色にアルファを掛ける。描く回数は 1 | 1 |
| 子が重なるグループ: 層になり、（赤の上の黒）× 0.5 になる。描く回数は 2（層への描き込みと重ねる描画） | 1 |
| 入れ子: 離れた子のグループの中の層は 2 つのアルファを掛けて重なる。層の中の離れた子のグループは、層の中で子にアルファを配る | 1 |
| 層の中のどの種類の命令も、その位置に描かれる（楕円の線・影・グラデーションとボーダーの角丸の矩形・グラデーションの線）。離れた子のグループでは、グラデーションもアルファを受け取る | 2 |
| 描き先からはみ出す層は描き先で切られ、テクスチャは 64 画素に切り上げた描き先の大きさを超えない。描き先の外にある層は描かず、層も作らない。その後の命令は描かれる | 1 |
| プールの上限が 0 バイトのとき、層の要るグループは子にアルファを配り、断った数を 1 数える | 1 |
| テクスチャを作る呼び出しが `E_OUTOFMEMORY` を返すとき、同じく子にアルファを配り、断った数を 1 数えて、フレームを描き終える | 1 |
| 3 つの兄弟の層は 2 枚のテクスチャを交互に使い、どれもその位置にそのアルファで描かれる | 1 |
| グループの中の ClearType の文字はグレースケールの層になり、アルファ 128 のグレースケールの文字をグループなしで描いた画素と同じになる | 1 |

- **許容 2:** グラデーションのディザが 8 ビットの 1 段まで足すためである（R4a と同じ）
- **表示リスト:** 子の外接矩形が層を決めること、和集合と交わる子で層になること、影（ぼかしと広がり）と入れ子のグループの外接矩形が数えられること、不透明度 1 と空のグループが何も記録しないこと、範囲の外の不透明度・`Push` の無い `Pop`・閉じていないグループの読み出しを断ること、を確かめた（`GroupListTests`）
- **文字:** グループの中の文字は `ResolveGlyphs` の後もグレースケールで、置いたグリフの四角形が、それを囲むすべてのグループの外接矩形を広げた（`ResolveGlyphs_TextInGroups_IsGrayAndWidensTheirBounds`）
- **定常状態:** 層・離れた子のグループ・グループの中の文字を持つフレームは、温まった後はアロケーション 0 で、表示リストも伸びず、層のテクスチャも同じものだった（`SteadyState_Groups_AllocateNothing`）

- **GPU:** 層の無い表示リストのシェーダは、main と同じ機械語である（`D3DDisassemble` で比べた）。`--shapes` の 600 フレームの GPU は、両方の版で 960〜1,100 µs の間を動いたので、1,200 フレームで交互に測った
- **`frames --curves` の Draw の段（2〜4 µs 長い）:** 機械語の置き場所の違いである。グループの無い `WriteInstances`・`WriteCurve`・`ReadCurve`・`TryNext`・`AddToDraw` は、この版と、表示リストだけを変えた 1 つ前の版とで同じ命令だった（`dumpbin /disasm`。番地だけが違う）。その 1 つ前の版の Draw の段は 108.2〜112.2 µs で、main（108.0〜110.6 µs）と範囲が重なった。グループの無い `WriteCurve` は、main とも同じ命令である
- **`frames --shapes` の表示リストの段（約 1 µs 長い）:** 影と角丸の矩形は、記録を書いた後に、グループの中かを確かめる（外接矩形を足すため）。そのために `this` を呼び出しの後まで持つので、`DrawShadow` は保存するレジスタが 1 つ増え、角丸の `FillRect` とともに 1 回の呼び出しで比べと分岐が増えた（`dumpbin /disasm` で、`DrawShadow` の速い道はレジスタの保存と戻し・写し・比べと分岐の 6 命令、角丸の `FillRect` は 4 命令長い）。比べの場面の `Scene.Build` も、`groups` の分かれ道で 99 命令長くなった。形 1 つで約 1 ns であり、グループの外接矩形を持つことの費用として残す
- **`fill-rect`:** 矩形を書いた後のグループの中かの比べで、`FillRect` は 103 命令から 107 命令になった。1 つ前の版では main より 0.07 ns 長いだけだった（7.60〜7.67 ns と 7.54〜7.58 ns）。この版の `FillRect` はその版と同じ命令で、残りの差は、`--grouped` の分かれ道を足した測る側のループの違いである
- **`draw-text`:** `DrawText` は 1 つ前の版と同じ命令で、そのときは 45.86〜46.56 ns だった

### Draw の段で見つけて直したもの（VS のコレクタで、`frames 20000 --curves` を main と並べて採った）

最初の版は、層の無い場面でも Draw の段が main より長かった（`frames` で 1〜2 µs、`frames --curves` で 4〜7 µs）。関数ごとの重みを main と比べて、次の 4 つを直した。直した後は、上の表のとおり main と範囲が重なる。

| 見つけたもの | 直し方 |
| --- | --- |
| 色にグループのアルファを掛ける `Faded<NoGroups>` が、関数の呼び出しのまま残った（ネイティブのコンパイラがインライン化しなかった） | `AggressiveInlining` を付けた |
| 線・楕円・円弧の命令を局所変数に写す所で、1 個ごとに `Memmove` が呼ばれた。写すのは、層の中で描き方を選ぶためだけである | グループの無い表示リストでは、命令をそのまま `WriteCurve` に渡す。グループの無い表示リストでは、残る種類はどれも線・楕円・円弧なので、種類の比べも main と同じ回数にした |
| グリフの run を書く所を関数に分けたら、呼び出しのまま残った | `AggressiveInlining` を付けた（main ではループの中に書いていた） |
| `WriteCurve` の中で層の原点を引いた 4 つの値が、関数の間ずっとレジスタに残り、呼び出しのたびに XMM レジスタを 4 つ多く保存し戻した（main の 326 命令に対して 351 命令） | 層の中では、`WriteCurve` を呼ぶ前に命令の座標から原点を引く。グループの無い `WriteCurve` は main と同じ機械語になった |

| --- | --- | --- | --- | --- |
| 層 0 個（`--layers 0`。グループ 100 個はどれも子にアルファを配る） | 39.3〜39.5 µs | 110.6〜111.6 µs | 0 | 2 |
| 層 10 個（`--layers 10`） | 39.1〜47.7 µs | 186.4〜188.4 µs | 2 枚、131,072 バイト | 32 |

どの場面でも、断った層は 0 だった。この表の回は、CPU の段がこの記録のほかの表より長く出た（層 0 個の Draw の段は、上の費用の表を測った回では 31.3〜31.7 µs だった）。そのため、層の CPU の費用は同じ回どうしでだけ比べる。

- **層 1 つの GPU:** 層 0 個の場面との差を層の数で割ると、10 個で約 7.6 µs、50 個で約 8.1 µs である。D10 の試作の約 2.2 µs より大きい。層ごとに別のテクスチャを使った版（PR #264 のレビューの前）は約 10〜11 µs で、そのうち層への描き込みが約 6 µs、重ねる描画が約 4.5 µs だった。描く回数（200 回増やして 21 µs）・消去・定数バッファの書き込み・描き先の切り替えのどれを抜いても下がらなかった。下げる仕事は行 Q4 で行う
- **層 1 つの CPU:** Draw の段の差を層の数で割ると、50 個で約 0.3 µs である（同じ回の、層ごとに別のテクスチャを使った版は約 0.6 µs）

### 兄弟の層のテクスチャ（PR #264 のレビュー）

層は `Push` から `Pop` までテクスチャを持ち、`Pop` で重ねる描画を出した後に返す。同じフレームの後の兄弟の層は、返されたテクスチャを使う。返したテクスチャをすぐに渡すか、間にほかの層をいくつ挟むか（`LayerPool.Spacing`）を、レビューの前の版と交互に 3 回ずつ測った。

| 形 | 層 50 個の GPU | 層 10 個の GPU | 層 50 個のテクスチャ |
| --- | --- | --- | --- |
| 層ごとに別のテクスチャ（レビューの前） | 657.4〜670.7 µs | 215.0〜218.1 µs | 50 枚、3,276,800 バイト |
| 返したらすぐに渡す | 685.1〜733.2 µs | 213.0〜224.3 µs | 1 枚、65,536 バイト |
| 間に 1 つの層を挟む（採った形） | 510.0〜520.2 µs | 186.4〜188.4 µs | 2 枚、131,072 バイト |
| 間に 2 つの層を挟む | 511.0〜525.3 µs | 192.5〜194.6 µs | 3 枚、196,608 バイト |
| 間に 4 つの層を挟む | 518.1〜523.3 µs | 192.5〜201.7 µs | 5 枚、327,680 バイト |

- **すぐに渡すと遅い:** 層が、直前の重ねる描画が読んだテクスチャを消去して描くので、その読みが終わるのを待つと考えられる
- **1 つ挟む形:** 2 枚のテクスチャが交互に使われ、層ごとに別のテクスチャを使った版より速くなった。2 つ・4 つ挟んでも速くならず、テクスチャが増えるだけだった。層ごとに別のテクスチャを使う版より速い理由は確かめていない
- **テクスチャの数:** 同時に開いている層の数（入れ子の深さ）と 1 枚で済み、フレームの層の総数に依らない。300 × 200 の項目 100 個が不透明度を変える画面でも、上限の 32 MB に届かない
- **重なりの検査の費用（`fill-rect 1.25 --grouped`、3 回）:** 10 個ずつをグループにした矩形 1 個は 14.50〜15.20 ns で、グループの無い 7.77〜7.85 ns より約 7 ns 長い。グループ 1 つの `PushOpacity` と `Pop` を 10 個で分けた分を含む。外接矩形の和集合を `MathF.Min` と `MathF.Max` で広げた最初の版は、1,000 個を 1 つのグループに入れて 1 個 15.8 ns だった。NaN と -0 の順を決めるので 1 つが約 13 命令になる。ただの比べ（`minss` と `maxss`）に替えて 13.4 ns、和集合を広げる関数をインライン化して 12.7 ns になった。表示リストの段では、層 0 個の場面が `frames`（グループ無し）より約 8 µs 長く、子 1 つで約 8 ns と同じ大きさである

### 層の描き方の候補

| 形 | 結果 |
| --- | --- |
| シェーダで層の原点を足す | 層の無い `frames --shapes` の GPU が約 6 µs 延びた。すべての画素の費用になる |
| 書いた後にマップしたバッファから読み戻して原点を引く | バッファが write-combined なので遅く、層の中の矩形 1,000 個で Draw の段が約 120 µs 延びた |
| 書くときに原点を引く（採った形） | 層の無い場面の費用は上の表のとおり |
| いつものシェーダでアルファを掛ける | 層の無い `frames --shapes` の GPU が約 5 µs 延びた |
| `false` に畳まれる `bool` の引数でシェーダを分ける | コンパイラの命令の並べ方が変わり、層の無い `frames --shapes` の GPU が約 2 % 延びた |
| 同じシェーダを `FADED` を定義してコンパイルした変種（採った形） | `FADED` の無いシェーダは main と同じ機械語になる |

### プール

- **大きさの丸め:** 層の幅と高さを 64 画素の倍数に切り上げ、入る中で最も小さい空いたテクスチャを使う。大きさが数画素変わる層も、同じテクスチャのまま描ける
- **上限:** 32 MB（2,560 × 1,440 のウィンドウの層 2 枚分）。場所を空けるために捨てるのは、前のフレームでも使わなかったテクスチャだけにした。最初の版はこのフレームでまだ頼まれていないテクスチャも捨てたので、画面の幅いっぱいの層が上限を超えると毎フレーム作り直し、GPU の p95 が 1.5 ms になった
- **捨てるまで:** 120 フレーム（60 Hz で 2 秒）使わなかったテクスチャは捨てる
- **メモリの無いデバイス:** テクスチャを作る呼び出しが `E_OUTOFMEMORY` を返したときは、上限で断ったときと同じく、子にアルファを配って断った数を数える。返されたテクスチャが間を置く前のものしかないときは、新しく作れなければそれを使う（`Layer_DeviceWithoutMemory_GivesTheAlphaToTheChildren`）
