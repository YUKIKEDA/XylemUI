# T13: テキストの葉のインラインオブジェクト

テキストの葉の行の中に、部品（インラインオブジェクト）を置けるようにした（ロードマップの行 T13、Issue #437、設計書 §4.8）。インラインオブジェクトを持つ葉の費用は、同じ文の、インラインオブジェクトを持たない葉と比べた。インラインオブジェクトを持たない葉が通る道（整形・layout・入力・フレーム）は、ブランチの基点（6f89761）と比べた。

どれも Windows 11 26300、Intel Core i5-13400F で測った。NativeAOT の Release を論理 CPU 2（P コア）に固定し、優先度を高くした。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c "start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe inline-objects plain > plain.json"
cmd /c "start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe inline-objects inline > inline.json"
cmd /c "start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe resize-text 51 > resize.json"
```

`segment`、`input`、`frames`、`frames --tree` も同じ形で流した。基点との比較は、2 つのビルドを A・B・B・A の順で 3 巡流した（先に流す側を巡ごとに入れ替える）。インラインオブジェクトを持つ葉と持たない葉の比較も、同じ順で 3 巡流した。どちらも 6 回ずつで、表の値は 6 回の中央値（p50）の最小〜最大である。

`inline-objects` は、ウィンドウを開かずに、Windows のフォント（`DirectWriteFontProvider`）で、14 px の日本語の 1 文の葉を 100 個、列に並べる。インラインオブジェクトを持つ葉は、文の中に 16 x 16 の箱を 2 つ持ち、揃え方は `Middle` である。持たない葉は、箱の所に「□」を持つ。100 の葉で、箱は 200 個になる。最初の葉の最初の箱は x = 44.15 に置かれた（「詳しくは」の後）。

## インラインオブジェクトを持つ葉の費用（`inline-objects`）

| 指標 | 持たない葉 | 持つ葉 |
| --- | --- | --- |
| 最初の layout（100 葉） | 1.41〜1.90 ms | 2.83〜3.16 ms |
| 描画の段（layout は済み） | 136.7〜151.6 µs | 180.9〜200.7 µs |
| 列の幅が変わったフレーム（1,200 と 1,100 を交互に） | 147.8〜163.4 µs | 192.7〜213.1 µs |
| 1 つの葉の箱の幅が変わったフレーム（持たない葉は文字の色） | 136.8〜151.6 µs | 189.4〜208.7 µs |

- **描画:** 持つ葉は、葉 1 つあたり約 0.45 µs 長い。中身は次の 3 つである。この差を分ける変種は作っていない
  - 範囲を持つ葉の道（`DrawRanges`）を通る
  - グリフの並びを箱の所で切って 2 本にする
  - 箱 2 つの背景（`FillRect`）を描く
- **幅の変化:** 葉の行のキャッシュには、どちらの幅も当たる。持つ葉は、layout のたびに箱 2 つを測る（箱は自分のキャッシュで返る）。箱が 200 個で約 45 µs、箱 1 つで約 0.22 µs である
- **箱の幅の変化:** 葉 1 つの箱の大きさが変わると、その葉の空きの送りを付け替え、行のキャッシュを捨てて、その葉を分け直す。フレームには描画の段（全体）が入る
- **最初の layout:** 持つ葉は、葉 1 つの文を、箱の前・箱・箱の間・箱・箱の後の 5 つの run に分けて整形する。空きの run には、空白のフォントを引く

## T12 の整形の差の原因（ロードマップの行 T13 の項）

T12 で、範囲を持たない葉の整形の最小値が 3〜5 % 大きくなった（`docs/benchmarks/t12-rich-text.md`、PR #426 のレビュー）。T12 が整形の道（`ShapingResult.Shape`）に足したものは 3 つある。

- run ごとに `RunStyle` を読む
- 2 つの `foreach` を添字のループにした
- グリフごとに字間を確かめる（`Spacing`）

これを分けるため、次の 4 つのビルドで `segment` を測った。4 つを、順を入れ替えながら 6 巡流した。

- T12 の前（d8abb47）
- この PR の head（bb35b92）
- 変種 1: head の 2 つのループを `foreach` に戻したもの
- 変種 2: head からグリフごとの字間の確かめを外したもの（測る文はどれも字間を持たない）

| 文の整形 | T12 の前 | head | 変種 1（`foreach`） | 変種 2（字間なし） |
| --- | --- | --- | --- | --- |
| 日本語 | 227.6〜235.6 µs | 231.0〜242.3 µs | 235.2〜250.4 µs | 223.4〜233.1 µs |
| 英文 | 206.6〜213.6 µs | 210.1〜230.4 µs | 208.0〜234.8 µs | 203.3〜227.2 µs |
| 絵文字（1 文字おき） | 410.4〜423.1 µs | 421.9〜448.8 µs | 423.5〜471.0 µs | 416.3〜464.8 µs |
| 絵文字なしの run | 185.3〜207.1 µs | 194.5〜210.0 µs | 194.2〜203.7 µs | 184.4〜207.5 µs |

- 差は、グリフごとの字間の確かめによる。外すと、日本語・英文・絵文字なしの run の最小値は T12 の前と同じか、それより小さい
- ループの形は効いていない。`foreach` に戻しても、最小値は head と同じか大きい
- 今の差は、日本語と英文の最小値で約 1.5〜2 % で、範囲は重なる。T12 の時点の 3〜5 % より小さい。T12 の測定は、ブランチの基点との比べ（3 巡）で、今回とは順の組み方が違う
- 字間の確かめは、字間を持つ範囲（T12 の `SpanStyle.LetterSpacing`）のための処理で、外せない。run の字間が 0 のときにグリフのループを分ければ、この差は無くせる。ただ、範囲が重なる差なので、この PR では変えていない

## 割り当て

次は 0 バイトだった（テストの `SteadyStateAllocation`）。

- インラインオブジェクトを持つ葉の書き直し（同じ子、色の入れ替わる範囲）
- 子の layout が変わり、大きさが変わらないときの layout とフレーム

## メモリ（テストの `Ranges_Memory_IsTheFormula`）

範囲を持つ葉の `TextRanges` は、160 + 80L + 60P + 144K + 36I バイトである（設計書 §4.8）。I はインラインオブジェクトの配列の長さで、インラインオブジェクトを持つ葉だけが、その 2 つの配列の頭 48 バイトを足す。

`inline-objects` の葉は、範囲を 1 つ、インラインオブジェクトを 2 つ持ち、リンクを持たない。配列は、レイアウトの範囲・描画の範囲・インラインオブジェクトが 2 の長さで、次のとおり 536 バイトである。

- `TextRanges` の頭: 160 − 24 = 136（リンクの配列が空で、その頭が無い）
- 範囲の配列の中身 2 つ: 160 + 120 = 280
- インラインオブジェクトの配列 2 つ: 頭 48 + 中身 72 = 120
