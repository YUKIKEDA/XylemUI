# P02b2: 範囲をまたぐ文字の選択

範囲をまたぐ文字の選択を、2 つの PR に分けて入れた（ロードマップの行 P02b2、Issue #499、設計書 §4.10）。この記録は、PR ごとの計測を足した。どれも Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で、プロセスを 1 つのコアに固定して（`start /affinity 4 /high`）、main とこの PR を交互に測った。比べた main は、1 つ目の PR が a22a5db、2 つ目の PR が 9ab1e44 である。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe input         # 欄の打ち込み・単語の移動・点滅・ドラッグ（text_field_*）
<dir>/XylemUI.E2E.exe rich-text     # 範囲のある葉とない葉の描画
<dir>/XylemUI.E2E.exe lists         # 1 万行の一覧の差分
<dir>/XylemUI.E2E.exe resize-text   # 1 万の文字の葉の最初のレイアウト
```

## 1 つ目の PR: 葉の選択と欄の移し替え

文字の葉（Core）が選択の範囲と色を持ち、描く段が選んだグリフの後ろに矩形を塗り、選んだグリフを選択の文字の色で描く。欄（`TextField`）は、選択を範囲のスタイルで書き直すのをやめ、葉の選択を置き直すだけにした。

### 欄の計測

1,000 文字の複数行の欄（`docs/benchmarks/p02b-text-field.md`）。値は 8 回の中央値の範囲である。

| 操作 | main | この PR |
| --- | --- | --- |
| 選択のドラッグの 1 フレーム | 49.0〜54.2 µs | 41.7〜45.4 µs |
| 　うち描く段 | 47.9〜53.0 µs | 41.1〜44.8 µs |
| 　うち配送 | 1.0〜1.1 µs | 0.6 µs |
| 点滅の 1 フレーム | 39.9〜44.3 µs | 39.2〜43.5 µs |
| 末尾に 1 文字打つ（4 回） | 137.4〜140.4 µs | 134.2〜136.0 µs |
| Ctrl+← で 1 単語戻る（4 回） | 59.9〜66.2 µs | 58.1〜64.7 µs |

- ドラッグの描く段は、点滅だけのフレームとほぼ同じになった。main では、選択が変わるたびに欄が葉を範囲のスタイルで書き直し、描く段が範囲の道を通っていた。今は、選択の無い行は範囲の無い葉の道を通り、選択のある行だけを切って描く
- 配送が 1.1 µs から 0.6 µs になったのは、選択の移動で葉の書き手（`TextBuilder`）が走らなくなったためである
- 打ち込みは、レイアウトの段が 4 回とも 2〜3 µs 短く出た。打ち込みの経路でこの PR が変えたのは、欄の書き手が選択を読まなくなったことだけで、レイアウトを速くするための変更ではない。原因は分けていないので、速くなったとは書かない

### 文字の葉が 8 バイト大きくなった

文字の葉（`TextLeaf`）は、選択への参照 1 つを持つ。選択の中身（範囲と色）は、初めて選ばれた葉だけが作って持ち続ける。P02b の教訓（`.cursor/rules/perf.mdc`）どおり、大きくする前に 1 万の葉の最初のレイアウトを測った。

| | main | この PR |
| --- | --- | --- |
| `resize-text` の `first_layout_wrapped_ms`（6 回） | 60.2〜82.5 ms（中央値 62.9） | 62.2〜64.1 ms（中央値 63.7） |

P02b で行の結果を大きくしたときの約 12 ms の遅れは無かった。

### main への影響

- `input` の既存の値（12 回）と `rich-text` の値（4 回）は、回ごとの幅の中に収まった。`us_per_disabled_change_10101_nodes_p50` は、1 回目の 4 回ではこの PR が速く、2 回目の 8 回では遅く出た。12 回を合わせると、main が 162〜204 µs、この PR が 180〜209 µs で重なるので、回ごとのぶれとみる
- `lists` の差分のうち、値の変更（`value_diff_us_p50`）だけが長かった。8 回ずつ測り、main が 78.1〜99.9 µs（中央値 79.5）、この PR が 83.5〜95.5 µs（中央値 85.5）で、中央値で約 6 µs 長かった。ほかの 3 つの差分は幅の中だった
  - 描く段を main に戻した版（変種 A）でも、値の変更は同じだけ長かった（83.7〜90.6 µs）。描く段の変更ではない
  - 2 つの実行ファイルを `dumpbin /disasm` で比べると、差分の経路の 249 の関数（`ForBlock`・反応の仕組み・`TextBuilder`・`NodeTextWriter`・`Invalidation`・`UiTree.Set*`・`ListCost`）のうち、命令が違うのは `TextLeaf` の 6 つと `UiTree.SetTextColor` だけだった。その違いも、葉のフィールドの位置が 8 バイトずれたこと（`[rbx+28h]` が `[rbx+30h]` に）だけである。ほかは番地のほかは同じ命令で、先頭の番地を 64 で割った余りが変わった関数が多い
  - 葉に参照を足したことによるフィールドの位置と、機械語の置き場所の違いとみる（`.cursor/rules/bench.mdc`）

### 描く段を分けた理由

最初の版は、範囲の道（`DrawRanges`）と、グリフを範囲ごとに切る `Pieces` に、選択の確かめを足した。選択の無い葉も、グリフごとに選択を確かめることになり、`rich-text` の範囲のある葉の描画が長くなった。

| 版 | `draw_ranged_us_p50`（4 回） |
| --- | --- |
| main | 242.0〜268.1 µs |
| 範囲の道に選択を足した版 | 252.2〜282.1 µs |
| 描く段を main に戻した版（変種 A） | 238.3〜264.5 µs |
| 選択のある行だけを別の関数で描く版（この PR） | 241.1〜243.7 µs |

今の形は、選択のある行だけを `DrawSelected` で描き、範囲の道と範囲の無い葉の道は main のコードのまま通す（`.cursor/rules/perf.mdc` の「ほとんどのフレームが使わない機能は、それを持たないループの写しを持つ」）。

## 2 つ目の PR: `SelectionArea` と Todo

`Primitive.SelectionArea` と `.Unselectable()` を入れ、`samples/Todo` の列を領域で包んだ。領域に加わる文字の葉は、描く段で当たりの領域を書く。木に領域が 1 つも無い間は、描く段はこの確かめをしない（`UiTree.SelectionAreas`）。

### 領域の計測

1,000 の文字の葉（「Item n」、Windows のフォントの 14 px、4 px おき）の列を領域で包み、最初の葉を押した状態から測った（`benchmarks/XylemUI.E2E/TextFieldCost.SelectionArea.cs`）。値は 4 回の中央値の範囲である。

| 操作 | 全体 | 配送 | 描く段 |
| --- | --- | --- | --- |
| 51 番目の葉と最初の葉の間を往復するドラッグの 1 フレーム（50 の葉を選ぶか外す） | 403.1〜420.9 µs | 15.6〜17.0 µs | 387.3〜403.7 µs |
| 同じドラッグで、終点が 51 番目の葉の下の隙間 | 377.5〜424.6 µs | 15.2〜18.0 µs | 361.9〜407.8 µs |
| Ctrl+A（1,000 の葉をすべて選ぶ） | 504.1〜525.0 µs | 31.3〜32.8 µs | 472.1〜491.3 µs |
| Ctrl+C（1,000 の葉をコピーする） | 36.6〜42.7 µs | 36.6〜42.6 µs | 0 µs |
| 選択を変えずに描き直すフレーム（1,000 の葉がすべて選ばれた状態） | 462.1〜500.1 µs | 0.2 µs | 461.9〜499.3 µs |

- **描く段:** どのフレームも、表示リストを丸ごと作り直す（設計書 §5.0.1）。1,000 の葉のグリフの並びと当たりの領域を書く分で、選択を変えずに描き直すフレームとほぼ同じである。選んだ葉は選択の届く行の道（`DrawSelected`）を通るので、すべて選ばれたフレームは、50 の葉だけが選ばれたフレームより長い
- **ドラッグの配送（約 16 µs）:** 領域は、表示リストの当たりの領域（葉ごとに 1 つと領域の 1 つ、約 1,000）を後ろから 1 回たどり、点の上の葉と、点より前の最後の葉を見つける。終点が隙間にあっても同じ 1 回である
- **Ctrl+A の配送（約 32 µs）:** 領域の中の葉を木の順に集め直し、1,000 の葉の選択を置く
- **Ctrl+C（約 40 µs）:** 1,000 の葉の文字を改行でつないで文字列を作る。この操作だけが割り当てる（設計書 §4.10「費用」）
- ドラッグと、選び始める押下のフレームの割り当てが 0 であることは、`SelectionAreaTests.SteadyState_DragAndPressFrames_AllocateNothing` で確かめた

JIT で最初に測ったときは、ドラッグの描く段が、選択を変えずに描き直すフレームの倍に出た。選択の無い葉 1 枚を描く時間も倍だった。そのため、測った順に起きた JIT の段階的な最適化（tiering）の差とみて、NativeAOT で測り直した。NativeAOT では、上の表のとおり倍の差は無い。

### main への影響

- `input` の既存の値は、`us_per_move_depth_1_p50` を除いて、回ごとの幅の中に収まった。`lists`・`rich-text`・欄の 4 つの計測も幅の中だった
- `us_per_move_depth_1_p50` は、main が 0.158〜0.164 µs、この PR が 0.167〜0.168 µs だった。この PR は、ホバーの変わる移動でカーソルを決める関数に確かめを 1 つ足しただけで、この計測の移動はホバーを変えない。`dumpbin /disasm` で、移動の経路の 19 の関数（`WindowInput` の `HandleInBatch`・`Point`・`Target`・`TestHover`・`SetHover`・`SendHoverChange`・`UpdateHover`、`DisplayList.HitTestAt`・`Holds` など）を比べると、番地のほかは命令がすべて同じで、多くは先頭の番地を 64 で割った余りが変わった。機械語の置き場所の違いとみる（`.cursor/rules/bench.mdc`）
- `todo` は、列を領域で包んだので main と同じ木ではない。文字の葉が当たりの領域を書く分、描く段が長めに出たが、各操作の値は main の回ごとの幅と重なった
