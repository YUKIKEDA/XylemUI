# L4 のレイアウトの基準値

CSS の結果を変えずにレイアウトの費用を減らした（ロードマップの行 L4、Issue #101、設計書 §3.2「L4 の方式」）後の費用を、L1a・L1b と同じ方法で測った。

## 測った物と機械

- コミット: このファイルを加えたコミット（`git log -1 -- docs/benchmarks/l4-layout.md`）
- 機械と版と作り方: L1a と同じ（`docs/benchmarks/l1a-layout.md`）。場面は L1a の 3 つと L1b の wrap の場面（`docs/benchmarks/l1b-layout.md`）
- XylemUI の葉は、比較の場面でも Taffy の XML テストでも、内容の幅の関数（`IntrinsicWidthsFunc`）を持つ。テキストの葉は T1 の後に、整形の結果から同じ関数を持つ

## 再現

```powershell
./benchmarks/compare/build.ps1 -Out <dir>
./benchmarks/compare/layout.ps1 -Built <dir> -Rounds 5
<dir>/xylemui/XylemUI.E2E.exe layout-loop <s6b|auto_min|percent|wrap> <change|width> 300000   # プロファイル用
```

**試して戻したもの**:

- 計測のキャッシュを初めて保存するときに確保する（Chromium の `measure_cache_`）: この場面では測られるノードが 10,100 あり、12.5 MB が 7.8 MB にしか減らず、最初の layout が 15〜48 % 遅くなった（間接参照と layout の中での確保）
- 計測のキャッシュの数を 2 にする: 幅の変更が 3 倍遅くなった（CSS の既定 1,078 → 3,540）
- 基準の大きさの引き継ぎを `UiNode` に持つ: ノードが 528 から 656 バイトになり、幅の変更が 11〜14 % 遅くなった。計測のキャッシュに移した
- 基準の大きさの引き継ぎを、実行の種類で分けずに 1 つだけ持つ: 容器は 1 回の pass で測られて layout され、2 つが互いに上書きして一度も使われなかった
- 問い合わせた軸の大きさが決まっている測るだけの実行で、読んだ印を付けない（行 L4 の項目）: テスト全体で、そうした問い合わせは 7 回しかなかった。エンジンは、大きさが決まっていれば問い合わせずにその値を使う

## 最も速い相手との差の説明（設計書 §3.2 の受け入れ (c)）

- **最初の layout（Flutter の約 3〜5 倍）**: 1 回の計算の費用は Flutter と同じ。XylemUI は S6b の意味で 3,082 µs ÷ 30,201 回 = 約 102 ns、Flutter は 1,047 µs ÷ 約 10,100 ノード = 約 104 ns。差は回数から来る。CSS Flexbox の手順は、葉 1 つにつき、内容の幅（1 回）、幅が決まったときの高さ（1 回）、本番の layout（1 回）を要る。CSS の既定では、列が行の自動の最小サイズのために行を min-content でも測るので、高さの計測が 1 回増える。Flutter の `Row` は自動の最小サイズも shrink も持たず、子を 1 回だけ layout する（`flex.dart` の `_computeSizes`）
- **1 か所の変更（Flutter の約 4〜7 倍）**: Flutter も XylemUI も、変えた葉の行と、根の列の flex を解き直す（変わっていない子は前回の結果を使う）。Flutter は変わっていない子 1 つにつき制約の比較 1 回（double 4 つ）で戻り、子 1 つあたり約 25 ns（5.0 µs ÷ 200 個）。XylemUI は約 100 ns（S6b の意味で 20.0 µs ÷ 200 個）。CSS の手順は項目ごとに、項目の作成・基準の大きさ・伸縮の解決・行の交差軸・使う交差軸・本番の配置の 6 つの段を通り、基準の大きさは引き継げても、ほかの段は値を毎回計算する
- **幅の変更（Avalonia の約 1.6 倍、`%` ありは約 4.6 倍）**: Avalonia の横の `StackPanel` は子を無限の幅で測るので、窓の幅が変わっても子を測り直さず、配置し直すだけになる。XylemUI は CSS どおり、幅の変わった 100 行の flex を解き直す（項目は 1 万個で、1 つあたり約 60 ns）。`%` ありでは、項目の幅が容器の幅に依存するので、基準の大きさを引き継げない

## 受け入れ（設計書 §3.2、Issue #101）

- (1) GPUI のレイアウト（Taffy 0.9.0）よりばらつきを超えて遅くない: 満たす（どの場面とどの指標も 2〜8 倍速い）
- (2) 幅の変更が Layout の予算 2.0 ms の内側: 満たす（最も遅い `%` ありで最大 1,853 µs）
- (3) 定常状態のアロケーション 0: `SteadyState_RelayoutAfterOneChange_AllocatesNothing`（CSS の既定・`%` あり・wrap の 3 つの場面、内容の幅の葉で）
- (4) 最も速い相手と同等を目標にし、届かない指標は CSS の手順で避けられない計算の回数と 1 回の費用で説明する: 上の説明
- L1b で L1a の場面の 1 か所の変更が 4〜8 % 遅くなった分は、L1a より速くなって解消した（S6b の意味で L1a 28.7 µs、今 20.0 µs）
