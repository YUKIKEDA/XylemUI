# P02a2: ヘッドレスのアプリの描画とゴールデン

ヘッドレスのアプリが WARP で描き、フレームを読み戻し、PNG に書き、ゴールデンと比べられるようにした（ロードマップの行 P02a2、Issue #468、設計書 §12.3）。描画は別のパッケージ `XylemUI.Testing.D3D11` の `WarpRenderer` で、`D3D11Renderer` をウィンドウもスワップチェーンも無しに、テクスチャへ描かせる。アプリの描画の経路（`WindowFrames`、`D3D11Renderer.Draw`）は変えていない。変えたのは、描き先がスワップチェーンかテクスチャかの分かれ道だけである。

どれも Windows 11 26300、Intel Core i5-13400F で、Release の JIT で測った。テスト基盤の時間なので、NativeAOT では測っていない。

## 1 フレームの時間

同じ木を、本物のウィンドウ（`DesktopWindow`、WARP、スワップチェーン）と、ヘッドレスのアプリ（`WarpRenderer`）で描いた。木全体の色を変えて 1 フレームを回すことを、50 回の慣らしの後に 400 回測り、中央値をとった。3 回流した。測りの道具は一時的なテストで、リポジトリには入れていない。

| 木 | ウィンドウの 1 フレーム | ヘッドレスの 1 フレーム | 読み戻し（`Capture`） |
| --- | --- | --- | --- |
| Counter（320 × 200） | 16,648〜16,672 µs | 26.9〜28.4 µs | 118〜170 µs |
| Todo（420 × 360） | 16,648〜16,659 µs | 28.3〜29.2 µs | 224〜247 µs |

- **ウィンドウ:** フレームの時間は、`Present` が画面のリフレッシュ（60 Hz）を待つ 16.6 ms でほぼ決まる
- **ヘッドレス:** `Present` は何もしない。28 µs は CPU が描く命令を積む時間で、WARP が描き終わるのは待たない
- **読み戻し:** フレーム全体をステージングのテクスチャに写し、WARP が描き終わるのを待ってから CPU に読む。だから WARP が描く時間を含み、画素の多い Todo（151,200 画素）のほうが Counter（64,000 画素）より長い。画素まで得るヘッドレスの 1 フレームは、0.15〜0.28 ms になる

## テストの時間

`XylemUI.Desktop.Tests` を、ブランチの基点（7abdbf6）とこのブランチで、交互に 3 回ずつ流した（`dotnet test --no-build`、Release）。

| 基点 | このブランチ |
| --- | --- |
| 8.8〜12.0 秒 | 8.6〜8.9 秒 |

- 本物のウィンドウで画素を読んでいた 3 つのテスト（Counter のボタンの中心、Todo のスクロールした行、スクロールで見える箱）を、ヘッドレスのアプリに移した。本物のウィンドウを開け閉めするテストは、メッセージ・閉じる・`XylemApp.Run` の 8 つになった
- 基点の 12.0 秒は 1 回目だけで、2 回目と 3 回目はこのブランチと重なる。差は測れなかったと読む

## ゴールデン

最初のゴールデンは `tests/XylemUI.Desktop.Tests/Goldens/` の 2 枚である。`XYLEMUI_UPDATE_GOLDENS=1` で書き、その後のふつうの実行で一致した。

- `counter.png`（320 × 200、1,681 バイト）
- `todo-scrolled.png`（420 × 360、7,271 バイト。10 項目を足して 64 だけスクロールした後）

CI の Windows のイメージの WARP の版が手元と違うと、文字の縁で ±2 を超える画素が出うる（設計書 §5.0.3）。合わなかったときは、CI が実際の画像と差の画像を成果物（`golden-failures-<attempt>`）に載せる。
