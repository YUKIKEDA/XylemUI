# KM2a: 既定のキーの載せ直し（Core）

K1 がコードに直書きしていた Tab・Esc・スクロールのキーを、既定のキーマップの行と Core の動作に載せ直した（ロードマップの行 KM2a、Issue #814、設計書 §7「既定のキーと動作」）。部品のキー（文字の欄、メニュー、Select、メニューバー）を動作にするのは、次の行 KM2b である。

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe input'    # キーの配送、Tab、スクロールのキー
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe keymap'   # 既定の行を作る時間と、キーマップの 3 つの場面
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe actions'  # 動作の配送
```

どれもウィンドウを開かない。

## 正しさ

- **既定の行と動作（`DefaultKeysTests`、6 件。`XylemUI.Testing.Tests`）:**
  - キーマップは Core の既定の 11 行（`tab`・`shift-tab`・`escape`・矢印 4 つ・`pageup`・`pagedown`・`home`・`end`）から始まり、どれも条件 `Window` を持つ。Tab と Shift+Tab はフォーカスを動かし、キーのハンドラには届かない。行を外すと、Tab はただのキーに戻る
  - ノードの文脈の行は、Core の既定の行に勝つ。フォーカスが、文脈を名乗るノードの子孫にあっても勝つ。文脈の無い行も勝つ。勝った行の動作が受けられなければ次の行を試し、動作の無い行は、既定の行の前でそこで終わる
  - Core の動作は、ノードの `OnAction` が先に受ける。受けて `Propagate()` したら、木が受ける。コードからの `Dispatch` でも木が受け、`CanDispatch` は真になる
  - 何も動かさない動作（端にいるスクロール、スクロールしない軸、ポップアップの無い Esc）は受けられず、キーはキーのハンドラへ進む。キーマップが取った Down の Up は、キーのハンドラへ届く
  - 木の動作に出すキー（`KeyBindingFor<FocusActions.Next>()`）は既定の行のもので、勝つ行が外すと無くなる
  - 既定の行を足すメソッドを 2 回登録しても、行は 1 回だけ入る
- **部品（`DefaultKeysPartsTests`、2 件。`XylemUI.Desktop.Tests`）:**
  - スクロールするページの中の文字の欄は、自分のキーを保つ。複数行の欄の上の矢印と Home、1 行の欄の Home と End はキャレットを動かし、ページは動かない。1 行の欄の下の矢印は欄のキーではないので、ページが 50 動く
  - スクロールするページの中のノードから開いたメニューは、矢印と Home と End でフォーカスを動かし、ページは動かない。Esc でメニューが閉じる
- **順が変わったことで書き直したテスト（`KeyFocusTests`、3 件。`XylemUI.Core.Tests`）:** キーのハンドラが Tab とスクロールのキーを止めても、キーマップが先に取るので、フォーカスは動き、箱はスクロールする。行を外すか、文脈の行で外すと、キーはキーのハンドラへ進む。定常状態のテストで、キーのハンドラが数える回数は、1 巡あたり 6 から 4 になった（Tab がハンドラに届かなくなった）。
- **Generator（`ActionTableGeneratorTests`、24 件。この行で新しく 6 件、書き直し 1 件）:** アプリのモジュール初期化子は、動作の表の後に、参照するアセンブリの既定の行を依存の順に登録する（Core、参照し合わないものは名前の順、参照するものは参照されるものの後、アプリ自身は最後）。ライブラリには書かない。`AddDefaults` が無い、静的でない、引数が違う、internal、クラスが internal の 5 つは、エラー XYLEM007 で、登録しない。
- **今あるテスト:** `XylemUI.Primitives.Tests` の 48 件と `XylemUI.Desktop.Tests` の 223 件（Select、メニュー、メニューバー、文字の欄のキーのテストを含む）は、部品の側のテストを変えずに通る。

MUTATION

## 計測

NativeAOT の Release（`win-x64`）。基準は KM1b のブランチ（`ea249ae`）で、KM2a は `869ee95`。論理プロセッサ 2 に固定し、優先度を High にして、同じ回の中で交互に流した（`input` は KM2a、基準、基準、KM2a を 4 巡で各 8 回。`keymap` と `actions` は各 4 回）。µs。値は各回の中央値の、中央値と範囲。計測の始めの CPU の負荷は 44 %、終わりは 100 % で、ほかのプロセス（`node`、`explorer`）が動いていた。固定していても長い回が混ざっているので、範囲が重ならない差だけを読む。

### キーの配送（`input`）

| | 基準（KM1b） | KM2a |
| --- | --- | --- |
| キー（A）、深さ 1 | 0.0624 [0.0565..0.1092] | 0.1274 [0.1164..0.1493] |
| キー（A）、深さ 50 | 1.920 [1.779..2.727] | 1.966 [1.827..3.079] |
| ボタンの Enter と Space のクリック | 0.1195 [0.1134..0.1971] | 0.1939 [0.1785..0.2291] |
| スクロールのキー | 0.0987 [0.0922..0.1077] | 0.2475 [0.2426..0.2866] |
| Tab（10,101 ノード） | 164.9 [161.7..228.8] | 174.9 [162.4..274.4] |
| 文字の欄の 1 文字の入力のうち、入力の処理 | 0.7 [0.6..2.4] | 0.7 [0.6..1.4] |
| 文字の欄の単語の移動のうち、入力の処理 | 21.3 [19.5..35.0] | 21.9 [20.1..22.5] |

- **どのキーも、約 0.065 µs（65 ns）長くなった。** 基準では、キーマップが空なので、キーの配送はキーマップを引かずに進んだ。今は、どのキーマップも既定の 40 行（Core の 11 行と Primitives の 29 行）を持つので、押下のたびに 40 行を端から見る（1 行あたり約 1.6 ns）。深さ 1 のキーとボタンのクリックの差（0.065 µs と 0.074 µs）がこれである。深さ 50 は範囲が重なり、差は読めない。
- **スクロールのキーは約 0.15 µs 長くなった。** 行に合ったキーは、根までの文脈を集め、動作を経路に配り（ハンドラは無い）、木が受けてスクロールする。基準は、キーの経路の途中で直にスクロールしていた。
- **Tab は範囲が重なる。** 1 回の Tab は 10,101 ノードの木をたどる 165 µs ほどで、照合と配送の分（1 µs 未満）は読めない。
- **文字の欄の入力は変わらない。** 文字になるキーは、欄にフォーカスがあるとキーマップを引かない（行 KM1b）。
- 合わないキーでは、文脈を集めない（最初の行がキーに合った時に集める）。行 KM1b の版は、行を見る前に集めていた。
- 行を最初のキーで引く索引は、入れていない。キーは 1 秒に多くて数十回で、1 回の 65 ns は、フレームの予算（§11.3）にも入力の遅延にも現れない。

- 200 行に合わないキーは、基準より短い。合わないキーで文脈を集めなくなったためである（上）。基準の側は長い回が多く（4 回のうち 2 回が 3.2 以上）、差の大きさは読めない。
- 割り当ては、3 つの場面とも 0 バイト。

## 覚えておくこと

- **リポジトリの全プロジェクトで Generator が動く。** 既定の行は、アプリのモジュール初期化子が登録する。テストとサンプルとベンチマークの実行ファイルも、それが無いと Tab とスクロールのキーが効かない。`Directory.Build.props` が、Generator のプロジェクトをアナライザとして全プロジェクト（Generator 自身、Core、Core が載るプロジェクトを除く）に足す。NuGet のパッケージでは、Core のパッケージが Generator を運ぶ。
- **Generator を使わないアプリ（C# でない言語など）には、既定の行が入らない。** 起動の時に `Keymap.RegisterDefaults(CoreKeyBindings.AddDefaults)` などを自分で呼ぶ必要がある。
- **部品の文脈は、ノードに 1 つである。** 部品は自分のノードに文脈を付ける（`TextField` など）。アプリが同じノードに `KeyContext(...)` を呼ぶと、部品の文脈が置き換わり、部品が外している既定の行が戻る。文脈を足す形にするかは、行 KM2b で部品の行を動作にする時に決める。
- **KM2b までの間、メニューの中の左右の矢印は、メニューが受けなくてもページを横にスクロールしない**（設計書 §7「KM2b までの部品」）。
