# P02f: Grid

行 P02f（設計書 §3.3「P02f で入れる形」）を、設計と 2 つの実装の PR に分けて入れる。Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で測った。

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
./benchmarks/compare/build.ps1 -Out <dir>
./benchmarks/compare/layout.ps1 -Built <dir> -Rounds 5
<dir>/xylemui/XylemUI.E2E.exe layout-loop grid width 20000   # プロファイル用（change も）
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe layout"
```

## 実装の 1 つ目の PR: トラックの大きさ・配置・`gap`・揃え（Issue #649）

main は 8464c13。場面は、4 列（`120px`・`auto`・`1fr`・`minmax(80px, 2fr)`）と auto の行 250 本のグリッドの各セルに、10 x 10 の葉を 1 つずつ置いたもの（1,001 ノード）で、2,000 x 2,000 で layout する。変更は、真ん中の行の `auto` の列の葉の内容の幅（10 と 20 を交互）で、`auto` の列を測り直す。幅の変更は、窓の幅（1,600 と 2,000 を交互）である。Taffy 0.15.1 は `taffy015` の名前で比べる場面だけが使い（`benchmarks/compare/taffy/src/grid.rs`）、Flex の場面は GPUI の版の 0.13.0 のまま比べる。Taffy 0.15.1 は出てから 13 日で、`dependencies.mdc` の 2 週間に 1 日足りないが、オーナーの指示で使った。Avalonia は `Grid`（列は `120`・`Auto`・`*`・`2*` で最小の幅 80）、Flutter は CSS の Grid が無いので `RenderTable`（`FixedColumnWidth(120)`・`IntrinsicColumnWidth()`・`FlexColumnWidth(1)`・`MaxColumnWidth(FixedColumnWidth(80), FlexColumnWidth(2))`）である。

### 4 つのフレームワーク

`layout.ps1` で 4 つを 5 ラウンド交互に流した（固定しない。ほかの場面と同じ）。ラウンドの中央値、括弧は最小〜最大（µs）。

| 値 | XylemUI | Taffy 0.15.1 | Avalonia | Flutter（`Table`） |
| --- | --- | --- | --- | --- |
| 最初の layout | 676（620〜1,115） | 613（516〜1,249） | 826（783〜1,074） | 86（79〜122） |
| 1 か所の変更 | 538（502〜965） | 469（422〜875） | 566（542〜703） | 70（65〜120） |
| 幅の変更 | 621（568〜1,232） | 459（413〜820） | 107（106〜115） | 65（62〜112） |

- XylemUI は Taffy より、最初の layout で 10 %、変更で 15 %、幅の変更で 35 % 長い。受け入れの「Taffy より遅くない」を満たしていない
- 1 回の pass で計算し直すノード（測定のキャッシュに無かったもの）は、変更で 757、幅の変更で 501 だった（`layout-loop grid` が出す）。どちらも大きさが変わる列の葉だけで、余計な計算は無い
- 幅の変更の CPU のプロファイル（Visual Studio のコレクター、NativeAOT、`layout-loop grid width 20000`、61,600 サンプル）: `ComputeGrid` が 99 %、そのうちトラックの大きさの計算が 48 %（1 本のトラックの子の経路が 40 %）、子の最終の layout（`PositionGridItem`）が 22 %、置き場所の決め直し（`RerunTrackSizing`）が 8 %、子の表を作る段が 7 %、配置が 6 %。トラックの大きさの計算の中身は、ほとんどが子の測定（`ContentContribution` から `LayoutChild` と測定のキャッシュ `MeasureCache.TryGet`・`Restamp`・`LayoutCacheKey`）である。Grid の手順そのものの自分の時間は小さい
- 子の状態から `LayoutStyle` の写しを外した（子ごとに 240 バイト）が、ループの時間は変わらなかった（同じ条件で 546〜601 µs と 539〜575 µs）。差は 1 回の測定の手間に散らばっている
- Avalonia 12.1.4 の `Grid` は、子を 1 回の pass で 1 度だけ測る。`Auto` の行の子は高さを無限、`*` の列の子は列の幅で測る（`Grid.cs` の `MeasureCell`、1132〜1160 行目）。CSS の Grid は、子の寄与を 3 種類（minimum・min-content・max-content）、列と行のそれぞれで測り、最後に子を layout する。幅の変更で Avalonia が短いのは、この測る回数の差による
- Flutter の `RenderTable` は、列の幅を `IntrinsicColumnWidth` の列だけ子の intrinsic で決め、ほかの列は子を測らずに決める。CSS の Grid のトラックの大きさの計算（§11.5 の子の寄与の 3 種類と 2 回の走り）を持たない

### main との比較

main（A）とこの PR（B）を、1 つのコアに固定して（`start /b /wait /affinity 4 /high`）、A・B・B・A・B・A・A・B の順に流した。値は各回の p50 の中央値と、範囲（µs、`frames --tree` は ms）。

| 値 | main | この PR |
| --- | --- | --- |
| s6b: 最初の layout | 6,479（4,739〜7,664） | 7,299（5,869〜7,701） |
| s6b: 1 か所の変更 | 31.0（22.3〜38.9） | 37.5（27.9〜41.4） |
| auto_min: 1 か所の変更 | 54.5（41.2〜70.0） | 61.3（44.0〜70.3） |
| percent: 1 か所の変更 | 55.9（43.0〜67.0） | 58.0（45.3〜74.0） |
| wrap: 1 か所の変更 | 4,958（3,724〜6,007） | 5,114（1,619〜6,435） |
| 絶対配置: 1 か所の変更 | 3.5（2.5〜4.2） | 3.2（2.4〜4.0） |
| `frames --tree`: layout の段 | 0.4（0.4〜0.5） | 0.4（0.4〜0.4） |
| `frames --tree`: CPU の 1 フレーム | 0.3（0.2〜0.3） | 0.2（0.2〜0.3） |

- どの値も main と PR の範囲が重なる。この回は 1 つのコアに固定した回のばらつきが大きく（s6b の最初の layout で main 自身が 4,739〜7,664）、Flex の場面の変更の中央値が 6〜20 % 長いのが、ノードが 16 バイト大きくなったこと（576 から 592 バイト）によるかは、この回の値からは言えない
- 固定した回は、同じ場面の固定しない回より一様に長かった（s6b で 1.36〜1.50 倍、Grid で 1.71〜1.78 倍）。main と PR は同じコアで比べたので、両者の比べには使える。4 つのフレームワークの比較は、ほかのフレームワークと同じく固定しない回の値を使った
- `XylemUI.E2E.exe` は 6,047,232 から 6,132,224 バイト（+84,992 バイト）。NativeAOT の publish に警告もエラーも無い
