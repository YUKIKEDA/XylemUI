# P02f: Grid

行 P02f（設計書 §3.3「P02f で入れる形」）を、設計と 2 つの実装の PR に分けて入れる。Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で測った。

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
./benchmarks/compare/build.ps1 -Out <dir>
./benchmarks/compare/layout.ps1 -Built <dir> -Rounds 5
<dir>/xylemui/XylemUI.E2E.exe layout-loop grid width 20000   # プロファイル用（change も）
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe layout"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe frames --tree"
```

## 実装の 1 つ目の PR: トラックの大きさ・配置・`gap`・揃え（Issue #649）

main は 8464c13。場面は、4 列（`120px`・`auto`・`1fr`・`minmax(80px, 2fr)`）と auto の行 250 本のグリッドの各セルに、10 x 10 の葉を 1 つずつ置いたもの（1,001 ノード）で、2,000 x 2,000 で layout する。変更は、真ん中の行の `auto` の列の葉の内容の幅（10 と 20 を交互）で、`auto` の列を測り直す。幅の変更は、窓の幅（1,600 と 2,000 を交互）である。Taffy 0.15.1 は `taffy015` の名前で比べる場面だけが使い（`benchmarks/compare/taffy/src/grid.rs`）、Flex の場面は GPUI の版の 0.13.0 のまま比べる。Taffy 0.15.1 は出てから 13 日で、`dependencies.mdc` の 2 週間に 1 日足りないが、オーナーの指示で使った。Avalonia は `Grid`（列は `120`・`Auto`・`*`・`2*` で最小の幅 80）、Flutter は CSS の Grid が無いので `RenderTable`（`FixedColumnWidth(120)`・`IntrinsicColumnWidth()`・`FlexColumnWidth(1)`・`MaxColumnWidth(FixedColumnWidth(80), FlexColumnWidth(2))`）である。

### 4 つのフレームワーク

`layout.ps1` で 4 つを 5 ラウンド交互に流した（固定しない。ほかの場面と同じ）。ラウンドの中央値、括弧は最小〜最大（µs）。

| 値 | XylemUI | Taffy 0.15.1 | Avalonia | Flutter（`Table`） |
| --- | --- | --- | --- | --- |
| 最初の layout | 676（620〜1,115） | 613（516〜1,249） | 826（783〜1,074） | 86（79〜122） |
| 1 か所の変更 | 538（502〜965） | 469（422〜875） | 566（542〜703） | 70（65〜120） |
| 幅の変更 | 621（568〜1,232） | 459（413〜820） | 107（106〜115） | 65（62〜112） |

- XylemUI は Taffy より、最初の layout で 10 %、変更で 15 %、幅の変更で 35 % 長い。受け入れの「Taffy より遅くない」を満たしていない。オーナーの決定で、この受け入れは実装の 2 つ目の PR に移した（行 P02f の受け入れは変えない）
- 1 回の pass で計算し直すノード（測定のキャッシュに無かったもの）は、変更で 757、幅の変更で 501 だった（`layout-loop grid` が出す）。どちらも大きさが変わる列の葉だけで、余計な計算は無い
- 幅の変更の CPU のプロファイル（Visual Studio のコレクター、NativeAOT、`layout-loop grid width 20000`、61,600 サンプル）: `ComputeGrid` が 99 %、そのうちトラックの大きさの計算が 48 %（1 本のトラックの子の経路が 40 %）、子の最終の layout（`PositionGridItem`）が 22 %、置き場所の決め直し（`RerunTrackSizing`）が 8 %、子の表を作る段が 7 %、配置が 6 %。トラックの大きさの計算の中身は、ほとんどが子の測定（`ContentContribution` から `LayoutChild` と測定のキャッシュ `MeasureCache.TryGet`・`Restamp`・`LayoutCacheKey`）である。Grid の手順そのものの自分の時間は小さい
- 子の状態から `LayoutStyle` の写しを外した（子ごとに 240 バイト）が、ループの時間は変わらなかった（同じ条件で 546〜601 µs と 539〜575 µs）。差は 1 回の測定の手間に散らばっている
- Avalonia 12.1.4 の `Grid` は、子を 1 回の pass で 1 度だけ測る。`Auto` の行の子は高さを無限、`*` の列の子は列の幅で測る（`Grid.cs` の `MeasureCell`、1132〜1160 行目）。CSS の Grid は、子の寄与を 3 種類（minimum・min-content・max-content）、列と行のそれぞれで測り、最後に子を layout する。幅の変更で Avalonia が短いのは、この測る回数の差による
- Flutter の `RenderTable` は、列の幅を `IntrinsicColumnWidth` の列だけ子の intrinsic で決め、ほかの列は子を測らずに決める。CSS の Grid のトラックの大きさの計算（§11.5 の子の寄与の 3 種類と 2 回の走り）を持たない

## 実装の 2 つ目の PR: `auto-fill`/`auto-fit`・名前付きの線・`dense`・絶対配置・速さ（Issue #657）

main は b97dec6。場面は 1 つ目の PR と同じである。この PR は、1 つ目の PR が満たさなかった「Taffy より遅くない」を満たす（オーナーの決定で移した）。

### 4 つのフレームワーク

`layout.ps1` で 4 つを 5 ラウンド交互に流した（固定しない）。ラウンドの中央値、括弧は最小〜最大（µs）。

| 値 | XylemUI | Taffy 0.15.1 | Avalonia | Flutter（`Table`） |
| --- | --- | --- | --- | --- |
| 最初の layout | 436（411〜468） | 516（433〜548） | 700（694〜905） | 78（76〜87） |
| 1 か所の変更 | 330（312〜344） | 399（378〜426） | 481（476〜873） | 65（64〜69） |
| 幅の変更 | 383（355〜393） | 382（370〜423） | 92（90〜138） | 60（59〜63） |

- 最初の layout と 1 か所の変更は、範囲が離れて Taffy より短い。幅の変更は、この 5 ラウンドでは中央値が並び、範囲が重なった
- 幅の変更を確かめるため、XylemUI と Taffy だけを交互に 15 ラウンド流した（同じ実行ファイル、固定しない）。XylemUI は 394（383〜401）、Taffy は 408（400〜417）で、XylemUI が短い。Taffy 自身の幅の変更の中央値は、回によって 382 から 416 まで動いた
- `layout` は、場面ごとに木を作り直す。木を作る割り当てが、測る区間に背景の GC を走らせる。同じ実行ファイルを concurrent GC を切って流すと、Grid の場面の 3 つの値はどれも約 8 % 短かった（`DOTNET_gcConcurrent=0`、2 回ずつ）。Taffy に GC は無い。測り方は他の場面と同じに保ち、この数字は使っていない
- Avalonia と Flutter との差の理由は、1 つ目の PR の節のとおりである（子を測る回数と、CSS の Grid のトラックの大きさの計算を持たないこと）

### 速さ: どこに時間があったか

1 つ目の PR は「時間は子の測定に散らばり、Grid の手順の自分の時間は小さい」と書いた。この PR で同じ幅の変更をプロファイルし直すと（Visual Studio のコレクター、NativeAOT、`layout-loop grid width 40000`、約 82,000 サンプル）、子の測定（`LayoutChild` 以下）は 22 % だった。残りの多くは、Grid の手順が子ごとに何度もスタイルを読み直す手間だった（`ContentContribution` の自分の時間 10 %、`PositionGridItem` 8 %、`KnownDimensions` 7 %、子の表を作る `GenerateGridItems` 6 %、`MinimumContribution`・`MarginSums`・`AvailableMinusMargins` などで計 10 % 余り）。

Taffy 0.15.1 の measure closure は、同じ場面で変更 1 回に 755 回、幅の変更 1 回に 500 回呼ばれた（数える版を作業用の場所で作って数えた）。XylemUI の layout の run は 757 回と 501 回で、子を計算し直す回数は同じである。差は、1 回ごとの Grid の手順の手間だった。

| 手を入れたこと | 幅の変更 | 1 か所の変更 |
| --- | --- | --- |
| 始め（この PR の機能を入れた後） | 485 | 505 |
| `PositionGridItem` の `LayoutStyle` の写しを外す（PR #650 のレビュー） | 504 | 523 |
| スタイルに大きさ・限り・余白・padding・枠が無い子（`IsBare`）は、寄与をスタイルを読まずに決める | 405 | 428 |
| その子の寄与を測る入力を 1 つ作って参照で渡し、最後の layout もスタイルを読まない | 372 | 395 |
| 線を持たない子は線を引かず、`IsBare` の子は余白と高さを読まない | 337 | 358 |
| 線も span も持つ子が無い時は、置き場所の見積もりと手順 1・2 を飛ばす | 316 | 341 |
| 線・自分の揃え・`overflow` も無い子（`IsPlainGridItem`）は、子の表を作る時にスタイルを読まない | 295 | 320 |

`layout-loop grid`（NativeAOT、固定しない、2 万回の平均を 3 回）の µs。写しを外すだけでは変わらなかった（1 つ目の PR と同じ）。流れの外の子の数（`OutOfFlowChildren`）で子のスタイルを読まずに数える変更も、値を変えなかった（Flex と同じ形にそろえた）。どの近道も、通常の経路と同じ結果を返す。この表の後に、揃えが伸ばさない子を fit-content の幅に決める変更（Chrome に合わせた）を入れたが、場面の子はすべて伸びるので、測る回数は増えない。最後の版は 312 と 338 だった（測る前の CPU の負荷 26 %）。
