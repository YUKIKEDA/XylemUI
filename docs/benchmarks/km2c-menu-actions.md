# KM2c: メニューの項目が動作を指す形

メニューの項目が動作を指せるようにした（ロードマップの行 KM2c、Issue #820、設計書 §7「メニューの項目が動作を指す形」）。項目は、メニューが開く前にフォーカスがあったノード（文脈のノード）から、キーの表示と「実行できるか」を読み、選ぶとそこから動作を配る。この記録は、正しさの確かめと、読み取りの費用の計測である。

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe menu'      # 項目の読み取りと、3 つのメニュー
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe input'     # キーの配送、Tab、スクロールのキー、文字の欄
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe menubar'   # keymap、select、actions、todo も同じ形
```

どれもウィンドウを開かない。`menu` に、メニューを 2 つ足した。どちらも、ラベルと欄の動作のキーを並べた項目が 10 個で、開く前に Todo の欄にフォーカスを置く。

- `written_*`: 項目は関数を呼ぶ今までの形で、キーの文字は書き込んである。
- `named_*`: 項目は動作を指し、キーをキーマップから引き、実行できるかを読む。
- `keys_read_*`・`can_read_*`: 欄にフォーカスを置いたまま、`KeyBindingFor(action)` と `CanDispatch(action)` を 1 回読む費用。フレームの外で測る。

## 正しさ

- **今あるテスト:** 欄と選択の領域のコンテキストメニューのテスト（`ContextMenuTests`）は、`MenuCommand` を渡す形から、動作を指す項目の形に書き直した。確かめる内容（使える条件、開く位置、選んだ後の動き）は同じである。ほかのテストは、変えずに通る。
- **ゴールデン画像:** Todo の欄のメニュー（`todo-menu.png`）を作り直した。項目の右にキー（Ctrl+X、Ctrl+C、Ctrl+V、Ctrl+A）が出る。有効・無効は前と同じ（空のクリップボードで、全部を選んでいない欄。「すべて選択」だけが有効）。
- **メニューの項目（`MenuActionItemTests`、10 件。`XylemUI.Desktop.Tests`）:**
  - メニューバーのメニューの項目は、バーを選ぶ前にフォーカスがあった欄から読む。コピーは有効で Ctrl+C、取り消しは履歴が無いので無効で Ctrl+Z、どこも受けない動作は無効でキー無し。選ぶと、メニューが閉じ、欄にフォーカスが戻り、欄がコピーする
  - コンテキストメニューは、フォーカスがメニューを付けたノードの外にあれば、そのノードから配る。中にあれば、フォーカスのノードから配る
  - サブメニューの項目は、外のメニューの文脈を持つ。押しても選べる。実行できない項目は、キーが飛ばす
  - 項目のキーは、メニューが開いている間も行の増減に付いていく。引数のある動作（`menubar::Open` の `Last`）は、引数が等しい行のキーを出す。キーは文脈のノードで引き、項目自身の文脈（`Menu`）の行は出さない
  - メニューの外で作った項目は、フォーカスから読む。メニューが開いている間に文脈のノードが消えたら、ルート関数が返したノードから読む。メニューを閉じた後に作った項目は、またフォーカスから読む
  - メニューが開いている間に、パネルの中の `Show` が作った項目は、メニューでもサブメニューでも、メニューの文脈のノードから読み、選ぶとそこから配る（PR #821 のレビュー）
  - メニューの中でフォーカスが動いても、項目は読み直さない。文脈が変わると、項目の数だけ読み直す
  - 欄は、取り消しとやり直しを履歴から答え、編集の後に読み直させる
  - 欄は、オプションで決まる動作（読み取り専用の編集、複数行だけの上下と改行、1 行で `OnSubmit` がある時だけの送信）を、受ける時と同じ条件で答える
  - 選択の領域は、コピー（選択がある）とすべて選択（文字がある）だけを答え、選択が変わると読み直させる
- **Core（`ActionAvailabilityTests`、10 件。`XylemUI.Testing.Tests`）:**
  - スクロールの 8 つの動作は、経路の箱がその向きへ動く時だけ実行できる。位置が変わると読み直す。型だけで聞く `CanDispatch<T>()` は、今までどおり真
  - 状態（`ScrollState`）の無い箱は、最初にスクロールした時に読み直させる。範囲が変わっても読み直す
  - フォーカスの移動は、一番上のフォーカスの範囲に移れるノードがある時、`popup::Dismiss` は閉じるポップアップがある時に実行できる。ノードが無効・フォーカス不可・非表示になると読み直す。フォーカスできるノードを後から木に付けても読み直す（PR #821 のレビュー）
  - 名前を付けた動作のキーは、引数が等しい行のもの。record でもクラスでも、Generator が生成した比較で比べる。名前の無い動作と、型だけの読みは、型の行のもの
  - ノードを指定した読みと配送は、そのノードから始まる。指定が無ければ、フォーカスから始まる。ノードが消えていれば、ルート関数が返したノードから始まり、今フォーカスがあるノードのハンドラには届かない
  - ノードを指定した読みは、フォーカスが動いても読み直さない
  - 部品の基底の型のハンドラは、動作ごとに受けられるかを答える。受けられない動作は、上のハンドラへ進む
- **Generator（`ActionTableGeneratorTests`。`XylemUI.Generators.Tests`）:** 引数のある動作の表は、引数を比べるメソッドと、その登録を持つ。引数の無い動作の表は持たない。読むだけのプロパティと、外から書けないプロパティは、表に出ない
- **ミューテーション:** 「実行できるか」の読み、Core の動作の答え、読み直しの知らせ、値で比べるキーの検索、ノードを指定した読み、文脈のノード、欄と選択の領域の答えに 85 個の変異を入れ、作業用の作業ツリーで関係するテストを流した。最初は 75 個を検出した。残りは、テストを足すか、コードを直して、85 個とも検出する。
  - スクロールの動きが 0 かの検査を消す: その後の比較と同じ結果になる余分な検査だった。検査を消した
  - 項目のキーの読みがフォーカスの知らせを読む: キーの読みと実行できるかの読みが、別々に同じ指定を書いていた。1 つの関数にまとめ、読み直さないことのテストが両方を守るようにした
  - 前面のポップアップの条件（閉じる途中のものと、ドラッグの絵は数えない）: Esc で閉じる処理と同じ条件を 2 か所に書いていた。1 つの関数にまとめ、閉じる途中のポップアップと、ドラッグ中の絵で「閉じるものは無い」と答えることのテストを足した
  - スクロールの範囲のシグナルを読まない: 内容を足すテストでは、木の変化の知らせで読み直されていた。ノードもハンドラも変えずに文字だけを増やすテストにした
  - 消えたノードを指定した読みの始まりを変える: フォーカスのノードが受ける動作と、ルート関数が返したノードが受ける動作で確かめる形にした（PR #819 のレビューで、消えたノードはフォーカスへ落とさない形に直した。直した後の 3 個の変異も検出する）
  - 欄の改行と送信の条件の片方を落とす: 複数行で読み取り専用の欄と、複数行で `OnSubmit` がある欄の場合を足した
  - 選択の領域が、文字の無い葉でもすべて選択に真を返す: 文字の無い葉の場合を足した
  - 項目のキーが、文脈の変化で読み直さない: メニューが開いている間に、文脈のノードの文脈を外して戻す確かめを足した
  - レビューの後に足したコード（引数の比較、Generator の出力、開いた後に作った項目がメニューを引く所、ノードを付けた時の知らせ）に、別に 9 個の変異を入れた。7 個を検出し、ノードを付けた時の知らせの 2 個が残った。テストの中では、ノードを作った時の別の知らせが先に効いていた。先に作っておいたノードを後から付けるテストにして、9 個とも検出する

## 計測

NativeAOT の Release（`win-x64`）。基準は main（`5d97e63`、KM2b）。論理プロセッサ 2 に固定し、優先度を High にした。基準・KM2c・KM2c・基準の順で繰り返し、同じ回の中で比べた。値は中央値で、角かっこは範囲。`input`・`todo`・`menu`・`menubar`・`select` は、レビューの後の `2db3658` を 16 回ずつ流した。`actions` と `keymap` は、その前の `8397521` と `44bf8ed` を 16〜24 回ずつ流した値で、その後の変更は、この 2 つの場面の経路に無い。CPU の負荷は、最初の回の前は 16〜17 %、`2db3658` の回の前は発行の直後で 29 % だった。単位は、断りが無ければ µs。

## 覚えておくこと

- **引数のある動作は、書くだけで値で比べられる。** Generator が、外から書き込める公開のプロパティを比べるコードを生成する。`IEquatable` を実装する必要は無い（最初は `IEquatable<IAction>` を見る形にしたが、record が実装するのは `IEquatable<自分の型>` なので、決め直した。PR #819 のレビュー）。
- **文脈のノードは、パネルを作る時に決まる。** メニューが開く時、フォーカスはまだ開く前のノードにある。選んだメニューバーのメニューでは、バーが覚えているノードである。サブメニューは、外のメニューのパネルの中で作られるので、その文脈を受け継ぐ。
- **開いたままの読み手がいるウィンドウで、ノードの付け外しが続くフレームは測っていない**（PR #821 の再レビュー）。ノードを付けた時と外した時の知らせは、「実行できるか」とキーの読み手を全部読み直させる。メニューの項目は開いている間しか読まないので、今の部品では表に出ない。ツールバーのボタンのように開いたままの読み手が 20 個あるウィンドウで、仮想化した一覧をスクロールすると、行が付け外しされるフレームごとに、キーを引く読みが 20 回走る（1 回 0.64 µs と 88 バイトなので、約 13 µs と 1.8 KB）。定常状態のフレームの割り当て 0（§11.3）に当たる。行 KM3 で測り、知らせを経路ごとに分けるかを決める。
- **フォーカスの移動で読み直す計算を増やさない。** フォーカスから読む計算（ツールバーのボタンなど）は、フォーカスが動くたびに読み直す。キーを引く読みは 1 回 0.58 µs と 88 バイトなので、数が多い所では、ノードを指定して読む。
- **ヘッドレスのテストは、フォーカスを移した後にフレームを回してからスクロールする。** 回さないと、フォーカスしたノードを見える所へ戻す処理が後から走り、スクロールの位置が戻る。
- **Tab の移動は、操作を受けない（inert の）ノードを飛ばさない。** 「移れるノードがあるか」の答えも、それに合わせている。
