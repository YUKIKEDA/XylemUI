# 容器が渡す文字のスタイル（行 TS1）

行 TS1 の実装の PR の計測です。設計書 §3.2「容器が渡す文字のスタイル」の「測ること」と、Issue #960 の「次」に従います。

## 条件

- 2026-11-28 04:11〜04:24、Windows 11 26300、i5-13400F、NativeAOT の Release（`benchmarks/XylemUI.E2E` を `win-x64` で発行）。
- main は `706457b`、ブランチは `816f8a1`（`feat/960-ts1` に main を取り込んだもの）。
- どの場面も窓を開かず、論理プロセッサ 2 に固定し、優先度を高にしました。
- 台本は手元の `.dev/ts1-measure.ps1` で、リポジトリには入れていません。各回の前に、CPU の負荷が 3 回続けて 25% 未満になるまで待ちました。記録した各回の前の負荷は 1〜22% です。
- `resize-text` は main とブランチを A B B A、B A A B、A B B A の順で 3 巡しました（各側 6 回）。TS1 の 2 つの場面は、ブランチで 3 回ずつ流しました。
- 下の時間は、各回の p50（`resize-text` は 51 回、TS1 の場面は 21 回の測った回から）の、回ごとの最小〜最大です。

## 1 万個の文字の葉の木のレイアウト（TS1 の前と後）

`resize-text` は、根の列の下に 100 行 × 100 個の文字の葉（短い日本語）がある 10,101 個のノードの木を、窓の大きさが変わった後に組み直します。容器の文字のスタイルは使いません。

| 値 | main | ブランチ |
| --- | --- | --- |
| 最初のレイアウト（折り返しあり） | 65.3〜74.2 ms | 61.3〜85.8 ms |
| 最初のレイアウト（1 行） | 51.5〜55.1 ms | 49.0〜52.4 ms |
| 大きさの変更、キャッシュに当たる（折り返しあり）の p50 | 1.99〜2.50 ms | 1.99〜2.70 ms |
| 大きさの変更、キャッシュに外れる（折り返しあり）の p50 | 10.26〜11.69 ms | 10.25〜11.06 ms |
| 大きさの変更、キャッシュに当たる（1 行）の p50 | 0.56〜0.78 ms | 0.53〜0.68 ms |
| ヒープ（木だけ） | 19,660,288 B | 19,660,296 B |
| ヒープ（折り返しの後） | 40,490,064〜40,508,040 B | 40,490,072〜40,508,048 B |
| ヒープ（1 行の後） | 36,085,320 B | 36,085,328 B |

時間は、どれも 2 つの側の範囲が重なっています。最初のレイアウト（折り返しあり）のブランチの 85.8 ms は、2 巡目の 1 回だけの値です。ブランチのほかの 5 回は 61.3〜68.5 ms でした。

ヒープは、3 つの値（木だけ、折り返しの後、1 行の後）のどれもブランチが 8 バイト多くなっています。折り返しの後の値は、両方の側で 2 つの値（差 17,976 B）のどちらかになります。これは TS1 より前からあるもので、同じ値どうしの差が 8 バイトです。8 バイトは、TS1 が `UiTree` に足した参照 1 つ（`_textStyles`）の分です。表（`TextStyleTables`）は、容器が文字のスタイルを持った時に初めて作ります。なので、容器のスタイルを使わない木が払うのは、この 8 バイトだけです。

ノードの大きさも変わっていません。
- `UiNode` は、`layout` の場面の `ui_node_bytes` で、main もブランチも 592 バイトです。TS1 の欄（印と葉の自分の欄）は、既存の詰め物の 1 バイトに入れました。
- `TextLeaf` は参照で持つクラスで、TS1 はその欄を変えていません。1 万個の葉の木でヒープの差が 8 バイトだけなので、葉の大きさも変わっていないとわかります。

## 容器の文字のスタイルを変えた時（`text-style`）

同じ木で、根の列に大きさ（次に太さ）を置く場合と、TS1 の前の唯一の方法である、10,000 個の葉の 1 つずつに同じ値を置く場合を比べます。それぞれ別の木を使い、毎回 2 つの値を交互に置きます。

| 値 | 容器に置く（TS1 の後） | 葉ごとに置く（TS1 の前の方法） |
| --- | --- | --- |
| 大きさ: setter の時間の p50 | 20.4〜22.1 ms | 20.8〜21.8 ms |
| 大きさ: その後のレイアウトの p50 | 54.0〜62.3 ms | 54.2〜60.1 ms |
| 太さ: setter の時間の p50 | 20.6 ms | 20.9〜21.0 ms |
| 太さ: その後のレイアウトの p50 | 53.0〜53.3 ms | 52.8〜53.2 ms |
| 印の付いた葉 | 10,000 | 10,000 |
| 解き直した葉 | 10,000 | 0 |
| setter の割り当て | 0 B | 0 B |

容器に 1 度置く形と、葉ごとに 10,000 回置く形の setter の時間は、範囲が重なりました。どちらの形も、変わった葉ごとに整形と改行のキャッシュを捨て、ノードに layout の印を付けます（設計書 §3.2「内容を書く」と同じ `SetTextStyle` の仕事）。容器の形は、それに加えて部分木を歩き、葉の効くスタイルを解きます。時間の内訳（どの仕事が何割か）は、プロファイルを取っていないので測っていません。値が同じなら、どちらの形も何もしません。

## Fluent のボタンがテーマの変更で書く 3 つの setter（`text-style-buttons`）

ボタンの形（箱の中の行の中の文字）を 1,000 個、列に並べます。各行に、`Fluent.Button` の Effect がテーマの変わった時に書く 3 つの setter（太さ、大きさ、行の高さ）を呼びます。

| 値 | 同じ値（色だけの変更） | 違う値（文字の形の変更） |
| --- | --- | --- |
| 3 つの setter の時間の p50（1,000 個） | 0.047〜0.048 ms | 0.53〜0.56 ms |
| 解き直した葉 | 0 | 3,000（ボタン 1 つに 3 回） |
| 印の付いた葉 | 0 | 1,000 |
| その後のレイアウトの p50 | — | 5.82〜6.19 ms |
| setter の割り当て | 0 B | 0 B |

**3 つの欄を 1 度に書く内部の口は足しません**（設計書 §3.2 が実装の PR に任せた判断で、この PR でエージェントが決めました）。3 回下っても、1,000 個で 0.53 ms です。1 度で書く口にして減らせるのは 3 回のうち多くて 2 回分（約 0.35 ms）で、変わった後のレイアウト（約 6 ms）を含むフレームの 6% ほどです。色だけが変わる時は、どこも歩きません。

## 実行ファイルの大きさ

`benchmarks/XylemUI.E2E` を NativeAOT で発行すると、8,119,296 B（main）から 8,153,088 B（ブランチ）になり、+33,792 B でした。ILC のマップ（`IlcGenerateMapFile`）の差は合わせて +31,961 B で、残りの 1,831 B は、節を 512 B の境界に丸めた分です。マップの差を、ノードの名前で次の 4 つに分けました（名前の分け方は、手元の `.dev/mapdiff.py`）。

| 分け方 | バイト | 中身 |
| --- | --- | --- |
| 計測の場面 | +13,656 | 名前が `XylemUI.E2E` のもの: `TextStyleCost` の 2 つの場面と、それを呼ぶ `Program.Main` の増分 |
| TS1 の Core のコード | +7,983 | `UiTree` の文字のスタイルのメソッド（`ResolveTextStyles`・`SetOwnTextStyle`・`SetHeldTextStyle`・`TextStyleGivenBy` など）、`InheritedTextStyle`、`ElementExtensions` の setter、木を変える所（`DetachChildren`・`DetachAfter`・`ReplaceChild`）の増分 |
| TS1 が足した総称の実体 | +7,331 | `Dictionary<NodeHandle, InheritedTextStyle>` と `Dictionary<NodeHandle, float>`、その `CollectionsMarshal` の補助、配列の型の情報 |
| 共有の表 | +2,991 | 凍った領域 1,552、メタデータ 831、スタックトレースの対応 366、総称の型の表 149 ほか。場面と src には分けていない |

Core のクロージャの番号が付け替わった分（`DisplayClass67_0` が `DisplayClass72_0` になるなど）は、足し引きで 0 です。アプリが TS1 のために払うのは、Core のコードと総称の実体（合わせて約 15.3 KB）と、共有の表の一部です。

## `Enum.IsDefined`

TS1 は、新しい setter と、src のほかの 5 か所の `Enum.IsDefined` を、範囲の確かめに替えました。最初の版の setter の割り当て 0 のテストで、`Enum.IsDefined` が割り当てていたためです。2026-11-28 に、使い捨ての NativeAOT のプログラム（`win-x64`、Release、.NET 10.0.15、`enum Slant : byte` の 3 つの値）で測り直しました。各回は 1,000 回の呼び出しです。

| 回 | `Enum.IsDefined` | 範囲の確かめ |
| --- | --- | --- |
| 1 回目（暖める前） | 6,096 B | 0 B |
| ブロッキングの GC の後 | 5,096 B（3 回とも） | 0 B |
| GC の無い 2 回目と 3 回目 | 5,096 B と 0 B | 0 B |

`Enum.IsDefined` は、ブロッキングの GC の後の最初の呼び出しで、毎回 5,096 B を割り当て直します。GC の無い回でも割り当てることがありました。範囲の確かめは、どの回も 0 B です。フレームの経路の setter は割り当てを 0 にするので（`.cursor/rules/perf.mdc`）、範囲の確かめを使います。
