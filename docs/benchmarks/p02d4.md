# P02d4: ポップアップのアンカーの Open

行 P02d4（設計書 §2.13、§7.3「アンカーの Open」）を 1 つの PR（Issue #590）で入れた。Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で、プロセスを 1 つのコアに固定して（`start /b /wait /affinity 4 /high`）測った。比べる main は、この PR の merge-base（978d612）を `.dev/` の worktree で publish した。値は各回の中央値（p50）の範囲である。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe menu"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe select"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe menubar"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe frames --tree"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe input"
```

## 流した組

- 1 組目は、main と PR を A・B・B・A の順で 2 回流した。回ごとに機械の状態が揺れ、`frames --tree` の CPU の 1 フレームは、main が 0.116〜0.726 ms、PR が 0.127〜0.198 ms に散った。比べられないので、2 組目を流した
- 2 組目は、逆の B・A・A・B の順で 2 回流した。8 回とも、描画の段が遅い状態（0.32〜0.37 ms）で走ったので、同じ状態どうしで比べられる。下の表は 2 組目の値である

## 結果

設計書 §7.3「アンカーの Open」は、開く・閉じるときに描き直すのは `Open` の見た目を持つアンカーだけで、見た目を持たないアンカーには何もしないとする。3 つの場面のアンカーは、どれも `Open` の見た目を持たない。この PR が開く・閉じる経路に足したのは、アンカーの疑似状態のビットを立てる・消すことと、閉じるときに同じアンカーに開いているほかのポップアップを探す 1 回のループ（開いているポップアップの数だけ回り、割り当てない）である。

| 値 | main | この PR |
| --- | --- | --- |
| `menu`: 開くフレームの変更の段 | 20.5〜29.4 µs | 21.1〜22.8 µs |
| `menu`: 開くフレームのレイアウトの段 | 57.6〜92.7 µs | 56.4〜62.0 µs |
| `menu`: 開いたまま Down で移るフレーム | 4.2〜4.7 µs | 4.3〜4.8 µs |
| `menu`: 移るフレームの割り当て（1,000 フレーム） | 0 バイト | 0 バイト |
| `select`: 開くフレーム | 79.9〜87.8 µs | 79.6〜88.8 µs |
| `select`: 開いたまま Down で移るフレーム | 4.8〜5.5 µs | 4.8〜5.6 µs |
| `select`: 移るフレームの割り当て（1,000 フレーム） | 0 バイト | 0 バイト |
| `menubar`: Down でメニューを開くフレーム | 261〜302 µs | 267〜275 µs |
| `menubar`: 選んだ状態で移るフレーム | 176〜196 µs | 176〜194 µs |
| `menubar`: 移るフレームの割り当て（1,000 フレーム） | 0 バイト | 0 バイト |
| `menubar`: 隣のメニューに移るフレーム | 276〜299 µs | 269〜294 µs |
| `menubar`: 隣のメニューに移るフレームの割り当て | 1 フレームあたり 37,424 バイト | 1 フレームあたり 37,504 バイト |
| `frames --tree` の CPU の 1 フレーム | 0.628〜0.715 ms | 0.647〜0.701 ms |
| キー 1 つの配送（深さ 50） | 1.67〜1.94 µs | 1.77〜1.89 µs |
| Tab（10,101 ノード） | 154.4〜171.8 µs | 159.4〜173.4 µs |

- 時間は、すべて main と重なる。割り当て 0 を求める移るフレームは、3 つの場面とも 0 バイトのままである
- 隣のメニューに移るフレームの割り当ては、1 フレームあたり 80 バイト増えた。2 組とも同じ値である。このフレームは、隣のメニューの中身を作り、10 個の項目それぞれが `.Focused(...)` の見た目を持つので、項目ごとに疑似状態の見た目のオブジェクト（`PseudoStyles`）を 1 つ作る。このオブジェクトは、`Open` の見た目への参照の分だけ 8 バイト大きくなった（`WindowInputTests.Sizes_NodeAndLooks_StayWithinTheirBounds` の上限を 336 から 344 バイトにした）。10 × 8 = 80 バイトである。`Open` の見た目そのものは別のオブジェクト（`OpenStyle`）に入れ、`.Open(...)` を付けたときだけ作る。最初の版は見た目を直接持ち、オブジェクトが 104 バイト大きくなって、上限のテストが落ちた
- `input` の文字の欄の変換の更新は、2 組目の p95 だけが PR の方が上に出た（main 144.3〜150.4 µs、この PR 152.1〜159.2 µs）。p50 は重なり（main 133.8〜134.9 µs、この PR 134.6〜147.6 µs）、1 組目では p95 も重なった（main 149.6〜290.9 µs、この PR 149.8〜178.3 µs）。この PR は文字の欄の経路に触れていない。2 組で結果がそろわないので、差として扱わない
