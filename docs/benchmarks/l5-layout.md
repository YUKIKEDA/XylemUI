# L5 のレイアウトの基準値

葉の内容が変わっても、親が読んだ値が変わらなければ親で止めるようにした（ロードマップの行 L5、Issue #110、設計書 §2.4.1「大きさが変わらなければ親で止める」）後の費用を、L4 と同じ方法で測った。

## 測った物と機械

- コミット: このファイルを加えたコミット（`git log -1 -- docs/benchmarks/l5-layout.md`）
- 機械と版と作り方: L1a と同じ（`docs/benchmarks/l1a-layout.md`）。場面は L4 と同じ 4 つ（`docs/benchmarks/l4-layout.md`）
- 新しい指標「内容の変更（大きさは同じ）」: 10,101 ノードの木の葉 1 つ（51 行目の 51 番目）の内容を、同じ大きさのまま変えて、次の pass を測る。XylemUI は `Invalidation.Invalidate(ChangeKind.TextContent)`、Flutter は葉の `markNeedsLayout`、Avalonia は葉の `InvalidateMeasure`。葉の内容は 10 x 10 に固定なので、どれも大きさが変わらない

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
./benchmarks/compare/build.ps1 -Out <dir>
```

- **内容の変更で動いた回数**: 葉のアルゴリズムか計測関数が動いた回数は、S6b の意味 2 回、CSS の既定と `%` あり 4 回、wrap 3 回。どれも変えた葉だけで、行と根は動かない。前回の入力での layout と内容の幅の求め直しが 1 回ずつで、残りは親が読んだ計測の項目の測り直し
- **Flutter が遅い理由**: Flutter の行は子を緩い制約で layout し、子の大きさを使う（`parentUsesSize`）ので、葉は relayout boundary でない。`markNeedsLayout` は行と根の列まで dirty にし（`markParentNeedsLayout`）、2 つの flex を解き直す。大きさを比べて止める仕組みは無い。wrap の場面では 1 万個の子を持つ `RenderWrap` を解き直すので 470 µs かかる
- **Avalonia**: `InvalidateMeasure` の後、`LayoutManager` が葉を前回の制約で測り直し、`DesiredSize` が同じなので親を無効にしない（`ChildDesiredSizeChanged` を呼ばない）。XylemUI は親が読んだ値（本番の layout の大きさ、計測の項目、内容の幅、ベースライン）を全部求め直すので、比べる値は Avalonia より多いが、10,101 ノードの木で 0.2〜0.3 µs だった
- **計測のキャッシュ**: 1 ノード 456 バイト（L4 と同じ）、10,101 ノードの木で 7.5 MB

**試して戻したもの**:

- 上書きした印（`MeasureCache.EvictedGeneration`）を、計測のキャッシュの項目の前のフィールドに置く: キャッシュが 1 ノード 456 から 464 バイトになり、S6b の意味の最初の layout が、main を先にした組と L5 を先にした組の両方で 7 % 遅くなった（3,213 → 3,424 µs、3,207 → 3,426 µs）。フラグの後の、構造体にもとからあった詰め物の位置に移すと 456 バイトに戻り、順番をそろえた組で main と範囲が重なった（3,194 → 3,070 µs）

## 内容の幅の関数を持たない葉

内容の幅の関数（`IntrinsicWidthsFunc`）を持たない葉は、列の中の行に置くだけで、最初の layout から 5 通り以上の入力で測られて、計測のキャッシュの 4 項目から溢れる（列が行を min-content と max-content で測り、行が葉をそれぞれの高さで測る）。溢れた葉は上書きした印を持つので、内容の変更は比べずに親へ伝わる（今の `MarkDirty` と同じ）。内容の幅の関数を持つ葉は、同じ木で 2 項目に収まり、親で止まる（`LayoutContentChangeTests`）。テキストの葉は T1 の後に内容の幅の関数を持つ（L4）。

## 受け入れ（設計書 §2.4.1、Issue #110）

- 内容の変更（大きさは同じ）で、動くのは変わった葉と読んだ値の求め直しだけ（親は動かない）: 満たす（上の「内容の変更で動いた回数」、`ContentChange_ThatKeepsEveryValueTheParentRead_StopsAtTheLeaf`）
- その時間が Avalonia と 5 ラウンド交互の中央値で同等か速い: 満たす（どの場面も 0.2〜0.3 µs、Avalonia は 0.8 µs）
- 大きさが変わる「1 か所の変更」が、L4 の値（S6b の意味 20.0 µs、CSS の既定 35.6 µs、`%` あり 38.0 µs）よりばらつきを超えて遅くならない: 満たす（20.2 / 34.3 / 37.3 µs。main と順番をそろえて測った 10 ラウンドでも範囲が重なる）
- 増分の結果と最初からの layout の結果が一致する、乱数のテスト: `LayoutRandomTests.IncrementalLayout_EqualsALayoutFromTheStart`（40 の種、各 30 回の変更）
- 上書きした印で伝わる場面のテスト: `ContentChange_AfterAnOverwrittenMeasurement_GoesOnToTheParent`
- 定常状態のアロケーション 0: `SteadyState_RelayoutAfterAContentChange_AllocatesNothing`（大きさが同じ変更と、変わる変更）
