# R3: 入力から表示まで（4 つのフレームワーク）

行 R3 の Grill で、R3 の受け入れを「Present から表示まで」から「入力から表示まで」に変えた（Present を遅らせるだけで短くなる値は、使う人には何も変えないため）。測り方は設計書 §11.3「Input-to-photon の測り方」（Issue #667）で、この記録はそのハーネス（Issue #673）で 4 つのフレームワークを測ったものである。

## 結果の要点

- **静止の画面でキーを押す（文字を打つ場面）:** XylemUI が最も短く、中央値 13.5〜15.3 ms（1 リフレッシュより短い）。Flutter 17.2〜28.7 ms、GPUI 25.3〜26.0 ms、Avalonia 26.9〜28.1 ms
- **アニメーション中にキーを押す:** XylemUI は中央値 26.3〜27.5 ms（約 1.6 リフレッシュ）で、GPUI（25.0〜26.1 ms）と並び、Flutter（17.0〜28.1 ms）より長い。Avalonia は 41.6〜42.5 ms
- **ウィンドウの角を別のウィンドウが覆っても、4 つとも値は変わらなかった。** XylemUI は覆われても MPO（`Hardware Composed: Independent Flip`）のままだった
- XylemUI のアニメーション中の 6 回のうち 1 回だけ、回の全体で 1 リフレッシュ長かった（中央値 43.5 ms）。理由は分かっていない（「送ったもの」）

どれも Windows 11 26300、NVIDIA GeForce RTX 3060 Ti、60 Hz のパネル（`\\.\DISPLAY1`、1 リフレッシュ 16.67 ms）、表示倍率 125 % で測った。XylemUI と Avalonia は NativeAOT、Flutter 3.47.7 は Windows のリリース、GPUI 0.2.2 は Rust のリリースで、どれも `benchmarks/compare/build.ps1` のビルドである（Avalonia 12.1.4）。

## 測り方

`benchmarks/compare/input.ps1` が、`XylemUI.E2E input-latency`（`benchmarks/XylemUI.E2E/InputLatency.cs`）を 4 つのフレームワーク × 4 つの場面で、ラウンドごとに交互に流した。3 ラウンドで、1 回の実行で 200 回押す。

- **アプリ:** M1a の比べる場面のアプリ（800 × 600、1,000 個の矩形と 1 行の日本語）。スペースのキーを押すたびに、左上の目印の矩形を #3366CC と #CC6633 で入れ替える。`--static` のアプリは、キーを押したときだけ描く
- **置き方:** アプリのウィンドウを、選んだモニタの上に置き、最前面にする。各実行の始めに 1 回、ウィンドウの左寄りの点を `SendInput` でクリックして前面にする。クリックの前に、その点のウィンドウがアプリのものかを確かめる
- **送る:** 毎回、送る直前に前面のウィンドウがアプリのものかを確かめてから、`SendInput` でスペースのキーを送る。間隔は 100 ms に 0〜16.7 ms の乱数を足す（待つ間のタイマーの分解能を `timeBeginPeriod(1)` で 1 ms にした。既定の 15.6 ms では乱数の分が丸められる）
- **読む:** 60 Hz のパネルの出力を Desktop Duplication で複製し、目印の画素が新しい色になった最初のデスクトップの画像の `LastPresentTime` までを、`SendInput` を呼ぶ直前の QPC から測る。パネルが画素を出すのは、その次のリフレッシュである
- **覆う場面（`--covered`）:** E2E 自身のアニメーションのアプリ（毎フレーム Present するフリップのウィンドウ）を最前面にし、アプリのウィンドウの右下の 4 分の 1 に重ねる。目印は覆わない
- **照らし合わせ:** 同じ回の PresentMon 2.6.0 で、アプリの表示方式（`PresentMode`）を数える

Avalonia は既定の合成（Windows.UI.Composition）のまま測った。利用者が使う形だからである。そのため PresentMon は Avalonia の Present を記録しない（M1a）。

## 読み方

- XylemUI の静止のアプリは、キーを受けたその処理の中で 1 フレームを要求し、描いて Present する（`External.App`）。静止の画面の表示方式は、PresentMon が記録しなかったので読めなかった（次の節）。GPUI は静止でも `Composed: Flip` で、GPUI と Avalonia は静止でも 1.5 リフレッシュを超える
- XylemUI のアニメーション中は、静止より約 12 ms（0.7 リフレッシュ）長い。アニメーション中のアプリは、スワップチェーンの待機オブジェクトが鳴るたびに描き、キーで変えた色は、キーの後に始まる次の描画で入る。押す時刻はリフレッシュの中に均等に散らしたので、その待ちは平均で半リフレッシュ（8.3 ms）になるはずで、残りの約 4 ms は調べていない（「送ったもの」）。R3 の Grill の Q2 の「遅く描き始める」は、この待ちを縮める手である
- Flutter は回ごとのばらつきが大きい（静止の中央値 17.2〜28.7 ms、アニメーション中 17.0〜28.1 ms）。アニメーション中の覆わない 1 回目は、PresentMon の記録が無かった。ばらつきの理由は調べていない
- 覆う場面で値が変わらなかったのは、角を覆われても DWM が XylemUI のウィンドウを MPO で出し続けたためである。`docs/benchmarks/r3-latency.md` で合成になったのは、同じ大きさのウィンドウが真上に重なり、下のウィンドウが丸ごと隠れたときだった。丸ごと隠れたウィンドウは使う人に見えない

## PresentMon の入力の列は使えなかった

設計書 §11.3 は、PresentMon の入力から表示までの列（`MsAllInputToPhotonLatency`、`MsClickToPhotonLatency`）で照らし合わせるとした。管理者でない PresentMon 2.6.0 では、どの回もこの 2 つの列が NA だった（XylemUI のアニメーション中の回で、538 行すべて）。`SendInput` で注入したキーは記録されない。表示方式（`PresentMode`）の記録には使えた。

また、静止の場面では、PresentMon は XylemUI・Flutter・Avalonia のどれの Present も記録しなかった（ファイルを書かなかった）。GPUI だけ、6〜16 行を記録した。キーを押した時にしか Present しないアプリの表示方式は、この方法では読めない。

## 送ったもの

- **XylemUI のアニメーション中の 1 回（中央値 43.5 ms）:** 6 回のうち 3 ラウンド目の覆わない回で、200 回の分布の全体が約 1 リフレッシュ（16.7 ms）長かった（p99 52.0 ms、最大 52.2 ms）。表示方式はほかの回と同じく MPO だけだった。`r3-latency.md` の (4)（`external` の XylemUI のアプリで、14 回のうち 1 回、表示まで 66.0 ms のまま続いた）と同じく、回の全体で表示を待つ列が 1 つ深いままに見える。行 R3 で調べる
- **アニメーション中の待ちの内訳:** 静止との差の約 12 ms のうち、次の描画を待つ平均の半リフレッシュ（8.3 ms）を超える約 4 ms。キーの受け取りから描き始め、Present、表示までを分けて測る
- **試作を続けるか:** R3 の Grill の Q2 の試作（遅く描き始める、tearing、Composition Swapchain）を続けるかは、この結果を持った Grill で決める

## 再現

```powershell
./benchmarks/compare/build.ps1 -Out <dir>
./benchmarks/compare/input.ps1 -Built <dir> -PresentMon <PresentMon-2.6.0-x64.exe> -Rounds 3 -Presses 200
```

`<dir>/input.jsonl` に 1 回ごとに 1 行が入る。1 回が約 1 分で、48 回で約 50 分かかる。測る間は PC を使わない。使うと前面のウィンドウが変わり、ハーネスはキーを送らずに止まる。
