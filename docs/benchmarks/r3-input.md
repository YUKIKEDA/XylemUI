# R3: 入力から表示まで（4 つのフレームワーク）

行 R3 の Grill で、R3 の受け入れを「Present から表示まで」から「入力から表示まで」に変えた（Present を遅らせるだけで短くなる値は、使う人には何も変えないため）。測り方は設計書 §11.3「Input-to-photon の測り方」（Issue #667）で、この記録はそのハーネス（Issue #673）で 4 つのフレームワークを測ったものである。

## 結果の要点

- **静止の画面でキーを押す（文字を打つ場面）:** XylemUI が最も短く、中央値 13.5〜15.0 ms（0.81〜0.90 リフレッシュ）。Flutter 17.2〜28.9 ms、GPUI 25.5〜25.7 ms、Avalonia 26.5〜28.1 ms
- **アニメーション中にキーを押す:** 覆われていないとき、XylemUI は中央値 26.3〜26.8 ms（約 1.6 リフレッシュ）で、GPUI（25.1〜26.1 ms）と並び、Flutter（17.9〜28.1 ms）より長い。Avalonia は 41.6〜42.9 ms
- **別のウィンドウが角を覆うと、XylemUI のアニメーション中だけが長くなった。** 中央値 29.4〜30.9 ms、p95 45.3〜49.2 ms（覆われていないときは 34.0 ms）。表示方式は MPO（`Hardware Composed: Independent Flip`）のままだった。ほかの 3 つと、XylemUI の静止は、覆われても範囲が重なった
- XylemUI のアニメーション中の覆われていない 3 回のうち 1 回だけ、回の全体で 1 リフレッシュ長かった（中央値 43.5 ms）。理由は分かっていない（「送ったもの」）

どれも Windows 11 26300、NVIDIA GeForce RTX 3060 Ti、60 Hz のパネル（`\\.\DISPLAY1`、1 リフレッシュ 16.67 ms）、表示倍率 125 % で測った。XylemUI と Avalonia は NativeAOT、Flutter 3.47.7 は Windows のリリース、GPUI 0.2.2 は Rust のリリースで、どれも `benchmarks/compare/build.ps1` のビルドである（Avalonia 12.1.4）。

## 測り方

`benchmarks/compare/input.ps1` が、`XylemUI.E2E input-latency`（`benchmarks/XylemUI.E2E/InputLatency.cs`）を 4 つのフレームワーク × 4 つの場面で、ラウンドごとに交互に流す。3 ラウンドで、1 回の実行で 200 回押す。

- **アプリ:** M1a の比べる場面のアプリ（800 × 600、1,000 個の矩形と 1 行の日本語）。スペースのキーを押すたびに、左上の目印の矩形を #3366CC と #CC6633 で入れ替える。`--static` のアプリは、キーを押したときだけ描く
- **置き方:** アプリのウィンドウを、選んだモニタの上に置き、最前面にする。各実行の始めに 1 回、ウィンドウの左寄りの点を `SendInput` でクリックして前面にする。クリックの前に、その点のウィンドウがアプリのものかを確かめる
- **送る:** 毎回、送る直前に前面のウィンドウがアプリのものかを確かめてから、`SendInput` でスペースのキーを送る。間隔は 100 ms に 0〜16.7 ms の乱数を足す（待つ間のタイマーの分解能を `timeBeginPeriod(1)` で 1 ms にした。既定の 15.6 ms では乱数の分が丸められる）
- **読む:** 60 Hz のパネルの出力を Desktop Duplication で複製し、目印の画素が新しい色になった最初のデスクトップの画像の `LastPresentTime` までを、`SendInput` を呼ぶ直前の QPC から測る。パネルが画素を出すのは、その次のリフレッシュである
- **覆う場面（`--covered`）:** E2E 自身のアニメーションのアプリ（毎フレーム Present するフリップのウィンドウ）を最前面にし、アプリのウィンドウの右下の 4 分の 1 に重ねる。目印は覆わない。アプリをクリックして前面にすると、アプリは最前面のウィンドウの中でいちばん上に上がるので、その後に覆うウィンドウを上げ直し、覆うウィンドウの真ん中の点のウィンドウが覆うウィンドウであることを確かめる
- **照らし合わせ:** 同じ回の PresentMon 2.6.0 で、アプリの表示方式（`PresentMode`）を数える

Avalonia は既定の合成（Windows.UI.Composition）のまま測った。利用者が使う形だからである。そのため PresentMon は Avalonia の Present を記録しない（M1a）。

覆われていない場面と覆う場面は、別の時に測った。最初の測定では、覆うウィンドウがアプリの下に回っていて（上の「覆う場面」の上げ直しが無かった）、実際には覆っていなかった。PR #674 のレビューの確かめの中で分かり、覆う場面だけを測り直した。下の表の覆う場面の値は、測り直したものである。

## 読み方

- XylemUI の静止のアプリは、キーを受けたその処理の中で 1 フレームを要求し、描いて Present する（`External.App`）。GPUI は静止でも `Composed: Flip` で、GPUI と Avalonia は静止でも 1.5 リフレッシュを超える
- XylemUI のアニメーション中は、静止より約 12 ms（0.7 リフレッシュ）長い。アニメーション中のアプリは、スワップチェーンの待機オブジェクトが鳴るたびに描き、キーで変えた色は、キーの後に始まる次の描画で入る。押す時刻はリフレッシュの中に均等に散らしたので、その待ちは平均で半リフレッシュ（8.3 ms）になるはずで、残りの約 4 ms は調べていない（「送ったもの」）。R3 の Grill の Q2 の「遅く描き始める」は、この待ちを縮める手である
- 覆われた XylemUI のアニメーション中は、中央値が 3〜4 ms、p95 が 11〜15 ms 長くなった。表示方式は覆われていないときと同じく MPO だけだったので、合成に落ちたためではない。理由は調べていない（「送ったもの」）。覆われた XylemUI の静止は、範囲が覆われていないときと重なった
- Flutter は回ごとのばらつきが大きい（静止の中央値 17.2〜28.9 ms、アニメーション中 17.9〜28.1 ms）。ばらつきの理由は調べていない
- `docs/benchmarks/r3-latency.md` で合成（`Composed: Flip`）になったのは、同じ大きさのウィンドウが真上に重なり、下のウィンドウが丸ごと隠れたときだった。角を覆われただけでは、XylemUI は MPO のままだった

## PresentMon の入力の列は使えなかった

設計書 §11.3 は、PresentMon の入力から表示までの列（`MsAllInputToPhotonLatency`、`MsClickToPhotonLatency`）で照らし合わせるとした。管理者でない PresentMon 2.6.0 では、どの回もこの 2 つの列が NA だった（XylemUI のアニメーション中の回で、538 行すべて）。`SendInput` で注入したキーは記録されない。表示方式（`PresentMode`）の記録には使えた。

静止の場面では、PresentMon は多くの回でアプリの Present を記録しなかった（ファイルを書かなかった）。最初の測定（覆われていない回と、覆えていなかった覆う回の 6 回ずつ）で記録したのは、GPUI の 5 回（6〜16 行、`Composed: Flip`）だけだった。測り直した覆う場面の 3 回ずつでは、GPUI の 3 回（63〜339 行、`Composed: Flip`）、XylemUI の 1 回（69 行、`Composed: Flip`）、Flutter の 1 回（78 行、`Composed: Copy with GPU GDI`）が記録した。キーを押した時にしか Present しないアプリの表示方式は、この方法では確かには読めない。

## 送ったもの

- **XylemUI のアニメーション中の 1 回（中央値 43.5 ms）:** 覆われていない 3 回のうち 3 ラウンド目の回で、200 回の分布の全体が約 1 リフレッシュ（16.7 ms）長かった（p99 52.0 ms、最大 52.2 ms）。表示方式はほかの回と同じく MPO だけだった。`r3-latency.md` の (4)（`external` の XylemUI のアプリで、14 回のうち 1 回、表示まで 66.0 ms のまま続いた）と同じく、回の全体で表示を待つ列が 1 つ深いままに見える。設計書 §2.11「待たずに出した Present」（Issue #675）の直しの PR で、タイムアウトで回したフレームの数と、待たずに出した Present の数を数えて確かめる
- **覆われた XylemUI のアニメーション中:** 中央値が 3〜4 ms、p95 が 11〜15 ms 長い理由
- **アニメーション中の待ちの内訳:** 静止との差の約 12 ms のうち、次の描画を待つ平均の半リフレッシュ（8.3 ms）を超える約 4 ms。キーの受け取りから描き始め、Present、表示までを分けて測る
- **試作を続けるか:** R3 の Grill の Q2 の試作（遅く描き始める、tearing、Composition Swapchain）を続けるかは、この結果を持った Grill で決める

## 再現

```powershell
./benchmarks/compare/build.ps1 -Out <dir>
./benchmarks/compare/input.ps1 -Built <dir> -PresentMon <PresentMon-2.6.0-x64.exe> -Rounds 3 -Presses 200
```

`<dir>/input.jsonl` に 1 回ごとに 1 行が入る。1 回が約 1 分で、48 回で約 50 分かかる。測る間は PC を使わない。使うと前面のウィンドウが変わり、ハーネスはキーを送らずに止まる。
