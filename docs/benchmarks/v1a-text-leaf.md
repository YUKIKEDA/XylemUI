# V1a: 文字の葉

文字の葉を足した（ロードマップの行 V1 の V1a、Issue #300、設計書 §3.2「文字の葉」と §2.4.1「layout 中の例外」）。文字の葉は、T1 の整形と折り返しで自分を測り、2 段のキャッシュを持つ。その正しさと費用を確かめた。どれも Windows 11 26300、Intel Core i5-13400F で、時間は NativeAOT の Release で測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe resize-text 101
<dir>/XylemUI.E2E.exe segment
<dir>/XylemUI.E2E.exe layout
```

`resize-text` は、§11.3 の 10,101 ノードの木（列 1 → 行 100 → 文字の葉 100）を、Windows のフォント（`DirectWriteFontProvider`）で 14 px の「日本語のテキスト」の葉にして測る。場面は 2 つある。

- **折り返す葉:** 葉は CSS の既定どおり行に合わせて縮む。幅 1,600 px では葉 1 つが 16 px、1,200 px では最小の内容の幅の 14 px になり、どちらも 1 文字ずつ 8 行に折り返す
- **1 行の葉:** 葉は縮まず（`FlexShrink = 0`）、最大の内容の幅の 1 行のまま。M1a の計測関数の葉（幅を覚えた葉、2.0〜2.3 ms）と同じ形である

キャッシュが当たる場合は、幅 1,600 px と 1,200 px を交互に layout する。外れる場合は、layout のたびに幅を 1 px ずつ変え、どの葉も新しい幅で折り返す（4 つの項目を使い回す）。

## 正しさ（`TextLeafTests`・`FontTests`・`LayoutWorklistTests`）

期待値は fontTools で読んだ値から求めた。テストのフォントは ascent 1160、descent 288、lineGap 0（hhea、1,000 units per em）、同梱のフォントは 1069、293、0（OS/2 の typo。USE_TYPO_METRICS がある）。20 px のテストのフォントの 1 行は 23.2 + 5.76 = 28.96 px になる。

- **フォントの値:** HarfBuzz の `hb_font_get_h_extents` から読んだ値が、2 つのフォントとも fontTools の値と一致した
- **1 行:** 葉は 24.4 × 28.96 px（「nn」、610 × 2 / 1000 × 20）で、最初のベースラインは 23.2 px
- **折り返し:** 「nn nn」を幅 30 px で 2 行（57.92 px）。最初のベースラインは最初の行のもの
- **2 つのフォントの行:** 「#」を同梱のフォントに回した「n#」は、ascent と descent のそれぞれの最大で 29.06 px
- **行の高さの倍率:** 倍率 2 で 40 px、ベースラインは (40 − 28.96) / 2 + 23.2 = 28.72 px
- **空の内容と空の行:** 空の葉は幅 0、高さ 1 行で、整形の結果を持たない。「n\n\nn」は 3 行
- **内容を書く:** 同じ内容と同じスタイルは dirty にしない。違う内容と違うスタイルは、キャッシュを捨てて dirty にする
- **内容の幅:** 行（flex）の中で、広い窓では最大の内容の幅（53.28 px）の 1 行、狭い窓では最小の内容の幅（24.4 px）の 2 行。Debug のビルドは、内容の幅と計測の一致も確かめる
- **確定した幅:** 確定した項目は、ほかの幅を 8 回取っても上書きされない
- **範囲の外の値:** 大きさ 0・NaN・∞、行の高さの倍率 0・∞ は `ArgumentOutOfRangeException`。`TextContext` の無い木と、文字の葉でないノードへの `SetText` は `InvalidOperationException`
- **例外の報告:** 投げ続ける葉は、1 回目だけを報告し、その後の 2 回を数えた。dirty のままの葉のスタイルの変更と `MarkDirty` で、それぞれ 1 回ずつまた報告した。型が変わると、また報告した
- **割り当て:** 100 個の文字の葉を、当たる 2 つの幅で交互に layout するときと、6 つの幅を回して項目を上書きし続けるときは、どちらも 0 バイトだった（項目が初めて行の多い幅を受け持つときに配列を広げるので、測る手順を 1 回流してから測った）
- **葉 1 つのメモリ:** 「日本語のテキスト」の葉（n = g = b = 8、r = L = e = 1）を 1 つ足して初めて layout すると、1,528 バイトだった（Release）。そのうち、葉のオブジェクトが 88、内容のバッファが 40 バイトである。§3.2 の式の値 656 バイトに頭（配列 14 個 × 32、オブジェクト 7 個 × 64）を足した上限 1,552 バイトの内側にある

## 費用

### リサイズ（`resize-text`、101 回、3 回の中央値の範囲）

| 場面 | キャッシュが当たったとき（中央値 / p95） | 外れたとき（中央値 / p95） | 最初の layout |
| --- | --- | --- | --- |
| 折り返す葉 | 1.78〜1.88 / 3.07〜3.16 ms | 10.06〜10.30 / 12.31〜14.72 ms | 65.6〜68.2 ms |
| 1 行の葉 | 0.55〜0.68 / 0.66〜1.08 ms | — | 53.4〜63.2 ms |

- **受け入れ:** キャッシュが当たったときの中央値は、この 3 回ではどちらの場面も 2.0 ms 以下だった。ただし、折り返す葉は実行ごとのばらつきが大きく、別の 2 回では 1.93 ms と 2.38〜2.46 ms だった。測っている間、ほかのプロセス（ほかのセッションとエディタ）が CPU の約 25 % を使っていた
- **M1a との比較:** M1a の計測関数の葉（幅を覚えた葉）は 2.0〜2.3 ms だった。1 行の葉はそれより速い。M1a の葉は内容の幅の関数を持たず、行が max-content を尋ねるたびに計測のキャッシュを通った。文字の葉は内容の幅を返すので、その問い合わせで計測を呼ばない。差がこれによるかは、プロファイルで確かめていない
- **p95 の尾:** 折り返す葉の p95 は 3 ms を超えた。交互に使う 2 つの幅を分けて集めると、どちらも同じ分布だった（中央値 1.93 と 1.93 ms、p95 3.25 と 3.24 ms）。プロセスを 1 つの E コアに固定すると中央値 3.58 ms で、P コア（論理 CPU 2）に固定したとき（1.80 ms）の約 2 倍だった。P コアに固定しても、p95 は 2.90 ms で残った。割り当ては 0 バイトで、GC は起きない。尾は、葉の処理ではなく、実行するコアの違い（P と E）と、同じ物理コアをほかのプロセスと分け合うことによると推定する
- **当たったときの内訳（CPU のプロファイル、Visual Studio のコレクタと xperf、当たる場面だけを 3,000 回）:** 標本のうち、`MeasureText` が 15.3 %、`Shape`（整形の結果が有効かを見る）が 7.0 %、葉の確定（`ComputeLeaf` 6.7 %、`Compute` 8.7 %、`Restamp` 6.3 %、`OnRectChanged` 3.9 %）、行の flex（`GenerateFlexItems` 9.9 %、`ComputeFlex` 8.5 %）だった（関数ごとの自分の時間）。折り返す葉は、リサイズのたびに幅が変わり、すべての葉が確定し直される。1 行の葉は幅が変わらないので、確定し直さない
- **幅の鍵と大きさを `LineBreakCache` の中に並べた:** 幅を項目に持つと、幅を引く `TryGet` だけで 9.8 % になった。1 万の葉の項目がヒープに散らばり、読むたびにキャッシュに乗らないためである。幅を中に並べた版（B）と、大きさとベースラインも中に並べた版（C）を、先に流す版を入れ替えながら交互に 4 巡測った。折り返す葉で当たったときは、B が 1.89〜2.66 ms、C が 1.66〜1.92 ms だった。C を採った
- **外れたとき:** 1 万の葉をすべて新しい幅で折り返して行を並べる。葉 1 つが 8 行で、layout の費用も含めて葉 1 つあたり約 1 µs かかる。幅が変わり続けるリサイズ（ウィンドウの縁を引く間）は、毎フレーム外れる。§11.3 の予算（120 Hz で 2.0 ms）には収まらない
- **最初の layout:** 1 万の葉をそれぞれ DirectWrite でフォントの run に分け、HarfBuzz で整形する。葉 1 つが約 5〜6 µs である

### メモリ（`resize-text`、管理ヒープ）

| 木 | 管理ヒープ | 文字の葉の分（葉 1 つ） |
| --- | --- | --- |
| 文字の葉でない葉（1 つの計測関数） | 18.4 MB | — |
| 1 行の葉 | 33.6 MB | 15.2 MB（1,507 バイト） |
| 折り返す葉 | 38.0 MB | 19.6 MB（1,946 バイト） |

- 文字の葉の分は、同じ木の、文字の葉でない葉の木との差である。ノードのアリーナと計測のキャッシュは、どちらの木にもある
- 1 行の葉は、テストで測った葉 1 つ（テストのフォント）の 1,528 バイトとほぼ同じだった
- 折り返す葉は、+∞ の幅の 1 行の項目のほかに、16 px の幅の 8 行の項目を持つ。§3.2 の式では 8 行の項目が 64 × 8 + 24 × 8 = 704 バイトで、差の 439 バイトとおおよそ合う（足りない分は、行の配列が広がった後の余り）
- 1 万の日本語テキストノードのメモリを Flutter・Avalonia・GPUI と比べるのは、行 M1b である

### 整形と折り返し（`segment`、main と交互に 4 巡、中央値の範囲）

T1b のレビュー（PR #293）で、日本語の画面の折り返しの時間を、改行の候補と同じ表に入れると約束した。V1a で `ShapingResult` の配列の初めの大きさと作業用の配列の置き場所を変えたので、main（bb7339c）と交互に測った。

| 文 | 改行の候補（ns/文字） | 整形（1 回） | 折り返し（Pass1） | 行を並べる（Pass2） | 幅を変えて折り返し直し |
| --- | --- | --- | --- | --- | --- |
| 日本語 main | 27.5〜67.0 | 272.2〜314.0 µs | 18.3〜19.4 µs | 14.5〜15.6 µs | 18.6〜19.2 µs |
| 日本語 V1a | 27.1〜40.1 | 260.5〜543.4 µs | 18.7〜36.2 µs | 14.9〜25.5 µs | 18.6〜40.3 µs |
| 英文 main | 20.4〜22.3 | 248.1〜269.2 µs | 5.2〜5.5 µs | 14.0〜14.5 µs | 4.7〜4.9 µs |
| 英文 V1a | 20.6〜38.7 | 228.2〜424.1 µs | 5.2〜11.5 µs | 14.1〜23.1 µs | 4.7〜5.3 µs |

- 範囲はすべて重なった。V1a の範囲の上の端は 1 巡だけのもので、その巡では、V1a が変えていない書記素の列挙も 2 倍（日本語 6.9 → 14.4 ns/文字）になった。機械のほかの負荷である
- 最も小さい値どうしは、日本語の折り返しで 18.3 と 18.7 µs、行を並べる処理で 14.5 と 14.9 µs だった
- L1a の layout の場面（`layout`、同じ 4 巡）も、指標の範囲がすべて重なった（たとえば 1 か所の変更で、S6b 21.1〜37.7 と 21.0〜38.3 µs、wrap の幅の変更 1,238.7〜3,898.2 と 1,255.6〜2,868.1 µs）

### 絵文字の run の数ごとの整形（`segment`、1 回）

T1b のレビュー（PR #293）で約束した測定である。同じ英文の画面（3,200 文字）に、64 語・16 語・4 語・1 語ごとに絵文字を 1 つ入れた。

| 絵文字 | run の数 | フォントの run への分割（DirectWrite） | 整形（`ShapingResult.Shape`） |
| --- | --- | --- | --- |
| なし | 1 | 45.8 µs | 203.9 µs |
| 64 語ごと | 25 | 120.9 µs | 219.0 µs |
| 16 語ごと | 95 | 379.8 µs | 250.7 µs |
| 4 語ごと | 337 | 1,307.6 µs | 326.8 µs |
| 1 語ごと | 917 | 3,620.1 µs | 479.0 µs |

- 整形は、run が 1 つ増えるごとに約 0.3 µs 増えた（917 run で 275 µs 増）。run ごとに HarfBuzz を 1 回呼ぶ費用である
- フォントの run への分割は、run 1 つで約 3.9 µs 増えた。DirectWrite の `MapCharacters` を範囲ごとに呼ぶ費用で、整形の約 13 倍である。絵文字の多い文の費用の大半は、`ShapingResult` ではなく、フォントの選び方にある
