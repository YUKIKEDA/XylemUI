# V3c: `samples/Todo`

`Show` と `For` の上に、TODO の一覧のサンプルを作った（ロードマップの行 V3 の V3c、Issue #380、設計書 §2.7「確かめ方」）。サンプルの形は V3c の Grill（Q1〜Q6）で決めた。

- **項目:** 済みを切り替えるボタンと消すボタン（`×`）の横並び。済みは `[x]` の印と灰色の文字で見せる
- **見出し:** `todos: N` と `left: K`
- **絞り込み:** `All`／`Active`／`Done` の 3 つで、選んだボタンの背景を暗くする
- **並べ替え:** 新しい順／古い順を切り替えるボタン 1 つ
- **一覧:** `ScrollView` の中に置く

どれも Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で測った。

## 再現

```powershell
dotnet publish samples/Todo -c Release -r win-x64 -o <todo>
dotnet publish samples/Counter -c Release -r win-x64 -o <counter>
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe app-startup <todo>/Todo.exe --at 24,60 --runs 1 --idle       # 起動と、何もしていないときのメモリ
<dir>/XylemUI.E2E.exe app-startup <counter>/Counter.exe --at 20,40 --runs 1 --idle
<dir>/XylemUI.E2E.exe idle 3                                                       # M1a の場面の何もしていないとき
cmd /c start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe todo                # 1,000 項目の各操作（ウィンドウを開かない）
```

- **`--at 24,60`（物理画素）:** Todo の Add ボタンの中に当たる点。倍率が 100〜150 % のどれでも当たる。ボタンの背景は Counter と同じ `#3366CC` である
- **`--idle`:** この PR で `app-startup` に足した。ボタンの色が画面に出たら 3 秒待ち、そこから 10 秒の CPU 時間と、終わりの working set・private bytes を読む。M1a の比べ方（`External.Idle`）と同じ定義である
- **測った exe:** `Todo.exe` と `Counter.exe` は、ほかのファイルの無いディレクトリに 1 つずつ置いて走らせた

## 正しさ（`TodoTests`、WARP、6 件）

- **MoonBit 版の V3 の到達点:**
  - Add を 3 回押すと `todos: 3` と `left: 3` になる
  - 10 項目にして一覧の位置を 64 にすると、2 つ目の項目の y は変わらない
  - 一覧の下に切られていた項目のボタンの画素は、スクロールの前はボタンの色でなく、後は `TodoApp.ButtonBackground` になる
- **足した機能:**
  - **済み:** クリックで `[x] Item 2` と `TodoApp.DoneColor` になり、もう 1 回で戻る。`left` も追う
  - **消す:** その項目だけが消える
  - **絞り込み:** 3 つとも、通す項目と、選んだボタンの背景
  - **並べ替え:** 順とボタンの文字
- **割り当て 0:** 済みの切り替えと並べ替えの後のフレーム（`SteadyStateAllocation`、1,000 回、100 項目）。描き先は、描くことも Present もしない（確かめるのはフレームの段の割り当て。WARP で 1,120 回 Present すると、CI の Windows のジョブが 30 分の上限を超えた）。変更そのものはアプリが新しい一覧を作るので、測る外に置いた。そのため `SteadyStateAllocation` に、測らない準備を受ける形を足した

## 起動と、何もしていないときのメモリ（Todo と Counter を交互に 6 巡）

| 指標 | Todo | Counter |
| --- | --- | --- |
| 起動から、ボタンの色が画面に出るまで | 675〜824 ms | 690〜828 ms |
| 何もしていないときの private bytes | 59.6〜61.2 MB | 59.6〜61.0 MB |
| 何もしていないときの working set | 52.0〜57.0 MB | 51.4〜53.3 MB |
| 何もしていないときの CPU（10 秒） | 0 ms が 4 回、15.6 ms が 2 回 | 0 ms が 4 回、15.6 ms が 2 回 |

- 起動は Counter と範囲が重なる。どちらも 1 巡目が長かった（824 ms と 828 ms）。M1a の目標（中央値 250 ms 以下）より長いのは、R4d が入れた実行時のシェーダのコンパイルのためで、行 C0 でビルド時のコンパイルにする（`docs/benchmarks/v1d-components.md`）
- private bytes は、M1a の目標（比べた 3 つの最も小さい 75.6 MB より小さく、目安は 64 MB 以下）を満たす
- 何もしていないときの CPU は、Todo も Counter も、6 回のうち 2 回で 15.6 ms（計測の 1 刻み）だった。目標は「分解能未満」である。同じ時間帯に M1a の場面（`idle 3`）を測ると、3 回とも 15.6 ms だった（M1a の記録は 0 ms）。この時間帯の機械の側の分で、サンプルの差ではない
- `Todo.exe` は 3,700,736 バイトで、警告は 0 だった（Counter は 3,352,576 バイト）

## 1,000 項目の各操作（`todo`、性能コアに固定して 3 回、31 標本の中央値）

場面は、サンプルの `TodoApp` を 1,000 項目（半分は済み）のモデルの上に作る。ウィンドウは 420 x 360 で、文字の道具（DirectWrite）を持ち、GPU は使わない。各操作は V3a の `lists` と同じく 3 つに分けて測る。

- **変更:** モデルのメソッド。その Effect がその場で行を合わせる
- **layout の pass**
- **描画の段:** 表示リストを作り、グリフをアトラスへラスタライズする

各操作は、元に戻す操作と対にして、どの標本も同じ 1,000 項目から始まる。ただし「すべてに戻す」だけは、未完了だけにした木から始める。その標本は、500 行を作り（測る）、500 行を外す（測らない）往復である。

| 操作 | 変更 | layout | 描画の段 |
| --- | --- | --- | --- |
| 末尾に 1 項目足す | 39.0〜39.8 µs | 100〜125 µs | 878〜913 µs |
| 真ん中の項目の済みを切り替える | 39.1〜41.9 µs | 88.9〜108.9 µs | 859〜902 µs |
| 真ん中の項目を消す | 40.3〜43.5 µs | 90.9〜101.9 µs | 867〜953 µs |
| 未完了だけにする（500 行を外す） | 419〜440 µs | 49.5〜53.1 µs | 567〜614 µs |
| すべてに戻す（500 行を作る） | 1,572〜1,599 µs | 5,625〜5,727 µs | 1,136〜1,146 µs |
| 順を逆にする（999 行が動く） | 106〜108 µs | 100〜113 µs | 867〜967 µs |

- **変更（1 項目の操作、約 40 µs）:** モデルが 1,000 項目の新しい一覧を作り、見せる一覧の Computed と未完了の数を求め直し、`For` が 1,000 のキーを比べる。逆順は、ほかに 999 行が 1 回ずつ動く（V3a の 1 行約 85 ns）。変わった項目の行の文字は、その場で書き直す。書き直しは `TextBuilder` の補間で、文字列を作らない（V1d の `TextBuilder` の割り当て 0 のテスト）。新しい一覧はアプリのモデルが作る
- **500 行を外す変更（419〜440 µs）:** 500 行の Scope を破棄する。行 1 つは、箱とボタン 2 つと文字の葉 2 つ、Computed、ハンドラを持つ
- **500 行を作る変更（約 1.6 ms）:** 500 行を作る。1 行約 3.2 µs
- **500 行を作った後の layout（約 5.7 ms）:** 新しい文字の葉 1,000 枚を、layout の中で初めて整形する。1 枚約 5.7 µs で、S8b の 1 行の整形（ループで 1.35 µs、フレームの最初の呼び出しで約 15 µs）の間にある。ほかの操作の layout（約 100 µs）は、1,000 行の列を並べ直す今のレイアウトの費用である
- **描画の段（約 0.9 ms）:** 描くフレームでは、表示リストをまるごと作る（設計書 §5.0.1）。切られて見えない行も含めて、1,000 行の命令を書く。見える行だけを作る仮想化は行 P02 である
- **すべてに戻した直後の描画の段（1,136〜1,146 µs）:** ほかの 1,000 行の描画の段（859〜967 µs）より長い。一時の版で、次の 2 つを確かめた
  - 同じフレームの 2 回目を描いても 1,118〜1,277 µs で、長いままだった。初めて描く分ではない
  - 絞り込みの後の木（作り直した 500 行が、残った行の間に入った木）で済みの切り替えを測り直すと、889〜1,003 µs で、ふだんと同じだった。ノードの並びの分でもない
  - layout の後、描画の段の前に `GC.Collect()` を入れた版（回収の時間は測る外）と今の版を、別の回に固定して交互に 4 回ずつ測った（PR #381 のレビュー）。結果は下の表のとおりで、回収した版では、すべてに戻した直後の描画の段がほかの操作と範囲が重なった。未完了だけにした直後の描画の段も短くなった

    | 版 | すべてに戻した直後 | 未完了だけにした直後 | 1 項目の操作と逆順 |
    | --- | --- | --- | --- |
    | 今の版 | 1,253〜1,437 µs | 657〜710 µs | 908〜1,175 µs |
    | 描く前に回収した版 | 1,100〜1,247 µs | 509〜566 µs | 991〜1,167 µs |

  長い分は、500 行を作るか外した直後の、まだ回収していないヒープの上で描く分である。この回は、上の表の回より全体が 1 割ほど長かった（済みの切り替えの描画の段が 916〜1,034 µs）ので、同じ回の中の値だけを比べた
- 並べ替えの描画の段は、1 回目の計測（固定しなかった回）で 2,367 µs と長く出た。そこで、並べ替えを絞り込みの前に測る一時の版と、今の順の版を固定して交互に 3 回ずつ測った。どちらも 1,064〜1,459 µs で、範囲が重なった。測る順の分ではなく、固定しなかった回のぶれだった
