# V3b: 変わらない部分木のスクロールの範囲を使い回す

ノードごとに部分木のはみ出しを覚え、layout が変えた所だけを求め直すようにした（ロードマップの行 V3 の V3b、Issue #376、設計書 §3.4.1「覚えた値を古いとする印」）。どれも Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で、性能コア（論理プロセッサ 2）に固定し、優先度を高くして測った。比べた main は、ブランチの土台の 817022c である。`layout` の場面のファイルは、両方とも V3b のもの（窓の大きさを変える標本を足したもの）で測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe layout
```

`layout` の場面は、ウィンドウを開かない。`scroll_*` の木は、S6b の場面の 10,101 ノードの木の根を、縦にスクロールする箱（`OverflowY = Scroll`、状態つき）にしたものである。

- **1 か所の変更:** 1 枚の葉の幅を変え、layout の pass と範囲を書くこと（`PublishScrollRanges`）を続けて測る（`scroll_change`）。範囲を書くことだけも測る（`scroll_publish`）
- **すべてを layout し直すとき:** 窓の幅を 1,999 と 2,000 に交互に変え、同じ 2 つを測る（`scroll_resize`、`scroll_resize_publish`）。V3b で足した系列である

## スクロールする箱の中の S6b（main と交互に 4 回、15 標本の中央値）

| 指標 | main | V3b |
| --- | --- | --- |
| 1 か所の変更、layout の pass と範囲を書くこと | 141〜147 µs | 23.2〜23.8 µs |
| そのうち範囲を書くこと | 116〜121 µs | 2.7〜2.8 µs |
| すべてを layout し直すとき、layout の pass と範囲を書くこと | 705〜763 µs | 697〜738 µs |
| そのうち範囲を書くこと | 118〜123 µs | 108〜114 µs |

- 表は 2〜4 回目の値である。1 回目は両方とも長かった。たとえば、1 か所の変更は main が 244 µs、V3b が 23.5 µs で、すべてを layout し直すときは main が 1,263 µs、V3b が 788 µs だった。測っていないときにも CPU の負荷は 19 % あり、固定してもこの回だけがずれた
- 1 か所の変更では、範囲を書く仕事が、変わった道の長さで決まる。main は、スクロールする箱の部分木の 10,101 ノードを毎回たどっていた（`docs/benchmarks/v2-scroll.md`）。V3b は、印のあるノードだけを求め直す。同じ形の小さな木では、求め直すのはスクロールする箱と、変わった行の 2 つだけだった（`ScrollRangeReuseTests.OneChange_FindsOnlyThePathAgain`）
- すべてを layout し直すときは、すべてのノードが印を持つので、範囲を書くことは main と同じくすべてをたどる。layout の pass と合わせた時間は main と重なる。範囲を書くことだけは、どの回も V3b のほうが短かった（108〜114 µs と 118〜123 µs）。V3b は覚えた値を書く分だけ仕事が多いので、覚えた値を使わない一時の版（`ScrollableOverflowOf` が覚えた値を返さない。ほかは V3b と同じ）を作り、別の回に main・その版・V3b を順を変えて 3 回ずつ測った。2・3 回目の範囲を書く時間は、main 133〜141 µs、その版 119〜124 µs、V3b 123〜131 µs で、その版も main より短かった。短くなったのは、覚えた値を使うことではなく、求め直す関数を分けたコードの形から来ている。この回の 1 回目は、main だけが 249 µs と長かった

## スクロールする箱の無い場面（同じ回、2〜4 回目）

| 指標 | main | V3b |
| --- | --- | --- |
| S6b、最初の layout | 3,381〜3,646 µs | 3,452〜3,614 µs |
| S6b、1 か所の変更 | 21.5 µs | 20.9〜21.3 µs |
| S6b、幅の変更 | 606〜656 µs | 569〜660 µs |
| auto_min、最初の layout | 5,029〜5,429 µs | 5,302〜5,677 µs |
| auto_min、1 か所の変更 | 38.1〜38.7 µs | 37.8〜39.0 µs |
| auto_min、幅の変更 | 570〜679 µs | 596〜692 µs |
| percent、1 か所の変更 | 37.0〜40.2 µs | 39.7〜40.5 µs |
| wrap、1 か所の変更 | 1,104〜1,254 µs | 1,167〜1,445 µs |
| absolute、1 か所の変更 | 2.2〜2.4 µs | 2.3〜2.4 µs |

- どの指標も範囲が重なる
- auto_min の最初の layout は、3 回のうち 2 回で V3b のほうが長かった（5,677 µs と 5,429 µs、5,338 µs と 5,029 µs）。残りの 1 回は V3b のほうが短かった（5,302 µs と 5,397 µs）。最初の layout はすべてのノードを commit するので、ノード 1 つにつき、覚えた値の配列（1 ノード 12 バイト）に印を 1 つ書く
- 覚えた値を `MeasureCache` に足すと、576 バイトから 592 バイトになった（一時のテストで `Unsafe.SizeOf` を読んだ）。`MeasureCache` の大きさは、L4 と L5 で layout の時間に効いたので（`LayoutCacheKey.cs` の注釈）、別の配列にした
