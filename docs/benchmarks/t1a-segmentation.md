# T1a: Unicode の表、書記素、改行の候補

Unicode 18.0.0 の表の生成器（`tools/UnicodeTableGen`）、書記素（UAX#29）と改行の候補（UAX#14）の列挙、フォールバックの境界の切り直しを足した（ロードマップの行 T1、Issue #284、設計書 §4.1「改行と書記素の決定」、§8.13）。その正しさと費用を確かめた。どれも Windows 11 26300、Intel Core i5-13400F で、時間は NativeAOT の Release で測った。

## 再現

```powershell
dotnet run --project tools/UnicodeTableGen -c Release   # 表を作り、表の大きさと 1 文字を引く時間を候補ごとに出す
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe segment                            # 画面 1 枚の文の、1 文字あたりの時間
```

`segment` は、40 行 × 80 文字（3,200 文字以上）の文を、1 つの文を繰り返して作る。文は日本語（『吾輩は猫である』の冒頭）、英文（数字と括弧を含む）、絵文字の混じった英文（ZWJ の家族、国旗、肌の色、異体字セレクタ）の 3 種類である。

## 正しさ（`UnicodeConformanceTests`・`SegmentationTests`・`FontFallbackTests`）

- **適合のテスト:** Unicode 18.0.0 の `GraphemeBreakTest.txt` と `LineBreakTest.txt` の全行（合わせて 20,199 ケース）が、例外なしで通った
- **規則は仕様から写した:** UAX#29 の Revision 49 と UAX#14 の Revision 57 の規則の節を読んで写した。Unicode 18.0.0 では、GB9c が `\p{InCB=Linker} \p{InCB=Extend}* × \p{InCB=Consonant}` に、LB12a が `[^SP HY HH] × GL` に変わった
- **端の場合:**
  - LB4・LB5 の強制改行のそれぞれ（VT、FF、U+2028、U+2029、CR、LF、NEL、CR LF は 1 つ）は、その後ろで必ず改行する
  - 小書きの仮名と長音記号の前では改行しない（strict）
  - 絵文字の ZWJ の並び、異体字セレクタ、肌の色、国旗、サロゲートペアは、書記素も改行の候補も切らない
  - 国旗 2 つの間では改行できる
  - 対のないサロゲートは、それだけで 1 つの書記素になる
- **フォールバック:** プロバイダの長さが書記素の途中で終わるとき、run はその書記素の終わりまで伸びる
- **表のバージョン:** 表の `Version` は、`vendor/versions.lock` の `unicode-ucd` の行と一致する
- **割り当て:** 改行の候補を求め、書記素をたどる処理は、配列が育った後は 0 バイトだった（Debug と Release）
- **ミュータント:** 3 個（小書きの仮名を ID に解決する、フォールバックの境界を伸ばさない、CR LF を 1 つにしない）。どれも、狙ったテストが落ちた

## 表の構造

1 文字の値は 32 ビットに詰めた。中身は、改行の種類 6 ビット、書記素の種類 4 ビット、拡張絵文字、東アジアの幅（F・W・H）、Indic_Conjunct_Break 2 ビット、規則が読む一般カテゴリ（Pi・Pf・Mn・Mc・Cn）3 ビットである。Unicode 18.0.0 では値は 112 種類しかないので、2 段目には値の表の番号を 1 バイトで持つ。

| ブロック | 1 段目 | ブロックの数 | バイト | 1 文字を引く時間（ns） |
| --- | --- | --- | --- | --- |
| 16 | 69,632 | 774 | 152,096 | 1.11〜1.12 |
| 32 | 34,816 | 621 | 89,952 | 1.12 |
| 64 | 17,408 | 441 | 63,488 | 1.15〜1.80 |
| **128** | **8,704** | **283** | **54,080** | **1.11〜1.12** |
| 256 | 4,352 | 185 | 56,512 | 1.12〜1.42 |
| 512 | 2,176 | 122 | 67,264 | 1.15〜1.34 |
| 1,024 | 1,088 | 83 | 87,616 | 1.13〜1.19 |

- 最も小さい、ブロック 128 を選んだ。引く時間は、どのブロックでもほぼ同じだった（生成器の中で、JIT の Release で 2 回測った範囲）
- 32 ビットの値をそのまま 2 段目に持つ表では、最も小さいもの（ブロック 64）で 147,712 バイトだった
- 表はどれもバイトの列（`ReadOnlySpan<byte>`）で持つ。`ushort` と `uint` の列で持つと、Debug のビルドでは読むたびに配列を作り、割り当て 0 のテストが 1 回に 19,008 バイトで落ちた（Release では 0）

## 費用（`segment`、3 回の中央値の範囲）

| 文 | 改行の候補（ns/文字） | 書記素（ns/文字） |
| --- | --- | --- |
| 日本語 | 27.4〜29.0 | 6.8〜7.7 |
| 英文 | 20.7〜22.2 | 6.8〜7.0 |
| 絵文字の混じった英文 | 17.8〜21.8 | 6.8〜10.9 |

- 画面 1 枚（3,200 文字）の改行の候補は、約 70〜90 µs である。改行の候補は文字の内容が変わったときにだけ求め、結果は文字の葉のキャッシュに持つ（設計書 §3.2、行 V1a）ので、毎フレームの費用ではない
- **内訳（CPU のプロファイル、Visual Studio のコレクタと xperf）:** 改行の候補の時間は、次のように分かれた
  - 規則を順に当てる `Decide`: 53 %
  - 単位に分ける `TakeUnits`: 19 %
  - 空白の前の単位を探す処理: 7 %
  - 単位を足す処理: 6 %
  - LB28a の確かめ: 5 %
  - そのほか: 10 %

  多くの境界（日本語では漢字と仮名のほぼすべての間）は、LB31 まで規則を順にすべて確かめる。そのため、日本語が最も長い
