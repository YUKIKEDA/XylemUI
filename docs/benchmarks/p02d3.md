# P02d3: 窓全体のアクセスキー・Label・メニューバー

行 P02d3（設計書 §13.1「窓全体のアクセスキー・Label・メニューバー」）を、2 つの PR に分けて入れる。Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で、プロセスを 1 つのコアに固定して（`start /b /wait /affinity 4 /high`）測った。比べる main は、各 PR の merge-base を `.dev/` の worktree で publish した。main と PR は、A・B・B・A の順を 2 回繰り返して流した。値は各回の中央値（p50）の範囲である。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe frames --tree"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe input"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe menu"
```

## 1 つ目の PR: 窓全体のアクセスキーと Label（Issue #577）

main は 82c1503（#576 のマージ）。この PR がアクセスキーの無い経路に足したのは、次の 2 つだけである。

- キーが経路を流れ終えて誰も止めなかったときに、Alt があり Control が無いかを見る分岐（`WindowInput.HandleKeyInBatch`）
- ボタンを作るときに、アクセスキーの相手として登録する 1 回の辞書の書き込み

フレームごとの経路には何も足していない。

| アクセスキーの無い経路の値 | main | この PR |
| --- | --- | --- |
| `frames --tree` の CPU の 1 フレーム（速い状態の回） | 0.124〜0.132 ms | 0.119〜0.138 ms |
| `frames --tree` の描画の段（速い状態の回） | 0.027〜0.030 ms | 0.026〜0.030 ms |
| キー 1 つの配送（深さ 1） | 0.052〜0.060 µs | 0.052〜0.060 µs |
| キー 1 つの配送（深さ 50） | 1.69〜1.88 µs | 1.70〜1.81 µs |
| キーでのボタンのクリック | 0.103〜0.114 µs | 0.103〜0.106 µs |
| Tab（10,101 ノード） | 158.0〜164.0 µs | 159.3〜163.3 µs |
| ホイール 1 つの配送 | 0.10〜0.11 µs | 0.10〜0.11 µs |
| メニューを開いたまま Down で移るフレーム（`menu`） | 4.6 µs | 4.2〜4.6 µs |
| 移るフレームの割り当て（`menu`、1,000 フレーム） | 0 バイト | 0 バイト |

- `frames --tree` は、main の 1 回目とこの PR の 7 回目だけが、描画の段が 10 倍ほど遅い状態で走った（描画 0.38 ms と、ほかの回の 0.026〜0.030 ms）。表の値は、両方の残りの 3 回である
- `input` は 2 組流した。2 組目は、1 組目と逆の B・A・A・B の順を 2 回である。表の `input` の値は 2 組目のもので、1 組目とも重なる
- 文字の欄の Control+Left（`text_field_word_move`）では、配送の部分だけが、2 組とも 4 回すべてでこの PR の方が上に出た。main は 19.0〜21.2 µs、この PR は 19.9〜22.3 µs で、差はおよそ 0.8 µs である。フレームまでの合計は、2 組目で main 58.6〜64.8 µs、この PR 59.5〜66.0 µs と重なる。このキーは、文字の欄のハンドラが止める（`TextField.cs` 583〜586 行目）ので、この PR が足した分岐まで来ない
- どの変更の分かを、`bench` の規則のとおり、この PR から `WindowInput` の分岐だけを main の形に戻した写し（下の表の「戻した写し」）を並べて確かめた。main・この PR・戻した写しを、3 つの順を入れ替えて 4 回ずつ流した（PR #581 のレビュー）

| `input` の値（4 回の範囲） | main | この PR | 戻した写し |
| --- | --- | --- | --- |
| Control+Left の配送 | 19.3〜19.5 µs | 20.1〜20.4 µs | 19.4〜21.3 µs |
| キーでのボタンのクリック | 0.108〜0.120 µs | 0.101〜0.109 µs | 0.103〜0.109 µs |
| キー 1 つの配送（深さ 1） | 0.053〜0.071 µs | 0.052〜0.070 µs | 0.052〜0.057 µs |

- 戻した写しの Control+Left は、4 回のうち 3 回が 19.4 µs で main と重なった。21.3 µs の 1 回は、フレームまでの合計も 64.7 µs と、ほかの回（58.6〜58.7 µs）より遅い回である。差は、分岐があるかどうかについてくる
- ただし、分岐はこの経路では実行されない。同じ `HandleKeyInBatch` を通るキーでのボタンのクリックとキー 1 つの配送は、この PR で遅くなっていない。したがって 0.8 µs は分岐を実行する時間ではなく、分岐のコードが加わって、バイナリの中でほかのコードの置かれる位置がずれた分と判断する（どの関数がずれたかは、プロファイルでは確かめていない）。2 つ目の PR は、さらにコードを足すので、この値をもう一度流して記録する

## 2 つ目の PR: メニューバー（Issue #580）

main は 82c1503（1 つ目の PR と同じ merge-base）。`menubar` の場面は、Todo のサンプル（200 項目）の上に、5 つの文字の項目のメニューバーを置く。各項目はフォーカスで背景を変え、10 個の文字の項目のメニューを持つ。窓は 420 × 360 で、文字は DirectWrite でラスタライズし、GPU には送らない。値は、キー 1 つの配送とそのフレームの合計である。

| `menubar` の値 | この PR（4 回の範囲） |
| --- | --- |
| F10 で選ぶフレーム | 199〜226 µs |
| 選んだ状態で Right で移るフレーム | 177〜195 µs |
| 移るフレームの割り当て（1,000 フレーム） | 0 バイト |
| 移るフレームで主のリストを作り直した回数（1,000 フレーム） | 1,000 |
| Down でメニューを開くフレーム | 256〜286 µs |
| 開いたまま Right で隣のメニューに移るフレーム | 263〜297 µs |
| 隣のメニューに移るフレームの割り当て | 1 フレームあたり 37,424 バイト |

- 移るフレームは、毎回、主のリストを作り直す。メニューバーの項目は主の木にあり、フォーカスの見た目が変わると、主のリストを書き直すからである（設計書 §7.3「表示リスト」）。値の大半は、Todo の 200 行の主のリストを作り直す時間である。開いたメニューの中で移る `menu` の場面は、ポップアップのリストだけを作り直すので、0 回である
- 選ぶフレームは、5 つの項目をフォーカスできるようにし、アクセスキーの下線を出す。下線を出すと、5 つの文字の葉を書き直して測り直す。最初の項目のフォーカスの見た目も変わるので、移るフレームと同じく主のリストも作り直す
- 隣のメニューに移るフレームは、開いていたメニューを閉じ、隣のメニューの中身（10 項目の文字の葉と、その部品のスコープ）を作る。割り当ては、このメニューの中身を作る分である。開く操作は 1 回の操作で、割り当て 0 を求めるフレームではない

| メニューバーの無い経路の値 | main | この PR |
| --- | --- | --- |
| `frames --tree` の CPU の 1 フレーム | 0.112〜0.137 ms | 0.110〜0.126 ms |
| `frames --tree` の描画の段 | 0.026〜0.030 ms | 0.024〜0.027 ms |
| キー 1 つの配送（深さ 1） | 0.053〜0.059 µs | 0.053〜0.060 µs |
| キー 1 つの配送（深さ 50） | 1.72〜1.75 µs | 1.70〜1.81 µs |
| キーでのボタンのクリック | 0.102〜0.104 µs | 0.103〜0.112 µs |
| Tab（10,101 ノード） | 160.1〜162.8 µs | 155.5〜166.7 µs |
| ホイール 1 つの配送 | 0.10〜0.11 µs | 0.10〜0.11 µs |
| 文字の欄の Control+Left の配送 | 19.5〜21.2 µs | 19.5〜21.6 µs |
| メニューを開いたまま Down で移るフレーム（`menu`） | 4.2〜4.6 µs | 4.2〜4.7 µs |
| `menu` の移るフレームの割り当て（1,000 フレーム） | 0 バイト | 0 バイト |
| `menu` の開くフレームのレイアウトの段 | 57.0〜63.4 µs | 62.5〜65.3 µs |

- この PR がメニューバーの無い経路に足したのは、キーが経路を流れ終えた後の、Alt と F10 を見る分岐と、ポインタの押下で「Alt だけ」を消す 1 つの代入である。フレームごとの経路には何も足していない
- 1 つ目の PR で上に出た Control+Left の配送は、この PR では main と重なった。1 つ目の PR の記録のとおり、実行される分ではなく、コードの配置の差である
- `menu` の開くフレームのレイアウトの段は、範囲は重なるが、この PR の 4 回が main の上半分に寄った。この PR は、メニューの項目の登録で、項目ごとに 1 つのデリゲートを作るようになった（文字で項目を選ぶ動作を、メニューバーの項目と同じ形で登録するため）。ただし、登録は中身を作る段で行い、レイアウトの段には入らない。レイアウトの段の差の原因は確かめていない。範囲が重なるので、`bench` の規則のとおり、この PR では差として扱わない
