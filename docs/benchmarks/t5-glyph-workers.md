# T5: フレームの新しいグリフをワーカーのスレッドで描く

1 フレームで初めて出るグリフを `DisplayList.ResolveGlyphs` がまとめ、UI スレッドを含む 1〜4 本で描く（ロードマップの行 T5、Issue #226、設計書 §5.0.3「初めて出るグリフ」）。その速さと、定常状態のフレームが遅くならないことを測った。どれも Windows 11 26300、Intel Core i5-13400F（論理 16 コア）、NativeAOT の Release で測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe glyph-resolve 9      # そろえる段の時間（場合ごとに 9 プロセスの中央値）
<dir>/XylemUI.E2E.exe draw-text            # 定常状態の DrawText、1 グリフ
<dir>/XylemUI.E2E.exe draw-text --cold     # キャッシュを追い出してから 1 行
<dir>/XylemUI.E2E.exe frames 2400          # フレームの段
```

`glyph-resolve` は、場合ごとに新しいプロセスを起こす。フォントはバイト列から開く（DirectWrite のメモリのローダー）ので、DirectWrite はほかのプロセスと何も共有せず、どのグリフも「どのプロセスもその大きさで描いていない」費用になる（`docs/benchmarks/t4-glyphs.md`）。各プロセスは、まず別の大きさのフレームを 1 つ描いてワーカーを起こし、各スレッドの font face を作ってから、測るフレームを描く。アプリが画面を送る頃には、どちらも済んでいるためである。

## そろえる段の時間（`glyph-resolve 9`）

游ゴシック 16 px の新しいグリフ:

| 新しいグリフ | 1 本 | 2 本 | 4 本 |
| --- | --- | --- | --- |
| 1 | 71 µs | 88 µs | 82 µs |
| 2 | 137 µs | 94 µs | 110 µs |
| 3 | 216 µs | 187 µs | 120 µs |
| 4 | 282 µs | 174 µs | 188 µs |
| 8 | 555 µs | 325 µs | 281 µs |
| 431 | 39.9 ms | 19.7 ms | 10.6 ms |

Segoe UI Emoji 32 px の新しい絵文字:

| 新しい絵文字 | 1 本 | 2 本 | 4 本 |
| --- | --- | --- | --- |
| 4 | 2.5 ms | 1.3 ms | 0.9 ms |
| 64 | 24.2 ms | 9.8 ms | 5.7 ms |

- 431 個（S8b の画面を 1 画面ずつ送るときの最大）は、設計の試作（1 本 42 ms、2 本 24 ms、4 本 16 ms）と同じ範囲になった。7 プロセスずつ繰り返すと、1 本 37.9〜39.2 ms、2 本 19.6〜27.1 ms、4 本 10.4〜17.0 ms だった
- 1 個は分けられないので、何本でも UI スレッドだけで描く。それでも 2 本・4 本の設定では 1 本より 11〜17 µs 長かった（測るフレームの前に描く 32 個のグリフは、どの設定でも同じ）。原因は分かっていない（Issue #227、行 Q3）

## 閾値（設計の Q6）

設計は 4 個から渡すとし、2〜4 個を測って決めるとしていた。2〜4 個を、ワーカーに渡した場合と UI スレッドだけの場合とで比べた（21 プロセスの中央値、括弧は 25〜75 パーセンタイル）:

| 新しいグリフ | 4 本に渡す | UI スレッドだけ | 2 本に渡す |
| --- | --- | --- | --- |
| 2 | 130 µs（121〜147） | 146 µs（141〜158） | 88 µs（77〜101） |
| 3 | 188 µs（155〜212） | 222 µs（214〜242） | 158 µs（152〜175） |
| 4 | 247 µs（242〜285） | 308 µs（299〜323） | — |

どれもワーカーに渡したほうが速かったので、閾値を 2 にした（`GlyphAtlas.ParallelThreshold`）。これは論理 16 コアのこの機械の値である。コアの少ない機械（論理 4 コアなら UI スレッドを含めて 2 本）では、ワーカーを起こす費用とグリフの費用の比が違いうるので、そのまま当てはめずに読む。`glyph-resolve` の `serial` の行（2〜4 個を UI スレッドだけで描く）でも、2 本の設定で 145・224・307 µs、4 本の設定で 160・226・286 µs と、渡したほうが速い。少ないグリフでは 4 本より 2 本のほうが速かったが、本数の既定（論理コア数 ÷ 2 を 1〜4 本）はこの行では変えていない。

## 正しさ

- `ParallelGlyphTests`（`tests/XylemUI.Platform.Windows.Tests`）: 40 行 80 字の游ゴシックの画面と絵文字 40 個の行を、100・125・150 % の 3 フレームで、1 本と 4 本のアトラスに入れた。4 本は毎回新しいアトラスと新しい DirectWrite のラスタライザで 200 回繰り返し、表示リストの命令と `GlyphInstance` とすべてのページの画素が、1 本と 1 バイトも違わなかった。例外も出なかった。Debug で 1 回 0.3 秒、200 回で約 1 分かかる
- `GlyphAtlasManyTests`（テストのラスタライザ）: 300 グリフで 1 本と 4 本のページと領域が同じ。ワーカーのスレッドで投げた例外は、すべてのワーカーが終わってから投げ直し、そのとき場所を取ったグリフはアトラスに残さない

## 定常状態

グリフがすべてアトラスにあるフレームでは、`ResolveGlyphs` は何もしない。

- **`DrawText`（`draw-text`、40 行 3,200 グリフ、200 フレームを 21 回、main と交互に 4 回ずつ）:** 1 グリフ、main 45.8〜46.6 ns、T5 45.5〜46.6 ns
- **フレーム（`frames 2400`、main と交互に 5 回ずつ、中央値）:** 表示リストの段は main 25.1〜29.0 µs、T5 26.3〜28.9 µs。Draw は 25.7〜32.8 µs と 27.0〜31.5 µs
- **冷えたキャッシュの 1 行（`draw-text --cold`、64 MB をなめてから場面の 1 行 22 グリフ、4,000 フレームの中央値、main と交互に 4 回ずつ）:** main 4.0〜4.3 µs、T5 4.6〜4.9 µs。段ごとの平均は、`BeginFrame` が 534〜601 ns と 615〜714 ns、`Reset` が 23〜26 ns と 21〜22 ns、`DrawText` が 3.56〜3.91 µs と 4.08〜4.44 µs

冷えたキャッシュの 1 行は、はじめ main より 0.7 µs 長かった（フレームの表示リストの段は 1.2 µs 長かった）。段ごとに分けると、`BeginFrame` の断ったグリフの表の片付けが 100〜200 ns、`Reset` の待ちの表の片付けが 100 ns、`DrawText` が 150〜550 ns 増えていた。片付けは、表を次に使うときにする形にして、`BeginFrame` と `Reset` は main と同じになった（`Reset` は 22〜30 ns）。T5 だけで使う状態は、表示リストとアトラスとは別のオブジェクトに移した。残る差（`BeginFrame` で約 100 ns、`DrawText` で約 500 ns）は、`DrawText` のループの形を変えても、アトラスの参照のフィールドを main と同じ数にしても変わらず、原因は分かっていない（Issue #227、行 Q3）。

## DirectWrite のラスタライザで試してやめたこと

アトラスはフレームの新しいグリフをすべて `Measure` してから `Rasterize` するので、`Measure` の解析を 1 つだけ覚えるラスタライザでは、`Rasterize` のたびに解析を作り直す。解析と色のグリフの画素をキーごとに保つ形を試したが、431 個を 1 本で描く時間は、保つ形で 38.3〜43.4 ms、今の形で 38.9〜43.8 ms、絵文字 64 個は 16.1〜26.8 ms と 17.8〜29.5 ms で変わらなかった（5 プロセスずつ）。複雑になるだけなので入れなかった（`docs/design-decisions.md`）。
