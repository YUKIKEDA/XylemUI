# V1c: ポインタの入力

ポインタの入力を、Win32 のメッセージから Core のハンドラまで通した（ロードマップの行 V1 の V1c、Issue #323、設計書 §7「ポインタの入力」と §5.0「描画の段とフレームの駆動」の「不透明度・変換・擬似状態」）。その正しさと費用を確かめた。費用はどれも NativeAOT Release で測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe frames 600 --tree              # V1b の木の場面（描画の段が遅くなっていないか）
<dir>/XylemUI.E2E.exe frames 600 --tree --no-text    # 同じ場面から文字の行を外したもの
<dir>/XylemUI.E2E.exe frames 600 --tree --hover      # 箱を止め、毎フレームポインタを 2 つの箱の間で動かす
<dir>/XylemUI.E2E.exe input                          # イベント 1 つの配送（ウィンドウを開かない）
```

`frames --tree --hover` の木は、`frames --tree` と同じ 1,000 個の箱に、ホバーの背景（`PaintStyle`）を持たせたもの。箱は最初のフレームの位置に止まり、フレームごとに、ポインタを 1 つ目の箱の中と 2 つ目の箱の中へ交互に動かす（`WindowInput.Handle`）。フレームは、ホバーの色の変化だけで描かれ、layout は流れない。`input_ms` は、その移動 1 回の配送の時間である。

`input` は、GPU を使わない木で、入れ子の箱の鎖（深さ 1 と 50）の先の葉の上で、ポインタを動かす。鎖の箱と葉は、それぞれ capture と bubble の両方に移動のハンドラを持つ。ホバーが変わる移動は、2 つの葉の間を交互に動かす。

## 正しさ

- **Core（`WindowInputTests`、合成した `PointerInput`、15 件）:**
  - capture と bubble の順、`StopPropagation` で両方のフェーズが終わること
  - キャプチャ: 押したノードに、外とウィンドウの外の Move と Up が届く。すべてのボタンを離した後に放す。CaptureLost で Cancel が届き、Click は来ない。キャプチャしたノードが外されたら、黙って放す
  - Click: 離した点が押したノードかその子孫のときだけ、bubble で届く。右ボタンでは来ない
  - Enter と Leave: 出たノードは内側から、入ったノードは外側から。共通の祖先には来ない
  - Hovered と Pressed: Hovered は当たったノードと祖先に、Pressed は押したノードと祖先に、外に出ても離すまで立つ。印は、その状態の見た目を持つノードにだけ付く
  - カーソル: 当たったノードから祖先へ最初に値を持つもの。キャプチャ中はキャプチャしたノードから
  - ハンドラの例外は `UnhandledExceptionHandler` に渡り、次のハンドラへ続く
  - `Rehit`: 動かないポインタの下で箱を入れ替えたフレームの後、Leave と Enter が届く
  - 倍率 2 で、変換（中心の周りの 2 倍）の中の `LocalPosition`
  - 遮る印、不透明度 0 の部分木（命令は 0、ヒット領域は 1、当たる）
  - 割り当て 0（`SteadyStateAllocation`、1,000 回）: ホバーの出入りと、それを描くフレーム、押して離す Click、`Rehit`
  - 大きさの上限（下の「大きさ」）
- **Platform（`Win32WindowPointerTests`、本物のウィンドウに `SendMessage`、4 件）:**
  - メッセージを `PointerInput` に直す関数: ボタン、`MK_*` のボタンとキー、符号のある位置、引数で渡す Alt、`GetMessageExtraInfo` の印からのタッチとペン
  - `ClickCount`: ダブルクリックの時間の中で 2、時間を過ぎたら 1、別のボタンは 1。時刻は偽の `TimeProvider` で進めた
  - 自分で放したキャプチャは CaptureLost にしない。`WM_CAPTURECHANGED` は CaptureLost にする
  - `WM_SETCURSOR` の `HTCLIENT` で、入力が選んだカーソルになる
- **画素（`DrawStageRenderTests`、WARP、125 %、5 件）:** 木から描いたものと、解決した値の命令を直接書いたもので、画素がすべて一致した
  - 擬似状態の 4 通り（なし・Hovered・Pressed・両方）の背景・枠線・子の文字の色。子の文字の葉は自分の色を持たず、ボタンの `Foreground` を受け継ぐ
  - 中心の周りの回転と拡大、部分木の不透明度 0.5
- **ミュータント:** 2 個。どちらも、狙ったテストが落ちた
  - `WindowFrames` が Present の後に `Rehit` を呼ばない
  - Click を、離した点によらず送る

## 費用

### 描画の段（`frames --tree`、600 フレームの中央値）

V1c は、描画の段の 1 つのノードで、入力・状態の見た目・スコープの有無を読む。状態も変換も無いノードでも払う分を、main（478725f）と #324 の修正だけのビルドと比べた。V1c のブランチは #324 の修正を含む。3 つのビルドを、巡ごとに順を逆にして 4 巡、同じ回の中で交互に走らせた。

| 場面 | main | #324 の修正 | V1c |
| --- | --- | --- | --- |
| `--tree` | 28.4〜28.8 µs | 30.8〜32.6 µs | 35.4〜37.9 µs |
| `--tree --no-text` | 23.8〜24.4 µs | 27.1〜29.3 µs | 31.1〜33.1 µs |
| layout の pass | 167〜184 µs | 170〜183 µs | 170〜195 µs |

- #324 の修正の 2〜4 µs は、毎フレーム動く 1,000 個の箱を `PaintUpdates` に積み、その印を消す分である（PR #326）
- V1c の残りの 4 µs 前後（1 ノード約 4 ns）は、`DrawNode` の枠の分である。`dumpbin /disasm` で比べると、枠は 0x80 バイトから 0xF8 バイトになった。XMM のレジスタの退避は 2 つから 8 つになり、呼ぶたびに 64 バイトを 0 で埋めるようになった。ほかに、ノードごとに `Input`・`States`・`Scoped`・`Pseudo` を読む

最初の実装では、V1c の描画の段は 62.0〜70.4 µs（`--tree`）だった。見た目を解決した値（`Look`）を、状態の無いノードでも毎回作って渡していた。次に `Look` をやめ、局所変数で解決した。それでも 43.4〜46.3 µs で、`DrawNode` の枠が 0x3C8 バイトあり、呼ぶたびに約 620 バイトを 0 で埋めていた（`Paint?` と `PaintStyle` は参照を含むので、0 で埋める）。解決を 1 つのメソッドに分けても、見た目を持つノードは毎回そのメソッドの枠（0x338 バイト）を払った。同じ回の 2 巡で、分けた形は `--tree` 44.4〜45.4 µs、`--no-text` 40.6〜41.2 µs、分けない形は 42.6〜44.6 µs と 38.6〜40.3 µs で、速くならなかったので採らなかった。今の形は、状態の見た目が当たるか、変換か不透明度を持つノードだけが、別のメソッド（`DrawResolved`、`NoInlining`）を呼ぶ。ほかのノードは、`NodeVisual` の値をそのまま箱の描画に渡す。変換か不透明度を持つかは `NodeVisual.Scoped` に持ち、`Matrix3x2?` を写さずに読む。

### ホバーだけが変わるフレーム（`frames --tree --hover`、4 回、600 フレームの中央値）

| 段 | 中央値 | p95 |
| --- | --- | --- |
| 入力（移動 1 回の配送） | 11.2〜11.7 µs | 14.3〜15.1 µs |
| 描画の段 | 65.4〜68.4 µs | 98.9〜107.7 µs |
| layout の pass | 0 | — |
| Draw | 32.7〜34.4 µs | — |
| CPU のフレーム（入力を除く） | 153〜171 µs | — |

- 描画の段は `--tree`（35〜38 µs）より約 30 µs 長い。1,000 個の箱がホバーの見た目を持ち、どれもヒット領域を書く。R4e で、ヒット領域 1 つを書くのは約 21 ns（1,000 個で約 21 µs）だった（`docs/benchmarks/r4e-hits.md`）
- 入力の 11 µs は、2 つの箱の Leave と Enter、フラグ、印、カーソルを求めることと、1,000 個のヒット領域を末尾から試すことである。R4e で、1,000 項目の判定はスコープの外で約 9 µs だった

### イベント 1 つの配送（`input`、5 回、21 標本の中央値）

| 場面 | 1 回の移動 | ハンドラの数 |
| --- | --- | --- |
| 深さ 1（葉だけ） | 0.136〜0.138 µs | 2 |
| 深さ 50 | 4.46〜4.83 µs | 100 |
| ホバーが変わる移動 | 0.156〜0.172 µs | — |

- 深さ 50 の移動は、ハンドラ 1 つあたり約 45 ns である。プロファイル（VS の収集器、NativeAOT）では、時間の 74 % が `WindowInput.Invoke` 自身にあった。`Invoke` は呼ばれるたびに 0x140 バイトの枠を取り、そのうち 192 バイトを 0 で埋める（`PointerEvent` と `HandlerEntry` が参照を含むため）。try と catch のために、rbp を使う枠にもなる。移動 1 回で、50 個のノードと 2 つのフェーズで 100 回呼ばれる
- ボタンのような経路（ハンドラが 1〜3 個）では 0.14 µs 前後で、フレームの予算（120 Hz で 8.3 ms）に比べて十分小さいので、直していない
