# R4e: `DrawingContext` と角丸のヒット領域

`DrawingContext` と、表示リストの中のヒット領域の一覧と、その判定を足した（ロードマップの行 R4、Issue #276、設計書 §5.0「ヒット領域と `DrawingContext`」、§7「ヒットテスト」）。その正しさと費用を確かめた。どれも Windows 11 26300、Intel Core i5-13400F、NVIDIA GeForce RTX 3060 Ti、主モニタは 125 % で、時間は NativeAOT の Release で測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe hit-region          # 領域を 1 つ書く費用と、1,000 個の領域に当たらない点の判定
<dir>/XylemUI.E2E.exe fill-rect 1.25      # 比べる矩形 1 つの費用
<dir>/XylemUI.E2E.exe frames 1200 [--shapes|--curves]   # ヒット領域の無い場面
```

`hit-region` は、角の半径 4 の 16 論理画素の領域を 1,000 個書く（`fill-rect` の矩形と同じ並べ方）。判定は、どの領域にも当たらない点で測る。全部の領域を試す、いちばん長い場合である。どちらも、スコープの外と、回転と角丸のクリップの中の両方で測る。

## 正しさ（`HitTestTests`・`HitRenderTests`）

- **角丸の角:** 0.37 画素おきの点で、当たりを円の式の内外と比べた。判定に使う距離の式とは別に求めた
- **回転した角丸のクリップ:** 30 度回したクリップの中で、0.53 画素おきの点を、点を回し戻したクリップの内外と比べた
- **上限を超えたクリップ（層）:** 互いを含まない角丸を 3 つ入れ子にし、層の外側の 2 つの外では当たらないことを、0.61 画素おきの点で確かめた
- **拡大率 0 の変換:** 中の領域は、クリップの有無にかかわらず当たらない
- **重なり:** 後に書いた領域（手前）が当たる
- **辺:** 125 % で、移動なし・整数の画素の移動・端数の移動のどれでも、領域の辺は同じ矩形の命令の辺と一致する
- **画素との一致（WARP）:** 125 % で、20 度回した角丸のクリップの中に角丸の形を描いた。青のチャネルから覆いを求め、覆いが 0.53 以上の画素の中心は当たり、0.47 以下は当たらない。形の縁とクリップの縁が同じ画素を通る所（どちらの CPU の覆いも 0 と 1 の間）は除いた。その画素の色は 2 つの覆いの積になるが、当たりは形とクリップの覆いがそれぞれ半分以上かで決まるためである
- **ミュータント:** 12 個（層の外のクリップを試さない、角丸のクリップを試さない、矩形のクリップを試さない、逆行列の無い変換で当たる、奥から試す、角の円弧を無視する、辺を画素に置かない、ヒット領域だけのグループを捨てる、ヒット領域だけの状態を捨てる、層が外の状態を持たない、`DrawingContext` がノードを渡さない、`DrawingScope` が戻さない）。どれも、狙ったテストが落ちた

## 費用

| 項目 | 値（5 回の中央値の範囲） |
| --- | --- |
| 領域を 1 つ書く（スコープの外） | 21.4〜23.0 ns |
| 領域を 1 つ書く（回転と角丸のクリップの中） | 20.6〜21.8 ns |
| 1,000 個の領域の判定（スコープの外） | 8.7〜15.4 µs（5 回中 4 回が 8.7〜9.1 µs） |
| 1,000 個の領域の判定（回転と角丸のクリップの中） | 38.6〜46.6 µs |
| 比べる矩形 1 つ（`fill-rect 1.25`、main） | 9.03 ns |

- **書く費用の内訳:** CPU のプロファイル（Visual Studio のコレクタと xperf、NativeAOT）で、書く処理の時間は次のように分かれた
  - `HitRegion` 自身（56 バイトの項目を作って配列に書く）: 47 %
  - 4 つの半径を確かめる `CheckRadius` の呼び出し: 19 %
  - 辺を画素に置く `Edges`: 13 %
  - 半径を CSS のように縮める `Fitted`: 9 %
  - ベンチマークの座標の計算: 9 %
  - 倍率を掛ける `Scaled`: 3 %

  矩形 1 つより長いのは、項目が大きい（矩形の 16 バイトに対して 56 バイト）ことと、半径の確かめと縮め方があるためである。4 つの半径を 1 回で確かめる版も試した。交互に 4 回測ると、試した版が 20.5〜30.5 ns、元の版が 21.1〜24.5 ns で、ばらつきの範囲だった。そのため戻した
- **判定の費用:** クリップの中の判定は、項目ごとに状態の変換の逆行列を求め、角丸のクリップの距離を求める。そのため、スコープの外の約 4.4 倍になる。判定は入力のたびに 1 回で、フレームごとではない
- **割り当て:** ヒット領域を書くフレームと判定は 0 バイトだった（`SteadyState_HitRegionsAndHitTest_AllocateNothing`）

## ヒット領域の無い場面（main と比べる）

1,200 フレームを 3 巡、交互に測った（中央値、µs）。この表は main を先に流した回である。

| 場面 | 段 | main | R4e |
| --- | --- | --- | --- |
| `frames` | 表示リスト | 32.9〜33.9 | 32.7〜34.1 |
| `frames` | Draw | 37.7〜38.5 | 36.7〜38.7 |
| `frames` | GPU | 112.6〜114.7 | 112.6〜113.7 |
| `--shapes` | 表示リスト | 73.3〜74.1 | 74.3〜75.4 |
| `--shapes` | Draw | 84.8〜85.7 | 86.1〜87.1 |
| `--shapes` | GPU | 1,101.8〜1,102.8 | 1,101.8〜1,102.8 |
| `--curves` | 表示リスト | 140.7〜151.2 | 138.1〜151.2 |
| `--curves` | Draw | 116.2〜120.5 | 119.2〜120.5 |
| `--curves` | GPU | 1,048.6 | 1,047.6 |

`--shapes` の表示リストと Draw の段は、R4e が 3 巡とも約 1 µs 長かった。Draw の段のコード（レンダラ）は変えていない。順番を入れ替えて R4e を先に流すと、表示リストは R4e 73.5〜75.1、main 73.9〜74.7、Draw は R4e 85.9〜86.4、main 84.8〜87.1 で、範囲が重なった。約 1 µs の差は、先に流した側が速いという順番の偏りだった。

測っている間、別のセッションの AuraORM のベンチマークが動いていた。どの比べる値も、同じ時間帯に交互に測った。
