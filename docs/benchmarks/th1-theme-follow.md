# TH1: 部品がテーマの切り替えに付いていく形（スパイク）

テーマの Grill の Q5（部品がテーマにどう付いていくか）に数字を付けるための計測である。1,000 個のボタンを 4 つの形で作り、作る費用、持ち続けるメモリ、テーマを切り替えるフレーム、ホバーのフレームを測る。Windows 11、Intel Core i5-13400F、NativeAOT の Release で測る。

場面は `benchmarks/XylemUI.E2E/ThemeFollowCost.cs`（`theme-follow`）。スパイクなので、`Theme` の型とトークンの表は場面のファイルの中にだけあり、`src/` には何も足していない。

## 場面

- **木:** 1,600 x 800 の窓の木（GPU なし、文字は DirectWrite で描く。`menu` の場面と同じ作り）。ウィンドウは開かない
- **ボタン:** `Primitive.Button` に番号の文字（`000`〜`999`）を入れたもの。40 x 32 で、40 個の行を 25 行並べる。5 個に 1 個は強調のボタン、10 個に 1 個は無効にする
- **テーマ:** 不変の 1 つのオブジェクト（`Theme`）を `Signal<Theme>` に入れ、`Context<IReadOnlySignal<Theme>>` の `Provide` でボタンの木を包んで置く。ボタンは作る時に `Use` で引く
- **ボタンの見た目:** 背景、枠の色、文字の色、角の半径、余白、ホバー・押下・無効の見た目。ライトとダークで余白は同じにした（Fluent と同じ）。だから切り替えは色だけの変更で、レイアウトは走らない（D は除く）

## 4 つの形

| 形 | 作り方 |
| --- | --- |
| A：プロパティごとの Signal | 見た目ごとに、テーマの Signal の `Computed` を `Bind` する。ボタン 1 つに Computed 8 個と Effect 8 個。疑似状態の見た目と余白には Core に Signal を受ける多重定義が無いので、場面が `NodeProperty` の internal のコンストラクタで作った（Q5-A で Core に足すものの代わり） |
| B：部品ごとに Effect 1 つ | ボタンごとに Effect を 1 つ作り、テーマの Signal を読んで、木の setter で見た目をすべて書く。setter は同じ値では何もしない。余白は、前のテーマと違う時だけ書く |
| C'：木を 1 度歩いて書き直す | 木に Effect を 1 つだけ作る。テーマが変わると、LC1 の `ShapeDefaultTextAgain` と同じように木のノードの枠をすべて歩き、部品の種類の印があるノードの見た目を、新しいテーマの表から書き直す |
| D：作り直す | ボタンをテーマの値で作り、テーマが暗いかどうかで切り替わる `Show` の下に置く。切り替えると 1,000 個のボタンを捨てて作り直す。フォーカスなどの状態は失われるので、報告書は採らない。費用の基準として測る |

### C' が、本当の C とどう違うか

報告書の C は「トークンの番号をノードの塗りに持ち、描く段で今のテーマの表から引く」形である。Core にはそのための口が無いので、スパイクでは次のように代えた。

- **印:** 部品の種類（標準・強調）の印を、ノードの枠の番号で引くバイトの配列として場面が持つ。本当の形なら `UiNode` の詰め物に 1 バイト足す
- **切り替え:** 木の Effect が全部の枠を歩き、印のあるノードに setter で書く。本当の C は切り替えの時に何も書かず、トークンを使うノードに色の変更の印を付けるだけで、描く段が毎フレーム表を引く
- **測れないもの:** 本当の C では、描く段（`DrawNode`）の塗りを読むところすべてに、トークンかどうかの確認が入る。その費用は、トークンを使わない木も払う。この場面では測れない。C を選ぶなら、Core に口を作ったうえで、トークンの無い木の描く段を main と比べる必要がある（`perf.mdc` の、木の数で飛ばす形）

## 報告する値

| JSON の名前 | 意味 |
| --- | --- |
| `build_us_p50` | 1,000 個を作る時間（Scope の作成から根に付けるまで）。31 回の中央値。各回は作って最初のフレームを描き、捨てる |
| `build_bytes_per_button` | 作る間に割り当てたバイト（31 回の中央値）÷ 1,000 |
| `first_frame_us_p50` | 作った後の最初のフレーム（レイアウト、文字の形、表示リスト） |
| `live_scopes` | 1 回作った後に増えた Scope の数。Effect の Scope を含む（`Scope.LiveCount`） |
| `computeds`・`effects` | 場面が自分の呼び出しで作った Computed と Effect の数（D の `Show` の中の Effect は数えない） |
| `retained_bytes_per_button_build` | 作る前と後の `GC.GetTotalMemory(true)` の差 ÷ 1,000。概算である（ほかの物の増減も入る） |
| `retained_bytes_per_button_frame` | 同じく、最初のフレームの後まで |
| `switch_dark_us_p50` | ライトからダークへの切り替え 1 回（Signal の `Set`、レイアウト、残りのフレーム）。31 回の中央値 |
| `switch_dark_change_us_p50`・`_layout_us_p50`・`_rest_us_p50` | その 3 つの段 |
| `switch_dark_bytes_p50` | その切り替え 1 回で割り当てたバイト（31 回の中央値） |
| `switch_light_*` | ダークからライトへの戻り。同じ値 |
| `hover_frame_us_p50` | 最初の 2 つのボタンの間でポインターを動かすフレーム。31 回の中央値 |
| `hover_bytes_per_frame` | そのフレーム 1,000 回の割り当て ÷ 1,000。0 でなければならない |
| `hover_missed` | ポインターの下のボタンがホバーにならなかったフレームの数。0 でなければならない |

場面は、切り替えのたびに最初のボタンの背景とホバーの見た目が新しいテーマのものかを確かめ、違えば止まる。ホバーも、時間を測るフレームごとに確かめる。

## 測る前の見込み

- **A:** ボタン 1 つに Effect 8 個なので、`live_scopes` は約 8,000。作る時間と持ち続けるメモリは 4 つの中で最も大きい（Computed と Effect とその Scope で、B より 1 ボタンあたり 2〜4 KB 多いと見る）。切り替えでは Computed 8,000 個を計算し直し、値の変わった 7,000 個の Effect が走る（余白は同じなので走らない）
- **B:** `live_scopes` は約 1,000。切り替えでは 1,000 個の Effect が、それぞれ setter を 7 回呼ぶ
- **C':** `live_scopes` は数個。切り替えは、約 2,000 のノードの枠を歩いて 1,000 個に書く。変更の段は 4 つの中で最も短いと見る
- **D:** 切り替えが、作る時間・捨てる時間・最初のフレームの和に近い（ms の桁）。割り当ては作る時の割り当てに近い
- **割り当て:** A・B・C' の切り替えは、setter が既にある見た目の入れ物に書くだけなので 0 バイトと見る。0 でなければ、どこで割り当てたかを調べる。ホバーはどの形も 0 バイト
- **ホバーの時間:** 木は 4 つとも同じ形なので、差は無いと見る

## 再現

```powershell
# vendor/out が無いワークツリーでは、先に vendor/build.ps1 を流す（engineering.mdc）
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
foreach ($round in 1..2) {
    foreach ($way in 'A', 'B', 'C', 'D', 'D', 'C', 'B', 'A') {
        cmd /c start "" /affinity 4 /high /wait /b <dir>\XylemUI.E2E.exe theme-follow $way
    }
}
```

- **順:** A・B・C・D・D・C・B・A を 2 巡（形ごとに 4 回）。各形が先にも後にも来る（`bench.mdc`）
- **固定:** 論理プロセッサー 2（性能コア）に固定し、優先度を高くする
- **負荷:** 各巡の前に、数秒間の CPU の負荷とそれを使うプロセスを読み、記録する
- **値:** 4 回の中央値。かっこの中は最小〜最大

## 読み取り

- **A は、作る費用も持ち続けるメモリも切り替えも、B の約 2.5〜3.5 倍である。** 作る時間は 3.0 倍、作る時の割り当ては 3.1 倍（ボタン 1 つに 5.4 KB 多い）、切り替えは 2.6 倍。見込み（B より 2〜4 KB 多い）より多かった
- **B と C' の差は小さい。** 切り替えは C' が 0.18 ms 短く（1,000 個で。変更の段の差は 0.12 ms）、メモリは C' がボタン 1 つに 320 バイト少ない（Effect 1 つとその Scope の分）。作る時間は C' が 11% 短い
- **D の切り替えは B の 9 倍で、3.6 MB を割り当てる。** 状態も失うので、見込みどおり基準にしかならない
- **A・B・C' の切り替えは 0 バイト、ホバーはどの形も 0 バイトで、取りこぼしも無い。** 見込みどおり
- **ホバーのフレームの差（A 661、C' 620、D 563 µs）は、回ごとの幅（B は 366〜662）の中にある。** 差があるとは言えない
- **最初のフレームは 4 つとも同じ幅の中にある。** 木の形が同じなので、見込みどおり

## このスパイクが答えないこと

- 本当の C の、描く段の費用（上の「C' が、本当の C とどう違うか」）
- テーマの切り替えのキーから画面に出るまでの時間（M1b の `theme-switch` の場面）
- 部品の状態（チェック、選択）が変わるフレーム（Q6）。ここで測るのは、テーマの変更とホバーだけである
- Flutter・Avalonia・GPUI との比較
