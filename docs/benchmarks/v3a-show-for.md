# V3a: `Show` と `For`

部分を作り直す `Show` と、キーで行を保つ `For` を入れた（ロードマップの行 V3a、Issue #368、設計書 §2.7「V3 の形」）。1 万行の一覧の変更が、どこにどれだけ時間を使うかを測った。どれも Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe lists    # 1 万行の For と Show。GPU もウィンドウも使わない
<dir>/XylemUI.E2E.exe frames   # フレームの段（ウィンドウを 1 つ開く）
dotnet publish samples/Counter -c Release -r win-x64 -o <dir2>
```

## 1 万行の一覧（`lists`、3 回）

`lists` の場面は、For で 1 万行を並べた列を持つ。各行は高さ 10 の箱で、背景は項目の色に従う。変更ごとに、差分（シグナルの `Set` から、行の付け替えが終わるまで）、レイアウトの pass、残りのフレーム（表示リストを作る）の 3 つに分けて時間を取る。変更は元に戻す変更と対にしてあり、どの標本も同じ行から始まる。値は 31 標本の中央値。

| 変更 | 差分 | レイアウト | 描画の段 |
| --- | --- | --- | --- |
| 末尾に 1 行足す | 116〜124 µs | 2.74〜2.87 ms | 725〜783 µs |
| 真ん中の 1 行を外す | 107〜111 µs | 2.80〜2.88 ms | 671〜757 µs |
| 順を逆にする（9,999 行が動く） | 856〜869 µs | 2.88〜3.07 ms | 789〜864 µs |
| 真ん中の 1 行の値を変える | 85〜86 µs | 0.1 µs | 397〜425 µs |

`Show` の条件を 1 回変える時間は、3 回とも 1.4 µs だった。

### 差分の内訳

1 行の変更でも、差分は 1 万行のキーと配列をたどる。どこで止めるかを変えた作業用の版（コミットしていない）で、末尾に 1 行足す変更を分けた。

| 止めた所 | 差分 |
| --- | --- |
| キーを求めた直後 | 約 27 µs |
| 先頭と末尾の共通部分を比べた直後 | 58〜59 µs |
| 共通部分を次の順の配列へまとめて写した直後 | 75〜78 µs |
| 最後まで | 116〜124 µs |

- **キー（約 27 µs、1 行あたり約 2.7 ns）:** 利用者のキー関数を 1 万回呼ぶ
- **共通部分の比較（約 31 µs）:** キーの比較と、項目が前と同じ物かの比較（`Keep`）。同じ物ならシグナルに書かない。書いていたときは、シグナル自身の比較（レコードの各欄）が差分の大半を占めた（1 万行で 1 行あたり約 26 ns）
- **配列の写し（約 17 µs）:** 共通部分のノード・スコープ・シグナル・項目を、次の順の配列へ `Array.Copy` で写す。1 行ずつ写していたときは、参照の書き込みバリアで 1 行あたり約 11 ns かかった
- **残り（約 40 µs）:** 1 行を作る・外す仕事と、使い終えた配列を消す仕事。値の変更では、同じ所が約 10 µs だった。`InsertAfter` と `DetachAfter` が親に印を付けない版では、ここが 25〜30 µs 短くなった。ただし、その版では標本の間のレイアウトの pass（2.7〜3.1 ms）も無くなる。キャッシュが温まったまま次の差分が始まるので、短くなった分を印のせいとは言えない。印を付ける `Invalidation.MarkDirty` の経路は、どの段も O(1) で、子の数に寄らない。これ以上は分けていない

順を逆にする変更では、最長増加部分列の外にある 9,999 行が 1 回ずつ動く。1 行の移動は約 85 ns だった。

### レイアウトと描画の段

- **レイアウト（2.7〜3.1 ms）:** 1 万個の子を持つ列を、1 行の変更でもまるごと並べ直す。今のレイアウトの仕組みの費用で、For の費用ではない。見える行だけを作る仮想化は、行 P02 で入れる
- **描画の段（0.4〜0.86 ms）:** 描くフレームでは、表示リストをまるごと作り直す（設計書 §5.0.1）。1 万行の矩形を書くので、変更の大きさに寄らない

### 割り当て

行の並べ替えと値の変更を繰り返す定常状態（100 行）では、差分とフレームのどちらも 0 バイトだった（`ShowForTests.SteadyState_ReorderAndValueFrames_AllocateNothing`）。

## main（50e21c9）への影響

### Counter の大きさ

| | main | V3a |
| --- | --- | --- |
| `Counter.exe` | 3,350,016 バイト | 3,350,528 バイト |

512 バイト増えた。Counter は `Show` も `For` も使わないので、`For` の本体は取り込まれない。`UiTree.ForContainers`（`HashSet<NodeHandle>`）を外した作業用の版は main と同じ大きさだったので、増えた分はこの集合による。

### フレームの段（`frames`、main と交互に）

| | main | V3a |
| --- | --- | --- |
| CPU のフレーム、中央値（7 回ずつ） | 0.083〜0.098 ms | 0.083〜0.090 ms |
| Present から表示まで、中央値（7 回ずつ） | 28.8〜31.1 ms | 32.6〜37.5 ms |

- CPU のフレームの範囲は重なる
- Present から表示までの時間は、上の 7 回ずつでは、どの回も V3a のほうが長かった。そこで、同じ main のビルドを 2 つのフォルダに置き、交互に 7 回ずつ走らせた（PR #369 のレビュー）。片方は 28.8〜37.5 ms、もう片方は 31.2〜37.7 ms で、同じ実行ファイルでも回ごとに約 9 ms 揺れた。V3a との 4〜7 ms の差はこの揺れの中に入るので、ビルドの差ではない。この場面の「Present から表示まで」は、走らせる回ごとに揺れる値で、ビルドを比べるのには使えない
