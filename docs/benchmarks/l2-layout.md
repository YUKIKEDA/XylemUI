# L2 のレイアウトの基準値

絶対配置・相対配置の insets・aspect-ratio・表示しないノードを入れた（ロードマップの行 L2、Issue #124、設計書 §3.2「L2 の方式」）後の費用を、L5 と同じ方法で測った。

## 測った物と機械

- コミット: このファイルを加えたコミット（`git log -1 -- docs/benchmarks/l2-layout.md`）
- 機械と版と作り方: L1a と同じ（`docs/benchmarks/l1a-layout.md`）。場面は L5 と同じ 4 つ（`docs/benchmarks/l5-layout.md`）に、「絶対配置の子」の場面を足した
- 新しい場面「絶対配置の子」: 100 個の箱（2,000 x 20、最小の高さ 0）を縦に並べ、各箱に 10 x 10 の葉を 100 個、絶対配置で左から 20 ずつ置く。変更は葉 1 つの内容（幅を 10 と 20 で交互）。XylemUI は `Position.Absolute` と `Inset`、Flutter は `Stack` と `Positioned`、Avalonia は `Canvas` と `Canvas.Left`。箱の最小の高さを 0 にしたのは、S6b の意味と同じく、Flutter の `Column` と Avalonia の `StackPanel` が子の内容を自動の最小サイズとして読まないため。CSS の既定のままだと、列が各箱の内容を測るので、変更が箱を越えて根の列まで伝わる

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
./benchmarks/compare/build.ps1 -Out <dir>
./benchmarks/compare/layout.ps1 -Built <dir> -Rounds 5
<dir>/xylemui/XylemUI.E2E.exe layout-loop absolute change 300000   # プロファイル用
```

- **Taffy（GPUI のレイアウト）**: Taffy の比較のアプリ（`benchmarks/compare/taffy`）に同じ場面を足した。葉の内容の幅をノードの context に持ち、変えたら `mark_dirty` する。Taffy の `mark_dirty` は根まで伝わり（境界を持たない）、根から計算し直してキャッシュに当たった子を飛ばす。子の中の変更は XylemUI の約 2 倍、最初の layout は XylemUI より 12 % 速い
- **絶対配置の子の中の変更（Flutter の約 5 倍、Avalonia の約 2.5 倍、Taffy の約半分）**: Flutter・Avalonia・XylemUI は、変わった子の箱が 100 個の子をすべて置き直す（Flutter の `RenderStack.performLayout`、Avalonia の `Canvas.ArrangeOverride`）。差は子 1 つあたりの費用で、XylemUI は約 100 ns、Flutter は約 20 ns。NativeAOT のプロファイル（`layout-loop absolute change 300000`、Visual Studio の collector）では、子ごとのスタイルの解決（大きさ・マージン・insets。`LayOutAbsoluteChild` の自身の分）が 26 %、insets で狭めた containing block が 12 %、マージンの解決が 9 %、子ごとに 2 回あるキャッシュの問い合わせ（測るだけの実行と layout の実行。`LayoutChild`・`LayoutCacheKey.Matches`・`MeasureCache.TryGet`）が合わせて約 22 %。Flutter は clean な子の制約を比べるだけで戻る。container の入力が同じ clean な子で前回の置き場所を使う仕組みは、行 L7 に置いた
- **絶対配置の子の場面の最初の layout（Flutter の約 2.3 倍、Taffy の 1.14 倍）**: 1 万個の絶対配置の子を、子ごとに測るだけの実行と layout の実行で 2 回求める。Flutter は 1 回
- **ノードの大きさ**: `UiNode` 520 バイト（main 528）、計測のキャッシュ 1 ノード 512 バイト（main 456）。L2 の 4 つの項目（`Position`・`Inset`・`AspectRatio`・`Hidden`）で `LayoutStyle` が 40 バイト増えた分を、`LayoutState.Box`（64 バイト）を計測のキャッシュへ移して打ち消した

- この組は、機械のばらつきが大きく（最大値が最小値の約 2 倍の回がある。Chrome・Cursor・Everything が CPU を使っていた）、どの指標も範囲が重なった。最小値どうしでは、1 か所の変更と固定サイズの行の中の変更が L2 で 2〜4 % 大きい（S6b の意味 20.2 → 20.7、CSS の既定 35.5 → 36.5、`%` あり 37.6 → 39.1 µs）。**この差の原因は突き止めていない**（オーナーの判断で、この記録のまま PR にした。行 L7 で、静かな機械で測り直して追う）。プロファイルでは関数ごとの差がばらつきに埋もれ、ノードを main より小さくしても残った
- **原因（行 L8 で判定、`docs/benchmarks/l8-counters.md`）:** 命令の数で数えると、L2 は 1 回の変更で 3.1〜4.6 % 増えていて、差はコードによるものだった。増えたのは、L2 の機能（表示しないノード、insets、aspect-ratio、計測のキャッシュに移した `Box`）を項目ごと・ノードごとに読む分。aspect-ratio を後の手順で項目ごとに引き直していた分は L8 で直した

**速くするために直したこと**（最初の実装から）:

- 流れの外の子が無い容器で、その処理を飛ばす: 最初の実装は、Flex と Block が流れの後にすべての子をたどり、子ごとにスタイルをコピーした。1 か所の変更が +26〜53 %、幅の変更が +30〜99 % 遅かった
- ノードが流れの外の子の数を持ち、0 なら子のスタイルを読まずに項目を数える: main は子を数えるとき `NextSibling` だけを読む。子のスタイル（ノードの別の場所）を読むと、1 か所の変更が約 5 % 遅かった（`layout-loop s6b change`、main と交互に 12 回）
- `LayoutState.Box` を計測のキャッシュへ移す: ノードが 576 から 520 バイトになった。ノードを 32 バイト小さくした実験（insets と比を持たない、測るためだけの版）では、1 か所の変更が約 4 % 速くなった
- 伸ばした項目の最大値を、比を持つ項目でだけ解き直す
- Block が子のスタイルをコピーする前に、流れの中かを確かめる: 絶対配置の子の場面の変更が 21.6 → 10.4 µs

## 受け入れ（設計書 §3.2「L2 の方式」、Issue #124）

- スキップの理由が行 L2 の Taffy の XML テストが 0 件: 満たす。L2 の機能だけを使う 204 件のうち 199 件が通る（通る数は 578 件から 777 件）。外した 5 件は、CSS の基準が親より外の祖先になる 3 件（設計: 基準は親）と、マージンの相殺を見る 2 件（設計: マージンを相殺しない）
- `Hidden` を切り替えたときの再 layout のテスト: `LayoutPositionedTests.Hidden_TakesNoRoomAndComesBack`
- 絶対配置の子と相対配置の insets の増分のテスト: `LayoutPositionedTests`、`LayoutRandomTests`（絶対配置のノードと `Hidden` の切り替えを入れた、40 の種）
- L1a・L1b の場面の指標が、main と順番をそろえて測ってばらつきを超えて遅くならない: 範囲はすべて重なる。最小値で 2〜4 % 大きい指標があり、原因は未確定（上）
- 定常状態のアロケーション 0: `SteadyState_RelayoutAfterOneChange_AllocatesNothing(scene: "positioned")`
- 絶対配置の子の中の変更を Flutter・Avalonia・GPUI（Taffy 0.9.0）と比べる: 上の表。Taffy の約半分、Avalonia の約 2.5 倍、Flutter の約 5 倍で、子ごとの費用を下げる仕組みは行 L7
