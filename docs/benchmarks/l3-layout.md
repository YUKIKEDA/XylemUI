# L3 のレイアウトの基準値

大きさのキーワード（`Stretch`、min / max の `MinContent`・`MaxContent`・`FitContent`・`Stretch`）を入れた（ロードマップの行 L3、Issue #133、設計書 §3.2「L3 の方式」）後の費用を、main と比べた。L3 は既存の場面に新しい処理の経路を足すだけなので、場面は L2 と同じ 5 つ（`docs/benchmarks/l2-layout.md`）で、他のフレームワークとの比較は測り直していない。

## 測った物と機械

- コミット: このファイルを加えたコミット（`git log -1 -- docs/benchmarks/l3-layout.md`）
- 機械と版と作り方: L1a と同じ（`docs/benchmarks/l1a-layout.md`）。NativeAOT
- 比べた相手: main（350b555）
- 順番: main・L3・L3・main を 1 組として 20 組。各回は `XylemUI.E2E.exe layout` を 1 回走らせる（1 回の中で各指標を 15 回測り、中央値を出す）。表の値は、その 40 回の中央値と最小〜最大（µs）

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>      # main とこのブランチで 1 つずつ
<dir>/XylemUI.E2E.exe layout                                               # 1 回分の JSON
<dir>/XylemUI.E2E.exe layout-loop auto_min change 100000                   # 1 つの指標を絞って比べるとき
```

- どの指標も、main と L3 の範囲が重なった。この 2 組は機械のばらつきが大きい（最大値が最小値の 2 倍を超える回がある。Cursor・Chrome・Everything が CPU の 10〜15 % を使っていた）
- 最初の layout の中央値は、組によって −1.3〜+6.8 % と動き、向きがそろわない。1 か所の変更は、どちらの組でも +0.5〜2.9 % の側にある
- 1 か所の変更を絞って測った（`layout-loop <場面> change 100000`、main・L3・L3・main を 6 組）。S6b の意味は −0.1 %、絶対配置の子は −1.5〜+0.7 %、CSS の既定は +1.4〜1.8 % だった。CSS の既定の差をプロファイル（NativeAOT、Visual Studio の collector、40 万回）で見ると、関数ごとの割合の差は ±0.8 ポイントの中で、`GenerateFlexItems` が +0.8 ポイント（項目ごとに、キーワードの印の読み出しと、`stretch` の交差軸の比較が 1 つずつ増えた）。ほかの差は、同じコードの関数どうしでも測るたびに入れ替わる大きさだった
- **ノードの大きさ**: `UiNode` 520 バイト、計測のキャッシュ 1 ノード 512 バイト。どちらも main と同じ（`LayoutState` に足した 1 バイトの印は、既存の詰め物に入った）

**速くするために直したこと**（最初の実装から）:

- Flex の項目のキーワードの確かめを、基準の大きさの引き継ぎ（`FlexBaseMemo`）の後ろに置き、キーワードの制限を持つ項目は引き継ぎを持たないようにした: 引き継ぎの前に置くと、CSS の既定の 1 か所の変更が main より 3.1 % 遅く、外すと 1.1 % だった（`layout-loop auto_min change`、main と交互に 12 回ずつ）
- 子がキーワードの制限を持つかを、スタイルを設定したときにノードの印（`LayoutState.HasKeywordLimits`）にして、Flex・Block・絶対配置はそれを読む: 絶対配置の子ごとにスタイルの 4 つの制限を読んでコピーすると、子の中の変更が main より 5.2 % 遅く、印にすると 0.7 % だった（`layout-loop absolute change`、main と交互に 12 回ずつ）

## 受け入れ（設計書 §3.2「L3 の方式」、Issue #133）

| 項目 | 結果 |
| --- | --- |
| スキップの理由が行 L3 の Taffy の XML テストが 0 件 | 満たす。`stretch` の 24 件のうち 14 件が通る。子のマージンが親の辺と接して Chrome が相殺する 4 件は、マージンを相殺しない設計（§3.2）の理由で外した。残る 6 件は、float（設計に無い）が 4 件、`overflow`（行 V2）が 2 件で外れる。`flex-basis: content` の 2 件は理由を行 V2 にした |
| Chrome から作ったテストが全件通る | 満たす。30 件（`tests/XylemUI.Core.Tests/Fixtures/XylemUI/`、Chrome for Testing 155.0.8059.84） |
| L1a・L1b・L2 の場面の指標が、main と順番をそろえて測ってばらつきを超えて遅くならない | 満たす。どの指標も範囲が重なる（上の表） |
| 定常状態のアロケーション 0 | 満たす。キーワードの制限を持つ葉を含む木の 1 か所の変更で 0 バイト（`LayoutGuardTests` の `keywords`） |
