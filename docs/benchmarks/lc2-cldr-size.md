# LC2: CLDR の表を入れた時のバイナリの大きさ

行 LC2 の「表の持ち方」と「地域から文字体系を補う推定」を決めるための計測（spike、Issue #862、設計書 §4.11「書式」）。Windows 11 26300、NativeAOT の Release（win-x64）で測った。

spike のコードは main に入れていない。ブランチ `spike/862-cldr-size`（`5de54ae`）の `spike/CldrSize/` と `tools/CldrSizeSpike/` にある。

## 何を測ったか

XylemUI を参照しない、何もしないコンソールのプログラム（935,424 バイト）に表を足し、実行ファイルがどれだけ大きくなるかを測った。

- **データ:** CLDR 49.0.0（cldr-json の `cldr-49.0.0-json-full.zip`、SHA-256 `3B1F5D684D29C541D3ACF91FE834B3FE36AE0F34775E3EE50E93558BF14CA174`）
- **表の種類:** 複数形と序数の規則、数値（記号と書式）、日付（名前、書式、週と時刻のデータ）、地域から文字体系を補う表（likelySubtags）
- **ロケールの数:** 1 個（ja）、10 個（en、ja、zh-Hans、zh-Hant、de、fr、es、ko、ar、ru）、全部（網羅の水準が modern の 420 個）
- **持ち方:**
  - (a) 宣言したロケールのデータだけをソースに入れる
  - (b) 420 個すべてのデータをソースに入れる。ロケールごとの入口を、式の本体で書いた `static ReadOnlySpan<byte>` のプロパティにし、アプリは宣言したロケールだけを参照する

## 結果: 基準からの増分（バイト）

| 表の種類 | 1 個 | 10 個 | 420 個 |
| --- | ---: | ---: | ---: |
| 複数形と序数 | 0 | 1,536 | 17,920 |
| 数値 | 1,024 | 10,752 | 176,128 |
| 日付 | 1,536 | 16,896 | 420,352 |
| 3 つと likelySubtags の合計 | 82,944 | 108,544 | 693,760 |

likelySubtags だけを入れると +80,384 バイトである（7,868 件の 1 つの表。宣言したロケールの数に依らない）。

- **(a) と (b) は、1 個でも 10 個でも、1 バイトも違わなかった。** NativeAOT は、参照されないロケールのプロパティと、その後ろのデータを落とす。ILC のマップファイルで数えた生成データの増分も、参照したロケールの生のデータの大きさと一致した（10 個の合計で 107,228 バイト）
- 実行ファイルの増分は、生のデータの大きさにほぼ等しい（ファイルの区切りで 512 バイト単位に丸まる）。複数形 1 個が 0 なのは、35 バイトが丸めに収まったためである
- 10 個のロケールで、3 つの表は合わせて約 28 KB である（108,544 − 80,384）

## 単純化したこと

- 日付のスケルトンの書式 20,160 個のうち 5,650 個は CLDR に無く、近い長さのもので埋めた
- 通貨の記号と名前、単位、相対時間、日付の解析用のデータは入れていない。数字は、既定の数字の種類だけである
- 文字列の重複は、1 つの表の中だけで除いた。圧縮はしていない
- 表を読むコードは、数バイトを読んで足し合わせるだけである。書式を組み立てるコードの大きさは含まない

## 再現

```powershell
git switch spike/862-cldr-size
python -I tools/CldrSizeSpike/generate.py --zip <path>\cldr-49.0.0-json-full.zip
./spike/CldrSize/measure.ps1 -OutRoot <scratch>\cldr-size -MapFile
```

22 個の構成を順に発行する。全部で約 7 分かかった。

## 期間の書式と通貨の記号（Issue #887）

行 LC2 の手順 1 の計測（設計書 §4.11「実装の前に測ること」）。上の spike の生成器に 2 つの表を足し、同じ方法（NativeAOT の Release、win-x64、ILC のマップファイル）で測った。2026-11-14、Windows 11（ビルド 26300）、Intel Core i5-13400F、.NET SDK 10.0.403。大きさの計測なので、CPU の負荷は結果に効かない。

spike のコードは main に入れていない。ブランチ `spike/887-lc2-size`の `spike/CldrSize/` と `tools/CldrSizeSpike/` にある。上の 22 個の構成は、生成するファイルが 1 バイトも変わらないので、同じブランチで再現できる。

### 何を測ったか

- **データ:** 上と同じ CLDR 49.0.0
- **期間の書式:** `ca-gregorian.json` の `dateTimeFormats.intervalFormats` のうち、`intervalFormatFallback` と、Flutter の 41 個のスケルトンに当たる項目である。`j` を含むスケルトンは `h` と `H` の 2 つに読み替え、重なるもの（`H` で読んだ `jm` は `Hm`）を除いた 45 個を、CLDR の鍵と文字どおり一致するかで引いた。近いスケルトンを探す手順は使っていない。項目には、違う欄（`y`、`M`、`d`、`G`、`a`、`B`、`h`、`H`、`m`）ごとの書式を入れた。項目を持つのは、422 個の表 × 45 個の 18,990 個のうち 10,349 個である
- **通貨の記号:** ロケールの `currencies.json` にある全部の通貨の、標準の形（`symbol`）と narrow の形（`symbol-alt-narrow`）である。標準の形が ISO 4217 のコードと同じものと、narrow の形が標準の形（標準の形が無ければコード）と同じものは入れていない。読む側は CLDR のとおりそこへ戻るので、失う値は無い。422 個の表で、通貨は延べ 114,219 個、入れた記号は 49,813 個である
- **ロケールの数:** 1 個（ja）、10 個（上と同じ）、全部。全部は、設計書 §4.11「ロケールの組」のとおりに生成器が数えた。modern の 420 個から変種を持つ 3 つ（`be-tarask`、`ca-ES-valencia`、`el-polyton`）を除き、`nb`、`bo`、`gsw`、`ug` を足した 421 個の表と、`root`（cldr-json の `und` のファイル）と、`fil` の表を指す `tl` の入口で、合わせて 423 個である。設計書 §4.11 の数え方では、`CldrLocales` の入口は `tl` を含めて 422 個で、`root` は `LocaleData.Root` である。この記録の「423 の入口」は、`root` も 1 つに数えた数である
- **持ち方:** (b) だけである。423 個すべてのデータをソースに入れ、アプリは宣言したロケールだけを参照する
- **比べ方:** 3 つの表と likelySubtags を入れた構成（`c-base-1`、`c-base-10`、`c-base-all`）を基準にし、期間の書式、通貨の記号、その両方を足した構成との差を、その表の増分とした

文字列の重複は、上と同じく 1 つの表の中だけで除いた（記号と narrow の形が同じなら 1 度だけ持つ）。中身が同じ表は 1 つを共有する（`tl` は `fil` の表を指す）。圧縮はしていない。

### 結果: 3 つの表と likelySubtags からの増分（バイト）

| 足した表 | 1 個 | 10 個 | 全部（423 の入口） |
| --- | ---: | ---: | ---: |
| 期間の書式 | 1,024 | 10,240 | 141,312 |
| 通貨の記号 | 512 | 9,216 | 216,064 |
| 両方 | 1,536 | 18,944 | 356,864 |

1 個と 10 個の列は、どれも 512 バイトの倍数である。実行ファイルの節が 512 バイトずつ並ぶためで、この 2 つの列は ±512 バイトの幅で読む値である（生のデータは、1 個で期間の書式が 890、通貨の記号が 803 バイト）。全部の列は、512 バイトより十分大きい。

基準の構成そのものの、何もしないプログラムからの増分は、1 個で 82,944、10 個で 108,544、全部で 701,440 バイトである。上の 420 個（693,760 バイト）との差は、ロケールの組を変えた分である。ILC のマップファイルで数えた生成データの増分は、下の生のデータの大きさと 1 バイトも違わなかった（全部で、期間の書式 128,375、通貨の記号 202,509、両方 330,884）。実行ファイルの増分は、それより大きい（全部で、期間の書式 +12,937、通貨の記号 +13,555）。423 の入口で割ると、1 つあたり 31〜32 バイトである。ロケールごとの入口（表を返すプロパティと、それを選ぶ分岐）のコードの分と見ている。マップファイルのコードの節は読んでいないので、内訳は確かめていない。

生のデータ（コンパイルする前。中身が同じ表は 1 度だけ数えた）は、次のとおりである。

| 表 | 1 個 | 10 個 | 全部（423 の入口） |
| --- | ---: | ---: | ---: |
| 期間の書式 | 890 | 9,643 | 128,375（136 個の表） |
| 通貨の記号 | 803 | 8,625 | 202,509（245 個の表） |
| 通貨の記号（コードや標準の形と同じものも入れた場合。測っていない） | 866 | 10,643 | 298,732（248 個の表） |
| 3 つの表（基準） | 2,194 | 27,113 | 582,296 |

3 つの表の全部は、上の 420 個（575,015 バイト）より 7,281 バイト大きい。`bo`、`gsw`、`ug`、`root` の数値と日付の表が増え、`el-polyton` の日付の表が減った。

### 測っていないこと

- 名前（`displayName`）、`symbol-alt-variant`、通貨の小数の桁（`currencyData`）は入れていない
- `intervalFormats` の `intervalFormatRanges` は入れていない
- 41 個に無いスケルトン（`Bh`、`GyMMMd` など）の項目は入れていない。41 個のうち CLDR に項目の無いもの（`E`、`QQQ`、`jmz` と `jz` を読み替えた 4 個など）は、実行時に `intervalFormatFallback` でつなぐので、データは要らない
- 鍵（`interval/yMMMd/d`、`currency-symbol/USD` など 345 個）の文字列は、本物の実装ではコードに入るので数えていない。上の 304 個と同じ扱いである
- 期間の書式を組み立てるコードと、記号を引くコードの大きさは含まない
- 上の記録が未計測とした、週末の曜日、`gmtFormat`、複数形の規則のメソッドの形、`XylemUI.Core.dll` の増分は、実装の PR が測る
