# LC2: CLDR の表を入れた時のバイナリの大きさ

行 LC2 の「表の持ち方」と「地域から文字体系を補う推定」を決めるための計測（spike、Issue #862、設計書 §4.11「書式」）。Windows 11 26300、NativeAOT の Release（win-x64）で測った。

spike のコードは main に入れていない。ブランチ `spike/862-cldr-size`（`5de54ae`）の `spike/CldrSize/` と `tools/CldrSizeSpike/` にある。

## 何を測ったか

XylemUI を参照しない、何もしないコンソールのプログラム（935,424 バイト）に表を足し、実行ファイルがどれだけ大きくなるかを測った。

- **データ:** CLDR 49.0.0（cldr-json の `cldr-49.0.0-json-full.zip`、SHA-256 `3B1F5D684D29C541D3ACF91FE834B3FE36AE0F34775E3EE50E93558BF14CA174`）
- **表の種類:** 複数形と序数の規則、数値（記号と書式）、日付（名前、書式、週と時刻のデータ）、地域から文字体系を補う表（likelySubtags）
- **ロケールの数:** 1 個（ja）、10 個（en、ja、zh-Hans、zh-Hant、de、fr、es、ko、ar、ru）、全部（網羅の水準が modern の 420 個）
- **持ち方:**
  - (a) 宣言したロケールのデータだけをソースに入れる
  - (b) 420 個すべてのデータをソースに入れる。ロケールごとの入口を、式の本体で書いた `static ReadOnlySpan<byte>` のプロパティにし、アプリは宣言したロケールだけを参照する

## 結果: 基準からの増分（バイト）

| 表の種類 | 1 個 | 10 個 | 420 個 |
| --- | ---: | ---: | ---: |
| 複数形と序数 | 0 | 1,536 | 17,920 |
| 数値 | 1,024 | 10,752 | 176,128 |
| 日付 | 1,536 | 16,896 | 420,352 |
| 3 つと likelySubtags の合計 | 82,944 | 108,544 | 693,760 |

likelySubtags だけを入れると +80,384 バイトである（7,868 件の 1 つの表。宣言したロケールの数に依らない）。

- **(a) と (b) は、1 個でも 10 個でも、1 バイトも違わなかった。** NativeAOT は、参照されないロケールのプロパティと、その後ろのデータを落とす。ILC のマップファイルで数えた生成データの増分も、参照したロケールの生のデータの大きさと一致した（10 個の合計で 107,228 バイト）
- 実行ファイルの増分は、生のデータの大きさにほぼ等しい（ファイルの区切りで 512 バイト単位に丸まる）。複数形 1 個が 0 なのは、35 バイトが丸めに収まったためである
- 10 個のロケールで、3 つの表は合わせて約 28 KB である（108,544 − 80,384）

## 単純化したこと

- 日付のスケルトンの書式 20,160 個のうち 5,650 個は CLDR に無く、近い長さのもので埋めた
- 通貨の記号と名前、単位、相対時間、日付の解析用のデータは入れていない。数字は、既定の数字の種類だけである
- 文字列の重複は、1 つの表の中だけで除いた。圧縮はしていない
- 表を読むコードは、数バイトを読んで足し合わせるだけである。書式を組み立てるコードの大きさは含まない

./spike/CldrSize/measure.ps1 -OutRoot <scratch>\cldr-size -MapFile

## 期間の書式と通貨の記号（Issue #887）

行 LC2 の手順 1 の計測（設計書 §4.11「実装の前に測ること」）。上の spike の生成器に 2 つの表を足し、同じ方法（NativeAOT の Release、win-x64、ILC のマップファイル）で測った。2026-11-14、Windows 11（ビルド 26300）、Intel Core i5-13400F、.NET SDK 10.0.403。大きさの計測なので、CPU の負荷は結果に効かない。

spike のコードは main に入れていない。ブランチ `spike/887-lc2-size`の `spike/CldrSize/` と `tools/CldrSizeSpike/` にある。上の 22 個の構成は、生成するファイルが 1 バイトも変わらないので、同じブランチで再現できる。

### 何を測ったか

- **データ:** 上と同じ CLDR 49.0.0
- **期間の書式:** `ca-gregorian.json` の `dateTimeFormats.intervalFormats` のうち、`intervalFormatFallback` と、Flutter の 41 個のスケルトンに当たる項目である。`j` を含むスケルトンは `h` と `H` の 2 つに読み替え、重なるもの（`H` で読んだ `jm` は `Hm`）を除いた 45 個を、CLDR の鍵と文字どおり一致するかで引いた。近いスケルトンを探す手順は使っていない。項目には、違う欄（`y`、`M`、`d`、`G`、`a`、`B`、`h`、`H`、`m`）ごとの書式を入れた。項目を持つのは、422 個の表 × 45 個の 18,990 個のうち 10,349 個である
- **通貨の記号:** ロケールの `currencies.json` にある全部の通貨の、標準の形（`symbol`）と narrow の形（`symbol-alt-narrow`）である。標準の形が ISO 4217 のコードと同じものと、narrow の形が標準の形（標準の形が無ければコード）と同じものは入れていない。読む側は CLDR のとおりそこへ戻るので、失う値は無い。422 個の表で、通貨は延べ 114,219 個、入れた記号は 49,813 個である
- **ロケールの数:** 1 個（ja）、10 個（上と同じ）、全部。全部は、設計書 §4.11「ロケールの組」のとおりに生成器が数えた。modern の 420 個から変種を持つ 3 つ（`be-tarask`、`ca-ES-valencia`、`el-polyton`）を除き、`nb`、`bo`、`gsw`、`ug` を足した 421 個の表と、`root`（cldr-json の `und` のファイル）と、`fil` の表を指す `tl` の入口で、合わせて 423 個である。設計書 §4.11 の数え方では、`CldrLocales` の入口は `tl` を含めて 422 個で、`root` は `LocaleData.Root` である。この記録の「423 の入口」は、`root` も 1 つに数えた数である
- **持ち方:** (b) だけである。423 個すべてのデータをソースに入れ、アプリは宣言したロケールだけを参照する
- **比べ方:** 3 つの表と likelySubtags を入れた構成（`c-base-1`、`c-base-10`、`c-base-all`）を基準にし、期間の書式、通貨の記号、その両方を足した構成との差を、その表の増分とした

文字列の重複は、上と同じく 1 つの表の中だけで除いた（記号と narrow の形が同じなら 1 度だけ持つ）。中身が同じ表は 1 つを共有する（`tl` は `fil` の表を指す）。圧縮はしていない。

### 結果: 3 つの表と likelySubtags からの増分（バイト）

| 足した表 | 1 個 | 10 個 | 全部（423 の入口） |
| --- | ---: | ---: | ---: |
| 期間の書式 | 1,024 | 10,240 | 141,312 |
| 通貨の記号 | 512 | 9,216 | 216,064 |
| 両方 | 1,536 | 18,944 | 356,864 |

1 個と 10 個の列は、どれも 512 バイトの倍数である。実行ファイルの節が 512 バイトずつ並ぶためで、この 2 つの列は ±512 バイトの幅で読む値である（生のデータは、1 個で期間の書式が 890、通貨の記号が 803 バイト）。全部の列は、512 バイトより十分大きい。

基準の構成そのものの、何もしないプログラムからの増分は、1 個で 82,944、10 個で 108,544、全部で 701,440 バイトである。上の 420 個（693,760 バイト）との差は、ロケールの組を変えた分である。ILC のマップファイルで数えた生成データの増分は、下の生のデータの大きさと 1 バイトも違わなかった（全部で、期間の書式 128,375、通貨の記号 202,509、両方 330,884）。実行ファイルの増分は、それより大きい（全部で、期間の書式 +12,937、通貨の記号 +13,555）。423 の入口で割ると、1 つあたり 31〜32 バイトである。ロケールごとの入口（表を返すプロパティと、それを選ぶ分岐）のコードの分と見ている。マップファイルのコードの節は読んでいないので、内訳は確かめていない。

生のデータ（コンパイルする前。中身が同じ表は 1 度だけ数えた）は、次のとおりである。

| 表 | 1 個 | 10 個 | 全部（423 の入口） |
| --- | ---: | ---: | ---: |
| 期間の書式 | 890 | 9,643 | 128,375（136 個の表） |
| 通貨の記号 | 803 | 8,625 | 202,509（245 個の表） |
| 通貨の記号（コードや標準の形と同じものも入れた場合。測っていない） | 866 | 10,643 | 298,732（248 個の表） |
| 3 つの表（基準） | 2,194 | 27,113 | 582,296 |

3 つの表の全部は、上の 420 個（575,015 バイト）より 7,281 バイト大きい。`bo`、`gsw`、`ug`、`root` の数値と日付の表が増え、`el-polyton` の日付の表が減った。

### 測っていないこと

- 名前（`displayName`）、`symbol-alt-variant`、通貨の小数の桁（`currencyData`）は入れていない
- `intervalFormats` の `intervalFormatRanges` は入れていない
- 41 個に無いスケルトン（`Bh`、`GyMMMd` など）の項目は入れていない。41 個のうち CLDR に項目の無いもの（`E`、`QQQ`、`jmz` と `jz` を読み替えた 4 個など）は、実行時に `intervalFormatFallback` でつなぐので、データは要らない
- 鍵（`interval/yMMMd/d`、`currency-symbol/USD` など 345 個）の文字列は、本物の実装ではコードに入るので数えていない。上の 304 個と同じ扱いである
- 期間の書式を組み立てるコードと、記号を引くコードの大きさは含まない
- 上の記録が未計測とした、週末の曜日、`gmtFormat`、複数形の規則のメソッドの形、`XylemUI.Core.dll` の増分は、実装の PR が測る

## 宣言したロケールと、ロケールごとのクラス（行 LC2 の実装の 3 つ目）

アプリがロケールを宣言できるようになった PR の計測（設計書 §4.11、行 LC2 の (3)）。2026-11-20、Windows 11（ビルド 26300）、Intel Core i5-13400F、.NET SDK 10.0.403。`samples/Counter` を、NativeAOT の Release、win-x64、`-p:IlcGenerateMapFile=true` で発行し、ILC のマップファイルの節を名前ごとに足した。宣言は、`Program.cs` の `new WindowOptions("Counter", 320, 200)` に `{ SupportedLocales = … }` を一時的に足して変えた（変更はコミットしていない。Issue #906 でオーナーが決定）。main は `5d2e3ee`（実装の 2 つ目と行 PL1 の 4a が入った後）、ブランチは PR #941 の `f60c7ce` である（2026-11-21 に測り直した。初めの計測は、宣言の一覧を `Array.AsReadOnly` で包んでいた時のもので、下の「解決のコード」に残してある）。main とブランチは、同じネイティブのライブラリ（`vendor/out`、`vendor/versions.lock` の版）で発行した。

今のロケールごとのクラス（`CldrJa` など、423 個）は、表のバイト列を持たない。持つのは、型の情報、`Instance` の静的な欄とその初期化（ロケールのタグの文字列と週の 4 つの値を渡す）である。数値と日付の表は、実装の 4 つ目と 5 つ目で増える。

| --- | ---: | ---: | ---: | ---: |
| main | 5,450,240 | | 2,572,837 | |
| 宣言なし | 5,470,208 | +19,968 | 2,591,015 | +18,178 |
| 1 個（`Ja`） | 5,473,280 | +3,072 | 2,593,019 | +2,004 |
| 2 個（`En`・`Ja`） | 5,473,280 | 0 | 2,593,079 | +60 |

| 全部（`CldrLocales.All`、422 個と root） | 5,701,632 | +224,768 | 2,814,405 | +217,186 |

- **ロケールのクラス 1 つ:** 名前に `CldrJa` を含む節は 7 つで、合わせて 335 バイトである。内訳は、静的な欄を初期化するコード（`.cctor`）180、型の情報 96、静的な欄の基底を取る補助 22、GC の情報 13、静的な欄と書き込めるデータが 8 ずつ 3 つである。データのバイト列（`FieldRvaData`）は無い。コンストラクターの節は無い（静的な欄を初期化するコードに取り込まれている）。`CreatePlurals` と複数形の規則（`CldrPluralRules`、`PluralRules`）の節も無い。Counter は複数形を読まないので落ちている。複数形を使うアプリでは、ロケールのクラス 1 つはこの 335 バイトより大きくなる（測っていない）
- **参照しないロケールは落ちる:** 2 個の構成のマップにあるロケールのクラスは、`CldrEn`・`CldrJa`・`CldrRoot` の 3 つだけである（設計書 §4.11「大きさ」の確かめ）
- **10 個:** 名前に `Cldr` を含む節は、宣言なしの 251 バイト（`CldrRoot`）から 3,737 バイトになる。ロケール 1 個あたり 349 バイトである。マップの全体では 2 個から 10 個で 4,140 バイト増え、1 個あたり 518 バイトである（クラスの外の、メタデータ、スタックトレースの対応表、凍結した文字列、`Main` のコードの分を含む）
- **全部:** 10 個から 217,186 バイト増える。10 個の構成はすでに 11 個のクラス（10 個と `CldrRoot`）を持ち、全部は 423 個なので、増えたのは 412 個で、1 個あたり 527 バイトである。実行ファイルは 224,768 バイト増えた。マップとの開き 7,582 バイトは、PR #944 の後の main（`1a41ed1`）で測り直すと、10 個から全部で実行ファイル +223,744、マップ +217,198、開き +6,546 だった。`dumpbin /headers` で分けると、マップが数えないメソッドごとの巻き戻しの表（`.pdata`）+8,604 と再配置の表（`.reloc`）+5,056、節の 512 バイト揃え −3,708、`.text`・`.rdata`・`.data` の中の残り −3,406 である（残りが負なのは、マップが数えて節を増やさない物があるためで、どれかは確かめていない）。このうち `CldrAll` の一覧を作るコードが 21,588 バイト（GC の情報と合わせて 22,589）、メタデータが 14,537、凍結したオブジェクトが 13,104、スタックトレースの対応表が 8,891 である。名前に `Cldr` を含む節は 172,342 バイトで、`CldrAll` を除くと 423 個で 1 個あたり 354 バイトである
- **1 個から 2 個で実行ファイルが変わらない:** マップの差は 60 バイトで、節の区切り（512 バイト）に収まった。要素が 1 つの時と 2 つの時で、コレクション式が作る読み取り専用の一覧の型が替わる分（`ReadOnlySingleElementList` と `ReadOnlyArray`）が、ロケールのクラス 1 つの分とほぼ打ち消す
- **宣言なしで main から +18,178 バイト（実行ファイルは +19,968）:** 510 個の節が変わる。種類ごとには、型の情報 6,268、コード 5,400、メタデータ 1,109、GC の情報 805 などである。足された主なものは、`WindowLocale` の表を選ぶコード、`Localization.Provide`、Windows の時刻の書式の読み取り（`Win32TimeFormat`）、`Signal<LocaleData>`・`Computed<Locale>`・`ConditionalWeakTable` などのジェネリックの型の情報である
- **解決のコード（初めの計測で見つけたこと）:** 宣言の一覧を `Array.AsReadOnly` で包んで解決の関数に渡していた時は、`Localization.Resolve` が 1,684 から 3,228、`First` が 356 から 661、`FirstOfScript` が 420 から 723 バイトになっていた（ソースは変えていない。PR #941 のレビューの見立て）。包まずに配列を渡す形で発行して確かめると、3 つは 1,684・356・420 バイトに戻り、マップの合計は 2,974 バイト（うちコード 2,515）、実行ファイルは 3,584 バイト小さくなった。包んだ一覧は、アプリの解決の関数が配列にキャストして書き換えるのを防ぐためのものだった。包むのをやめ（Issue #906 でオーナーが決定）、解決の関数は渡された一覧を変えないと `WindowOptions.ResolveLocale` と `HeadlessOptions.ResolveLocale` の説明に書いた。上の表は、包むのをやめた後に測り直した値である
- **実行ファイルの差とマップの差の間（宣言なしで 1,790 バイト）:** 比べる相手の、PR #941 の前の main を発行し直していないので、測り直していない。同じ構成の差の分け方は、下の「数値の表」の節にある（大半は、マップが数えない `.pdata` と `.reloc` である）

### spike の見積もりとの比べ

上の spike は、ロケールごとの入口を「式の本体で書いた `static ReadOnlySpan<byte>` のプロパティ」として測り、複数形と序数の表だけなら 10 個で 1,536 バイト（1 個あたり約 154 バイト）だった。実装のロケールごとのクラスは、表のデータがまだ無いのに 1 個あたり 335〜354 バイト（クラスの節だけ）、マップの全体では 518〜527 バイトである。差は、クラスにしたことの分（型の情報 96、静的な欄の初期化のコード 180 など）である。全部を宣言したアプリの実行ファイルは、宣言なしから 231,424 バイト（5,701,632 − 5,470,208）、main から 251,392 バイト（5,701,632 − 5,450,240）増える（10 個から全部への差は 224,768 バイト）。

### 実装の 2 つ目の後の main の値

上の「文字体系だけの likelySubtags」の節の値は、PR #936 のレビューの直しの前のブランチで測った。解決の順を変えた後の main（`a80a733`）では、`Localization` と `LikelyScripts` のコードは合わせて 3,547 バイト（`Resolve` 1,684、`FirstOfScript` 420、`First` 356、`Fits` 330、`LikelyScripts` の 5 つのメソッド 682、静的な初期化 75）で、表のデータ 37,505 バイトは変わらない。

## 数値の表（行 LC2 の実装の 4 つ目）

数値の書式と解析を入れた PR #944 の計測（設計書 §4.11、行 LC2 の (4)）。2026-11-22、Windows 11（ビルド 26300）、Intel Core i5-13400F、.NET SDK 10.0.403。PR #944 のレビューの後の先端（`b6291aa`。短縮の複数形、桁の上限、`double` の丸め、通貨の記号の書記素の判定を生成器に移した後）で測り直した。

`samples/Counter` を、NativeAOT の Release、win-x64、`-p:IlcGenerateMapFile=true` で発行し、ILC のマップファイルの節を名前ごとに足した。実行ファイルの節は `dumpbin /headers` で読んだ。比べる相手は、同じブランチで書式を呼ばない構成（`Program.cs` は変えない）である。`Main` を一時的に変え、宣言したロケールごとに書式を 1 度ずつ呼んだ（`DecimalFormat`、`PercentFormat`、`NumberFormatter.Currency(locale, "JPY")`、`NumberFormatter.Compact(locale, CompactStyle.Short)` の `TryFormat`。変更はコミットしていない）。main（`1a41ed1`）と、すべての構成を、同じネイティブのライブラリで発行した。

### 1 回の書式の時間

`benchmarks/XylemUI.E2E` の `number-format`（窓を開かない）で、`en` と `ja` の 4 つの書式を、`decimal` と `double` の値で測った。1 万回の空回しの後、20 万回を 7 回測り、1 回あたりの中央値を取った。NativeAOT の Release、論理プロセッサ 2 に固定、優先度は高、3 回の実行の中央値である（2026-11-22 00:57、実行の前の負荷は 18〜53%）。

| 書式（`en`） | `TryFormat`（`decimal`） | `TryFormat`（`double`） | `Of` を文字に書く（`decimal`） | `Of` を文字に書く（`double`） |
| --- | ---: | ---: | ---: | ---: |
| 小数（1234.5） | 68.9 ns | 114.9 ns | 75.0 ns | 121.6 ns |
| 百分率（0.256） | 62.8 ns | 95.5 ns | 75.8 ns | 100.0 ns |
| 通貨 USD（1234.5） | 72.8 ns | 124.0 ns | 77.6 ns | 122.7 ns |
| 短縮（1234567） | 192.1 ns | 240.6 ns | 193.7 ns | 250.1 ns |

- `ja` も同じ幅である（62.7〜207.4 ns）
- 割り当ては、32 通りのすべてで 0 バイトである（`GC.GetAllocatedBytesForCurrentThread` を 7 回の前後で読んだ）
- `double` は、最短の往復の桁を作る分（`double.TryFormat`）だけ `decimal` より遅い。短縮は、表す数を丸めてから見せる数を作る分だけ遅い
- 1 フレームの予算 16.7 ms に対し、書式 1 つは 0.0003 ms より短い

### spike の見積もりとの比べ

上の spike は、数値の表を 10 個で 10,752、420 個で 176,128 バイト、通貨の記号を別に 202,509 バイト（Issue #887）と見積もった。実装のデータは、10 個で 17,366、全部で 279,920 バイトである（短縮の形と通貨の記号を含む）。spike が数えていなかったのは、ロケールごとの表の入口と書式のコードで、全部を宣言して 4 つの書式を呼ぶアプリでは、コードがデータとほぼ同じ大きさ（267,441 バイト）になる。

### 再現

`Main` を、宣言したロケールの並びを回して 4 つの書式の `TryFormat` を呼ぶ形に書き換え、構成ごとに `dotnet publish samples/Counter -c Release -r win-x64 -p:IlcGenerateMapFile=true` で発行して、マップと `dumpbin /headers` の節を比べる。時間は `dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64` の後、`XylemUI.E2E.exe number-format` を論理プロセッサ 2 に固定して走らせる。
