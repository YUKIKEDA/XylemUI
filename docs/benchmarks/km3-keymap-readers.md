# KM3: キーマップの行の数と、開いたままの読み手

キーごとの時間が既定の行の数でどう変わるか、最初のキーマップを作る時間の内訳、開いたままの読み手がいるウィンドウでノードの付け外しが続くフレーム、の 3 つを測った（ロードマップの行 KM3、Issue #829、設計書 §7「読み直しの知らせ」）。この記録は、直す前の値と、それをもとに決めたこと、直した後の値（末尾）である。

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe keymap'                  # キーごとの時間と行の数、最初のキーマップ
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe keymap --first-pieces'   # 最初のキーマップの内訳
cmd /c 'start /b /wait /affinity 4 /high "" <dir>\XylemUI.E2E.exe readers'                 # 読み手とスクロール
```

どれもウィンドウを開かない。場面のコード（`KeymapCost.cs` の追加と `ReaderCost.cs`）は、実装の PR で入る。この記録の値は、その場面のコミット `fc63536`（main `05e1ab4` の上）を測ったものである。

- `keymap`: 既定の行（87）に、部品の行と同じ形の行を足して、200・400・800 行にする。足す行は、既定の行のキーを順に繰り返し、条件の部品の名前だけを変える。フォーカスの文脈では、どれも成り立たない。合わないキー（A）、複数の部品が最初のキーに持つキー（Space。どの条件も成り立たず、キーのハンドラへ進む）、合うキー（Enter。根が動作を受ける）を、深さ 1 と 50 で測る。
- `keymap --first-pieces`: 最初のキーマップを作る前に、キーの文字列の解析と、条件の解析を 1 回ずつ走らせる。別のプロセスで測る。
- `readers`: 420 × 360 のウィンドウ（文字あり、GPU なし）に、読み手の箱を N 個並べた行、フォーカスのある 1 行の欄、1 万行（1 行 20）の仮想化した一覧を置く。読み手 1 個は、`CanDispatch(action)` と `KeyBindingFor(action)` を読む計算を 1 つずつと、その 2 つを読む Effect を 1 つ持つ（ツールバーのボタンの形）。動作は、欄の動作 20 種類。1 フレームは、一覧を 1 行ぶんスクロールして `RunFrame` を呼ぶ。100 フレームの後の 1,000 フレームを測る。

## 計測

NativeAOT の Release（`win-x64`）、`fc63536`。論理プロセッサ 2 に固定し、優先度を High にした。場面ごとに 8 回流した。値は中央値で、角かっこは範囲。CPU の負荷は、始める前に 10 % だった。発行の警告は 0。単位は、断りが無ければ µs。

### 読み手とスクロール（`readers`）

| | 読み手 0 個 | 読み手 20 個 |
| --- | --- | --- |
| フレームの時間（中央値） | 9.3 [8.5..15.2] | 1,161 [1,158..1,168] |
| フレームの時間（p95） | 12.25 [10.7..19.6] | 1,287 [1,231..1,988] |
| フレームの時間（p99） | 15.3 [12.9..29.2] | 1,541 [1,290..2,470] |
| 1 フレームの割り当て（バイト） | 641.8 | 137,900 |
| 1 フレームに作る行 | 1 | 1 |
| 「実行できるか」の読み直し（1 フレーム） | 0 | 1,560 |
| キーの引き直し（1 フレーム） | 0 | 1,560 |
| 読み手の Effect の実行（1 フレーム） | 0 | 0 |

- **読み手 1 個が、1 フレームに 78 回読み直す。** 答えは変わらないので、Effect は 1 回も走らない。読み直しだけで、フレームは約 125 倍になり、60 Hz の 1 フレーム（16,667 µs）の約 7 % を使う。
- **原因は 2 つ重なっている。**
  - 仮想化した一覧は、行が 1 つ入れ替わるたびに、箱の子を全部外して、全部付け直す（`src/XylemUI.Core/Elements/VirtualBlock.cs` の `Relink`）。この場面では、外すのと付けるのを合わせて約 78 回になる。
  - 外すたび、付けるたびに、「実行できるか」が変わりうるという知らせを出す。知らせをまとめる枠が無いので、1 回ごとに読み手が全部読み直す。外す側の知らせは行 KM1a から、付ける側は行 KM2c（PR #821）からある。
- **割り当ては、キーを引く読みのものである。** 1 回 88 バイト（文脈を集める配列）で、1,560 回で約 137 KB になる。
- **行 KM2c の見積もりは誤っていた。** `docs/benchmarks/km2c-menu-actions.md` とロードマップは、「読み手 20 個なら、キーの読みが 1 フレームに 20 回、約 13 µs と 1.8 KB」と書いた。行の付け外しが 1 回の知らせになる、と考えていたためである。実際は 78 倍だった。
- 今の部品には、開いたままの読み手が無い（メニューの項目は、開いている間だけ読む）。ツールバーのボタン（行 B8）が入ると、この形になる。
- 貼り付け（`text::Paste`）は、20 種類に入れていない。欄の貼り付けは、聞かれた時にクリップボードを読むので、開いたままの読み手は、読み直すたびにクリップボードを読む。この費用は、この場面に入っていない。

- **時間は、行の数にほぼ比例する。** 深さ 1 の合わないキーで、1 行あたり約 2 ナノ秒である（87 行から 800 行で 0.21 → 1.59）。どの場合も、割り当ては 0 バイトである。

- 深さ 50 の合うキーが、87 行と 200 行で合わないキーより短いのは、合った所でキーの配送が終わり、キーのハンドラの経路をたどらないためである。
- **足した行は、フォーカスの文脈では成り立たない。** 成り立つ行が多いアプリは、この場面では測っていない。

## 決めたこと（行 KM3 の Grill、Issue #829）

- **索引は入れない。** 800 行でも、キー 1 回が深さ 1 で約 3 µs、深さ 50 で約 5.4 µs である。キーは 1 秒に多くて数十回で、フレームの予算にも入力の遅延にも現れない。GPUI も、キーの照合では全部の割り当てを端から見る（zed v1.25.3 の `crates/gpui/src/keymap.rs` 165〜174 行目）。
- **読み手の読み直しは、3 つを入れる**（設計書 §7「読み直しの知らせ」）。
  - 知らせを、読み手の経路に関わる変化だけにする。
  - 1 回の入れ替えの知らせを、1 つにまとめる。
  - キーを引く読みの割り当てを無くす。
- **直した後に測る場面を 2 つ足す**（PR #831 のレビュー）。値は、下の「直した後」にある。
  - フォーカスが一覧の行の中にある場面。フォーカスから読む読み手の経路が、付け外しされる行を通る。
  - `focus::Next` が実行できるかを読む読み手がいる場面。フォーカスを取れる行が付け外しされるたびに、読み直す。
- **この行で直さないもの。** 仮想化した一覧は、行が 1 つ入れ替わるたびに、箱の子を全部外して付け直す（`VirtualBlock.Relink`、この場面で約 78 回）。知らせをまとめても、この付け外しは残る。読み手 0 個のフレームにも、641.8 バイトの割り当てがある。どちらも原因を調べていない。ロードマップの行 Q15 で調べる。

## 直した後（実装の PR、Issue #829）

NativeAOT の Release（`win-x64`）。基準は直す前の `fc63536`、直した後は `183f744`。同じ場面のコードを両方で流した。論理プロセッサ 2 に固定し、優先度を High にし、基準・後・後・基準の順に 2 巡、1 つの版を 4 回ずつ流した。値は中央値で、角かっこは範囲。発行の警告は 0。実行ファイルは 7,741,440 → 7,747,584 バイト。

**CPU の負荷。** `readers` と `menu` を流している間、ほかのプロジェクトのプロセスが動いていて、負荷は 14〜57 % だった。同じ 2 つの場面を、負荷がこれより高い別の 2 回でも流し、下の値と同じだった（読み手 20 個のフレームの中央値は 9.55〜9.8）。`todo` は、負荷が 8 % より下の時に流し直した値である。

- **行にフォーカスがある場面。** 一覧の行はフォーカスを取れる箱で、フレームごとに、見えている範囲の上から 3 つ目の行へフォーカスを移してからスクロールする。読み手 1 個は、1 フレームに 2 回ずつ読み直す。フォーカスの移動で 1 回、行の入れ替えで 1 回である。入れ替えの約 78 回の付け外しは、1 回にまとまっている。読み手 20 個で約 20 µs 増え、読み直し 1 回（「実行できるか」とキーの組）が約 0.5 µs になる。
- **`focus::Next` の読み手がいる場面。** 読み手は、フォーカスの移動が実行できるかを読む。1 フレームに 2 回読み直す。新しく作った行がフォーカスを取れるようになった知らせで 1 回、入れ替えで 1 回である。約 2.4 µs 増える。木の全体をたどる読みなので、1 回が約 1.2 µs である。
- **この 2 つの場面の割り当ては 753.8 バイトで、読み手の数で変わらない。** 行がフォーカスを取れる箱であることの分で、`readers` の 641.8 バイトと同じく、出どころは調べていない（ロードマップの行 Q15）。

### 入力（`input`）

- **1 万個のノードの木で Tab を 1 回押す時間は、4 回とも長くなった。** 負荷のある 3 回で 164.9 → 168.6、164.4 → 167.2、157.8 → 161.4（約 2 %）、4 回目は 168.3 [165.6..169.4] → 183.1 [169.4..186.2] だった。4 回目の差が大きい理由は分からない。Tab の移動の経路（`FocusManager.MoveInTabOrder`）のコードは変えていない。Todo の段と一緒に、行 Q14 で確かめる。
