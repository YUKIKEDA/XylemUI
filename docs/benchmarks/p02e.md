# P02e: 仮想化

行 P02e（設計書 §3.4「P02e で入れる形」）を 2 つの PR に分けて入れる。Windows 11 26300、Intel Core i5-13400F、NativeAOT の Release で、プロセスを 1 つのコアに固定して（`start /b /wait /affinity 4 /high`）測った。比べる main は、各 PR の merge-base を `.dev/` の worktree で publish した。main と PR は、A・B・B・A の順を 2 回繰り返して流した。値は各回の中央値（p50）の範囲である。

## 再現

```powershell
$env:PATH += ';C:\Program Files (x86)\Microsoft Visual Studio\Installer'
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe frames --tree --list virtual"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe frames --tree --list for"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe frames --tree --scroll"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe frames --tree"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe layout"
cmd /c "start /b /wait /affinity 4 /high """" <dir>\XylemUI.E2E.exe lists"
```

## 1 つ目の PR: 作る範囲・大きさのキャッシュ・スクロールの基準・Cached と持つ行（Issue #610）

main は 31beca8。`frames --tree --list` の場面は、窓と同じ大きさの縦にスクロールする箱に、高さ 20 の行を 1 万個入れたものである。行は `VirtualFor` で作るか（`virtual`）、列の中の `For` で全部作る（`for`）。1 フレームごとに 7 px ずつスクロールする。`virtual` では、3 フレームに 1 回ほど、行を 1 つ作って 1 つ捨てる。`layout_ms` は、作る段の各回とその layout の pass の合計である。各 4 回、この PR だけで流した。

| `frames --tree --list` の値 | `virtual` | `for` |
| --- | --- | --- |
| CPU の 1 フレーム | 0.083〜0.095 ms | 0.621〜0.743 ms |
| 表示リストを作る段 | 0.012〜0.013 ms | 0.465〜0.558 ms |
| 作る段と layout（`layout_ms`） | 0.0072〜0.0080 ms | 0.0017〜0.0019 ms |
| GPU へ送る段（`draw_ms`） | 0.021〜0.025 ms | 0.106〜0.120 ms |

- `for` の表示リストを作る段は、1 万行をすべてたどって描く（描く段は、切られた行も飛ばさない）。`virtual` は、見える行だけを描く。Cached の行（前後 250 px）は layout するが描かない
- `layout_ms` は `virtual` のほうが長い。`for` は、スクロールで layout が走らず、空の pass だけを測る。`virtual` は、毎フレーム作る段が範囲を確かめ、行を作るフレームでは行を作り、箱を layout し直す。その分が 5〜6 µs である
- 作る行が変わらないスクロールのフレームの割り当ては 0 である（`VirtualListTests.SteadyState_ScrollKeepingTheRows_AllocatesNothing`、1,000 フレーム）

| 仮想化の無い経路の値 | main | この PR |
| --- | --- | --- |
| `frames --tree` の CPU の 1 フレーム | 0.634〜0.654 ms | 0.636〜0.652 ms |
| `frames --tree` の表示リストを作る段 | 0.0438〜0.0447 ms | 0.0437〜0.0448 ms |
| `frames --tree --scroll` の CPU の 1 フレーム | 0.138〜0.747 ms | 0.146〜0.157 ms |
| `frames --tree --scroll` の表示リストを作る段 | 0.053〜0.075 ms | 0.067〜0.077 ms |
| `layout` の S6b の 1 か所の変更 | 19.1〜21.1 µs | 19.1〜19.3 µs |
| `layout` の S6b の幅の変更 | 534〜585 µs | 528〜584 µs |
| `layout` のスクロールの 1 か所の変更 | 21.7〜23.9 µs | 21.5〜22.0 µs |
| `layout` のスクロールの範囲を書く時間 | 2.7〜2.8 µs | 2.6〜2.7 µs |
| `layout` の大きさの変更の後に範囲を書く時間 | 100.8〜115.7 µs | 103.8〜106.7 µs |
| `lists` の 1 万行の後ろに足す layout | 2,613〜2,854 µs | 2,609〜2,831 µs |

- `frames --tree` は、1 回目の 8 回で、main の 2 回が遅い状態（描く段 0.37〜0.40 ms）で走った。順を逆にした 8 回（上の表）は、8 回とも同じ状態で走り、範囲が重なった
- `frames --tree --scroll` の main の CPU の 1 フレームの上の端（0.747 ms）は、遅い状態で走った 1 回である
- 最初の実装では、`layout` の大きさの変更の後に範囲を書く時間が 205〜223 µs で、main の約 2 倍だった。範囲を求める走査（`ScrollableOverflowOf`）が、ノードごとに仮想化した箱かを判定していた。判定を外した写しを作って測ると、main と同じ値に戻った。直した形では、仮想化した箱が自分の layout の終わりに範囲の覚えた値を書き、走査はノードごとの判定をしない。覚えた値が古いとき（行が layout の起点になったとき）だけ、仮想化した箱の表を引く
- 実行ファイル（`XylemUI.E2E.exe`）は 5,555,712 バイトから 5,679,616 バイトになった（+124 KB）
