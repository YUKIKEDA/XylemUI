# K1a: キーとフォーカス

キーのイベントと配送、Win32 のキーのメッセージ、フォーカス・Tab・押したときのフォーカス・Focused の 3 つの擬似状態・ウィンドウの活性化を入れた（ロードマップの行 K1 の K1a、Issue #355、設計書 §7「キーの入力とフォーカス」・§7.1・§7.2）。その正しさと費用を確かめた。どれも Windows 11 26300、Intel Core i5-13400F で、時間は NativeAOT の Release で測った。

## 再現

```powershell
dotnet publish benchmarks/XylemUI.E2E -c Release -r win-x64 -o <dir>
<dir>/XylemUI.E2E.exe input     # イベント 1 つの配送。キーと Tab を含む（ウィンドウを開かない）
dotnet publish samples/Counter -c Release -r win-x64 -o <dir>
```

`input` の `us_per_key_depth_*` は、深さ 1 と 50 の箱の鎖の端の、フォーカスした葉から配るキーの Down である。どの箱も capture と bubble にハンドラを持つ。`us_per_tab_10101_nodes` は、100 行 × 100 個の葉（10,101 ノード）のすべての葉をフォーカスできるようにした木で、Tab 1 回（木を 1 回たどり、フォーカスを次の葉へ移して FocusOut と FocusIn を配る）の時間である。

## 正しさ

- **Core（`KeyFocusTests`、13 件）:**
  - キーは根から、フォーカスしたノードへの capture、そこから根への bubble で配り、`StopPropagation` で両方が止まり、止めたキーは処理済みになる
  - フォーカスが無いとき、ウィンドウがアクティブでないときは、根から配る
  - Tab は (TabIndex, 木の順) で進み、端で戻り、Shift で戻る。`Hidden` の部分木とフォーカスできないノードを飛ばす。Control・Alt・Meta の付いた Tab、止められた Tab、候補の無い Tab は動かない
  - 左ボタンの Down は、経路を配る前に、最も近いフォーカスできる祖先にフォーカスする。右ボタンと、何も無い所の Down は変えない
  - Focused・FocusVisible・FocusWithin の立ち方。輪はキーの後に出て、押した後に消え、次のキーで戻る。見た目を持つノードだけに印が付く
  - 表示リストで、FocusWithin・Focused・FocusVisible の見た目がこの順に重なる
  - 非アクティブで FocusOut、状態を下ろし、ノードは覚える。戻れば FocusIn。非アクティブの間の `Focus()` は覚えるノードを替える
  - FocusOut の後に FocusIn。どちらも、状態と `IsFocused` を書き換えた後に配る
  - 配っている途中の `Focus()` は、配り終えてから動かす
  - 外す（外す前に FocusOut）・祖先を隠す・`Focusable(false)` で、フォーカスが空になり、キーは根へ、次の Tab は先頭から
  - `Focus()` は、フォーカスできないノード・`Hidden` の祖先を持つノード・木に無いノード・自分が `Hidden` のノードに false を返す
  - 割り当て 0（`SteadyState_KeysTabAndFocusFrames_AllocateNothing`）: 深さ 50 のキーの配送、見た目を持つ 2 つのノードの間の Tab、それを描くフレーム
- **部品（`ButtonTests`、2 件）:** ボタンは Tab と押したときにフォーカスする。チェーンの `Focus`・`IsFocused`・`On(KeyEventKind…)`・`On(FocusEventKind…)` は、足した Scope で動く
- **Win32（`Win32WindowKeyboardTests`、5 件）:** メッセージを `KeyInput` に直す関数（左右の修飾キー、スキャンコードと拡張の印、bit 30 は Down だけ、`VK_PROCESSKEY`・`VK_PACKET` は配らない）。`ToUnicodeEx` の結果の文字（死んだキー・2 文字・制御文字は無し、サロゲートの組は 1 文字）。処理したキーのメッセージは 0 を返す。`SC_KEYMENU` は 0 を返してメニューのループに入らず、`WM_MENUCHAR` は `MNC_CLOSE` を返す。`WM_ACTIVATE` の 3 つの値。止めなかったキーを `DefWindowProc` がどう扱うか（Alt+F4 で閉じる）は、キーボードの状態を読むので `SendMessage` では作れず、確かめていない
- **ポインタ（`Win32WindowPointerTests`）:** マウスのメッセージの修飾キーに、`GetKeyState` から読んだ Meta が入る
- **ミュータント:** 22 個。21 個は狙ったテストが落ちた。残る 1 個（アクティブに戻ったとき、覚えたノードがフォーカスできるかを確かめない）は、届かない分岐だった。覚えたノードがフォーカスできなくなる道（外す・隠す・`Focusable(false)`）は、どれもその場でフォーカスを空にする。分岐を消した
  - 最初は 2 個が残った。もう 1 個（新しいノードの状態を FocusOut の後に立てる）は、FocusOut のハンドラの中で状態を確かめていなかった。テストに足した

## 費用

### イベント 1 つの配送（`input`、3 回ずつ交互、21 標本の中央値）

main は 944ed17。

| 場面 | main | K1a |
| --- | --- | --- |
| 深さ 1 の移動 | 0.149〜0.239 µs | 0.151〜0.173 µs |
| 深さ 50 の移動 | 4.82〜5.59 µs | 5.25〜6.09 µs |
| ホバーが変わる移動 | 0.174〜0.206 µs | 0.194〜0.213 µs |
| Click | 0.261〜0.291 µs | 0.280〜0.305 µs |
| ホイール | 0.089〜0.090 µs | 0.081〜0.091 µs |
| 深さ 1 のキー | — | 0.051〜0.081 µs |
| 深さ 50 のキー | — | 1.72〜2.04 µs |
| 10,101 ノードの Tab | — | 196〜211 µs |

- 移動・ホバー・ホイールは、main と範囲が重なる
- Click の中央値は約 0.02 µs 長い。左ボタンの Down が、経路を配る前に、押したノードから根まで、フォーカスできるノードを探してたどる分である
- 最初の版のホバーは 0.217〜0.232 µs（main 0.189〜0.190 µs）だった。擬似状態の印を付けるかを決めるとき、`PseudoStyles` から約 108 バイトの `PaintStyle?` を値で取り出して `null` かを見ていた。取り出さずにその場で確かめる形にすると、0.194〜0.197 µs で main と重なった
- キーはポインタより速い。ヒットテストとホバーの集合を求めず、経路だけを作って配る
- Tab 1 回は 10,101 ノードで約 200 µs、1 ノード約 19 ns である。たどる走査は、ノードごとに `Input`（576 バイトのノードの 16 バイト目）、兄弟と子への辺（80 バイト目の前後）、`Hidden`（168〜391 バイト目の `Style` の中）を読み、3 つの別の 64 バイトの行に触れる。葉の 100 個に 1 個だけをフォーカスできるようにした一時のビルドでも 182〜189 µs で、葉ごとの `NodeInput` の参照の分は 1 割ほどだった（ビルドはブランチに入れていない）。Tab は 1 回のキーで 1 回なので、フレームの予算（16.7 ms）の 1.2 % である
