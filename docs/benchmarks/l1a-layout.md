# L1a のレイアウトの基準値

Block / Flex を CSS の意味にしたレイアウト（ロードマップの行 L1a、Issue #82、設計書 §3.2）の費用を、同じ場面の Flutter・Avalonia・Taffy（GPUI のレイアウト）と、同じ機械で同じ方法で測った。受け入れはこの表で判定した（設計書 §3.2 の「性能の受け入れ」）。

## 測った物と機械

- コミット: このファイルを加えたコミット（`git log -1 -- docs/benchmarks/l1a-layout.md`）
- 機械: M1a と同じ（`docs/benchmarks/m1-baseline.md`）
- 場面: 列 1 → 行 100 → 10 × 10 の葉 100 個ずつ（10,101 ノード）を 2,000 × 2,000 で layout する。測るのは、最初の layout（作ったばかりの木）、葉 1 つの幅を 10 と 20 で変えた後の layout、窓の幅を 1,600 と 2,000 で変えた後の layout
- XylemUI と Taffy は 3 つの場面で測る。S6b の意味（フレックスの子の min を 0 にして、自動の最小サイズを切る）、CSS の既定（`align-items: stretch` と自動の最小サイズ）、`%` あり（葉の幅 1 %、パディング 0.1 %）
- 版と作り方:
  - XylemUI: `benchmarks/XylemUI.E2E` の `layout` シナリオ（NativeAOT）
  - Flutter 3.38.5（Windows のリリース）: `benchmarks/compare/flutter/lib/layout_scene.dart`。レンダーツリー（縦と横の `RenderFlex` と、10 × 10 の `RenderConstrainedBox`）を `PipelineOwner` に付け、`layout` と `flushLayout` を測る（ウィジェットとフレームは含まない）
  - Avalonia 12.1.4（NativeAOT）: `benchmarks/compare/Avalonia` の `--layout`。縦と横の `StackPanel` と、10 × 10 を返すコントロールを headless のプラットフォームのウィンドウに載せ、`UpdateLayout`（レイアウトの管理の 1 回の pass）を測る。ウィンドウに載せない木は、子の変更が親に届かない
  - Taffy 0.9.0（GPUI 0.2.2 が使う版、Rust 1.99.0 のリリース、thin LTO）: `benchmarks/compare/taffy`。丸めない（XylemUI も丸めない）

意味の違い: Flutter と Avalonia には、自動の最小サイズも、stretch の後の測り直しも無い。比べているのは「同じ見た目の UI を出す時間」で、同じ計算の時間ではない。Taffy は XylemUI と同じ CSS の意味。

## 再現

```powershell
./benchmarks/compare/build.ps1 -Out <dir>
./benchmarks/compare/layout.ps1 -Built <dir> -Rounds 5
<dir>/xylemui/XylemUI.E2E.exe layout-loop <s6b|auto_min|percent> <change|width> 100000   # プロファイル用
```

## 結果

`layout.ps1` で、XylemUI → Taffy → Flutter → Avalonia の順を 5 ラウンド交互に測った。各実行は 15 回（Flutter・Avalonia・Taffy は 18 回から最初の 3 回を除いた 15 回）の中央値で、表はラウンドの中央値、括弧は最小〜最大。

| 指標 | Flutter | Avalonia | Taffy（S6b の意味） | XylemUI（S6b の意味） | Taffy（CSS の既定） | XylemUI（CSS の既定） | Taffy（`%` あり） | XylemUI（`%` あり） |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 最初の layout（µs） | 1,347（966〜1,365） | 5,488（5,215〜5,594） | 7,677（7,201〜7,866） | 3,858（3,728〜3,991） | 7,546（7,282〜8,126） | 7,666（7,143〜8,045） | 7,734（7,622〜11,063） | 5,412（5,232〜5,669） |
| 1 か所の変更（µs） | 6.0（5.0〜7.0） | 28.8（28.2〜29.1） | 62.7（62.2〜63.0） | 28.7（27.2〜29.7） | 62.0（61.7〜62.6） | 53.1（52.9〜54.0） | 67.7（67.2〜104） | 43.1（41.6〜43.9） |
| 幅の変更（µs） | 787（471〜1,076） | 328（287〜374） | 5,252（5,030〜5,600） | 939（910〜989） | 5,108（5,013〜6,579） | 1,586（1,487〜1,862） | 6,933（6,516〜8,634） | 1,926（1,753〜2,041） |

XylemUI の固定サイズの行の中の変更は、S6b の意味で 8.8 µs、CSS の既定で 35.6 µs、`%` ありで 30.3 µs（ラウンドの中央値）。S6b の基準値（S6b の簡略な flex、Issue #30）は、最初の layout 1,571 µs、1 か所の変更 21.1 µs、固定サイズの行の中の変更 5.5 µs、幅の変更 1,638 µs。

## 数字の内訳

- **計算の回数**: 最初の layout で、ノードのアルゴリズムか計測関数が動いた回数は、XylemUI で S6b の意味 40,201 回、CSS の既定 90,301 回、`%` あり 60,301 回（葉 1 つあたり 4・9・6 回）。Taffy の `main`（e82f526）の葉は 40,000・90,000・60,000 回で同じ、Taffy 0.9.0 は 60,000・60,000・90,000 回。CSS Flexbox の手順は、子の内容の大きさを測ってから伸縮を解き、stretch で交差軸が決まった後にもう一度測る。Flutter の `Row` は伸縮しない子を緩い制約で 1 回 layout するだけで、ノード 1 つに 1 回（約 10,100 回）
- **1 回の費用**: 最初の layout を回数で割ると、XylemUI は 1 回あたり約 92 ns、Flutter は約 89 ns（Dart の AOT）。差は回数から来る
- **1 か所の変更**: XylemUI は、変えた葉の行と根の列の flex を、手順どおり解き直す（子はキャッシュに当たる）。Flutter は、清潔な子に「制約が前回と同じなら返す」確認（4 つの double の比較）をするだけ
- **Avalonia の幅の変更**: 横の `StackPanel` が子を無限の幅で測るので、窓の幅が変わっても子は測り直さず、配置し直すだけになる

## 受け入れ（設計書 §3.2、L1a の Grill で決め直した）

- (1) 意味が同じ GPUI のレイアウト（Taffy 0.9.0）よりばらつきを超えて遅くない: すべての場面と場合で満たす
- (2) 幅の変更が Layout の予算 2.0 ms の内側: 満たす（ラウンドの最良値で S6b の意味 910 µs、CSS の既定 1,487 µs、`%` あり 1,753 µs。`%` ありは最大 2,041 µs）。1 万ノードの最初の layout はフレームの予算に入れず、(1) で見る
- (3) 定常状態のアロケーション 0: `SteadyState_RelayoutAfterOneChange_AllocatesNothing`（CSS の既定と `%` あり）
- Flutter（最初の layout と 1 か所の変更）と Avalonia（幅の変更）との差は、行 L4 で詰める

## 決めるために測ったこと

**計測のキャッシュの数**（設計書 §3.2: 1・2・4・9 で測り、時間がそれ以上下がらない最小の数）。3 ラウンド交互、最良値。測ったのは途中のコミットで、表の後で最適化した分は入っていない。

| 指標 | 1 | 2 | 4 | 9 |
| --- | --- | --- | --- | --- |
| `UiNode` の大きさ（バイト） | 528 | 608 | 768 | 1,168 |
| `Arena.TryGet`（ns） | 25.6 | 25.6 | 26.3 | 27.1 |
| CSS の既定・1 か所の変更の計算の回数 | 60,400 | 802 | 802 | 10 |
| CSS の既定・1 か所の変更（µs） | 6,589 | 112 | 126 | 82.5 |
| CSS の既定・幅の変更（µs） | 9,442 | 10,061 | 2,227 | 2,704 |
| `%` あり・1 か所の変更（µs） | 4,700 | 87.5 | 94.6 | 62.6 |

N = 9 にした。4 以下では、1 か所の変更で計算し直しが 80 倍に増える。

**キャッシュの置き場所**（設計書 §3.2: `UiNode` の中と、ノードの外の配列）。4 ラウンド交互、最良値。外の配列にした（`UiTree.MeasuresOf`）。

| 指標 | 外の配列 | `UiNode` の中 |
| --- | --- | --- |
| `UiNode` の大きさ（バイト） | 432 | 1,160 |
| S6b の意味・最初の layout（µs） | 4,848 | 5,676 |
| S6b の意味・幅の変更（µs） | 1,232 | 1,529 |
| CSS の既定・幅の変更（µs） | 2,002 | 2,310 |
| CSS の既定・1 か所の変更（µs） | 62.9 | 62.3 |

**試して残したもの**（6 ラウンド交互、前のコミットと比べた）: スタイルをコピーせず参照で読む、`%` を使うかをスタイルを設定したときに計算する、キャッシュのキーを手で比べる（コンパイラの比較は項目ごとに比較器を通り、走査の 1 回の当たりに約 200 ns かかった）、座標の小さな関数を `AggressiveInlining` にする（全項目で 10〜18 % 速い）、エンジンの小さな関数を `AggressiveInlining` にする（全項目で 5〜11 % 速い）。

**試して戻したもの**（差がばらつきの中）: キーに 64 ビットのハッシュを持たせて先に比べる、キーの比較の順を入れ替える、葉のスタイルをコピーせず読む、計測の問い合わせで計測のキャッシュを先に引く。
